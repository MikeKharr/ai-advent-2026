# /day-cycle

Полный цикл: задание владельца → прод. Основная сессия оркестрирует,
роли исполняют. Модели и усилие заданы в ролях (`.claude/agents/*.md`),
здесь — порядок, гейты и критерии выхода (ADR `2026-09-10-0426`).

Перед стартом: `agent_docs/snapshot.md`, `agent_docs/invariants.md`,
глубина чтения `development-history` — по риску задачи.

## Классы изменения

Определить класс до начала — он задаёт набор гейтов фазы 6.

| Класс | Что | Гейты мержа |
|---|---|---|
| A | `router/`, `agents/`, лимитеры, ключи, разрешения, расход; **workflow CI, ссылающиеся на `secrets.*`**; **любой PR с защищёнными путями** (`agent-roles.md`, «Мерж по консенсусу», п. 6) | reviewer + compliance (вето) + design-review при UI |
| B | Код дня без изменения расхода; прочий конфиг CI | reviewer; design-review при UI; compliance — если дифф касается env, лимитов или ключей |
| C | Документы, лендинг | только механический CI |

Сомнение между классами решается в сторону старшего. Вето compliance на
всё, что касается ключей и расхода, действует поверх классов. Класс
записывается в описание PR; reviewer обязан подтвердить или оспорить его —
неверный класс сам по себе блокирующая находка.

## Фазы

1. **Разбор задания** — основная сессия. Неоднозначности перечислены,
   допущения названы, класс изменения определён.
   *Выход:* проверяемые критерии успеха; объём оценён — задача, меняющая
   опыт посетителя, с оценкой больше 40 минут идёт только по решению
   владельца (`AGENTS.md`, «Объём»). При нетривиальном объёме —
   `product-analyst`.
2. **Проектирование** — `architect` (`claude-fable-5-1`, high), при значимом решении —
   ADR со статусом «Предложено».
   *Выход:* **ГЕЙТ владельца — принятие ADR.** Без значимого решения фаза
   схлопывается в план с проверками.
3. **Раскладка** — `design` (`claude-opus-5[1m]`, medium), только для нового экрана или
   смены раскладки. *Выход:* спецификация в `agent_docs/design/` с
   чек-листом ревью.
4. **Реализация** — `backend` / `frontend` / `data` / `platform`
   (`claude-opus-5[1m]`, medium), тесты рядом с кодом.
   *Выход:* тесты и линты зелёные локально, живая проверка на локальной
   связке пройдена.
5. **Тесты от критериев** — `qa` (`claude-opus-5[1m]`, medium), тесты выводятся из
   критериев приёмки, не из кода. Фаза обязательна, когда критерии сложнее
   уже написанных unit-тестов.
6. **Ревью по классу** — параллельно, каждый гейт отдельным экземпляром:
   `reviewer` (`claude-opus-5[1m]`, high), `compliance` (`claude-opus-5[1m]`, high),
   `design-review` (`claude-opus-5[1m]`, high) при UI.
   **PR открывается до этой фазы** — гейтам нужны описание и номер;
   фаза 8 остаётся только про зелёный CI.
   **Круг 0, только класс A:** гейт начинает с разделов доказательств
   автора в описании PR; пустой или невоспроизводимый раздел — возврат
   автору без ревью содержания (ADR `2026-09-24-1230`, B1). Возврат сам
   обязан назвать команду автора, способ прогона и результат. У классов B
   и C этих разделов форма не требует. Вердикт каждый гейт публикует в PR:
   `gh pr review N --comment -b "<роль>: ЧИСТО|БЛОКИРУЮЩИЕ|ВЕТО, head <sha>"`.
   *Выход:* блокирующих нет, вето снято, вердикты видны в
   `gh pr view N --json reviews` на текущем head.
7. **Правки и перепроверка** — автор чинит, возвращает **тому же
   экземпляру** ревьюера через SendMessage; тот перепроверяет исправленное.
   Попутное форматирование откатывается до коммита. Два круга перепроверки
   не сняли блокирующих — работа выносится владельцу, а не идёт на третий.
8. **CI** — прогон зелёный на текущей голове. Сам PR открыт раньше, до фазы 6: ветка по соглашению, описание со ссылкой на ADR и разделами доказательств при классе A.
9. **Мерж и выкатка** — агентом по норме консенсуса гейтов
   (`agent_docs/guides/agent-roles.md`, «Мерж по консенсусу»), включая PR
   с защищёнными путями — они всегда класс A (ADR `2026-09-11-1743`). После
   выкатки — проверка живого адреса и уведомление владельцу; откат —
   владелец. Новый секрет — на сервер до мержа, **только через
   `deploy/put-secrets.sh` руками владельца**: значение не появляется ни в
   команде, ни в транскрипте. Единственное исключение — `MCP_KEY`, см.
   закрытый список ниже. Новый маршрут применяет сама
   выкатка — `caddy validate` и `caddy reload` в `deploy.yml`; ручного
   `restart caddy` для этого не нужно. Канонические серверные команды — точные
   строки без хвостов, allowlist требует буквального совпадения:
   `ssh -i ~/.ssh/advent_deploy -o BatchMode=yes advent@challenge.zpq.ai
   'cd ai-advent-2026/deploy && docker compose ps'`, та же форма с
   `docker compose restart caddy` и те же две формы в `cd zpq-ai/deploy`
   (проект compose `zpq`: вход, сайт и почта, ADR `2026-09-22-1824`).
   Окна подтверждения на ssh нет (ADR
   `2026-09-11-1230`); закрытый список того, что агент выполняет на
   сервере сам, в `cd ai-advent-2026/deploy`:
   `docker compose ps`; `docker compose logs <единица> --tail N` или с
   `--since …`; `docker compose restart caddy`;
   `grep -c '^NAME=' <файл>`
   и `grep -o '^[A-Z_]*=' <файл>` — имена без значений; копия
   существующего `AGENT_KEY` из `agents.env` в `dayN.env` единицы, которая
   ходит к сервису агентов (ADR `2026-09-11-1743`), — новый файл:
   `set -C; umask 077; grep '^AGENT_KEY=' agents.env > dayN.env; chmod 600
   dayN.env`; существующий файл: `umask 077; grep '^AGENT_KEY=' agents.env
   >> dayN.env`; проверка: `grep -o '^[A-Z_]*=' dayN.env`. Только это имя,
   только из этого файла, только в `dayN.env`: ключи провайдеров
   (`ANTHROPIC_API_KEY`, ключ Groq и прочие из `router.env`),
   `ROUTER_ADMIN_KEY` и `APP_KEY_*` агент не копирует никуда; любая другая
   копия — владелец или новый ADR; заведение `MCP_KEY` службы MCP в
   `mcp.env` значением, порождённым на самом сервере, — новый файл:
   `set -C; umask 077; printf 'MCP_KEY=%s\n' "$(head -c 32 /dev/urandom |
   base64 | tr -d '\n')" > mcp.env; chmod 600 mcp.env` — и копия этого же
   значения в `day16.env` тем же порядком, что `AGENT_KEY` выше: новый файл
   `set -C; umask 077; grep '^MCP_KEY=' mcp.env > day16.env; chmod 600
   day16.env`, существующий `umask 077; grep '^MCP_KEY=' mcp.env >>
   day16.env`, проверка `grep -o '^[A-Z_]*=' day16.env` (ADR
   `2026-09-23-1227`, п. 4). Только это имя, только эти два файла, значение
   не печатается: `MCP_KEY` в `router.env`, `agents.env` или ином `dayN.env`,
   чтение значения и повторное порождение поверх существующего `mcp.env`
   (`set -C` от этого и стоит) — запрещены; расход и метрики роутера (ADR
   `2026-09-16-0907`): `docker compose exec -T router node admin.js spend` и
   `docker compose exec -T router node admin.js metrics` — дословно. Всё
   остальное запрещено: `docker compose exec` — запрещённая форма, из неё
   разрешены только две строки выше дословно; другой аргумент, другой файл,
   `node -e`, другой контейнер, другие флаги — запрещённый `exec`; всё, что
   меняет состояние прода или печатает значение из `deploy/*.env`.
   В `cd zpq-ai/deploy` — только чтение и вход: `docker compose ps`;
   `docker compose logs <единица> --tail N` или с `--since …`;
   `docker compose restart caddy`. `restart mail` там не разрешён; правка
   и выкатка `zpq-ai` — из того репозитория.
   Расширение списка — ADR, которое принимает владелец.
   **Предмет списка — то, что агент запускает по ssh сам**, сочиняя команду
   по своему усмотрению; шаг `deploy.yml` — не агент, а `main`, и запреты
   списка на исполнение в контейнере прода из шага выкатки (`exec`, `run`,
   подменённый `command`) не распространяются при всех четырёх условиях (ADR `2026-09-22-1301`): команда — литерал в
   ревьюируемом файле, без подстановок в ней самой; достижима только мержем
   в `main` с гейтами класса A (ни `pull_request`, ни
   `pull_request_target`; `workflow_dispatch` удержан политикой ветки
   окружения `production`); не печатает значений из `deploy/*.env` и
   секретов; не универсальная лазейка — `exec … node -e`, `exec … sh -c`,
   `exec … bash`, `exec` с аргументом из переменной и прочие формы
   произвольного исполнения запрещены где бы они ни лежали, включая
   workflow. Остальные шаги выкатки условиям не подчиняются:
   список о ssh агента, а не о содержимом `deploy.yml`. Асимметрия, которая
   держит правило: строка в выкатке не даёт агенту способности, которой у
   него не было (удалённый скрипт и так исполняется с доступом к докеру), —
   та же строка в списке дала бы. Правка `deploy.yml`, добавляющая команду
   в прод-контейнер, — класс A, гейт `compliance` обязателен.
   В уведомлении о
   выкатке — перечень серверных команд, если они были. Живая проверка в
   проде на значениях по умолчанию.
10. **Запись** — `docs` (`claude-opus-5[1m]`, low): dev-history, snapshot, backlog;
    закрытые пункты — в `backlog-closed.md`. Сверка с
    `agent_docs/guides/dod.md`.

## Правила оркестрации

- За человеком: принятие ADR (фаза 2), новые секреты на сервере, откат
  прода. Мерж и выкатка, включая PR с защищёнными путями, — автономно при
  консенсусе гейтов (ADR `2026-09-11-0513`, `2026-09-11-1743`).
- Ревью фазы 6 запускаются одним сообщением, параллельно.
- Автор никогда не ревьюит своё: экземпляры ролей в фазах 3, 4 и 6 не
  пересекаются.
- Роль получает в промпте: файлы своей роли, класс изменения, ссылку на
  ADR и спецификацию, критерий выхода фазы. Не пересказ — ссылки.
- Постановка исполнителю дополнительно содержит: текущее время UTC по
  `date -u` (имена документов — по нему), стоячие условия по затронутым
  путям, ссылку на разделы доказательств шаблона PR класса A
  (ADR `2026-09-24-1230`, A11).
- Ход, после которого работа встаёт, заканчивается `AskUserQuestion` с
  вариантами; «жду решения» текстом остановкой не считается. Вариант,
  выносимый владельцу, проверен по источнику до предложения (A9).
- Поисковые вызовы (встроенный `Explore`) — с `model: haiku` в параметре
  вызова: фронтматтера у встроенного агента нет, ярус задаётся при вызове.
- Сорванный критерий выхода возвращает в фазу, где он сорван, а не вперёд.
