# /design-review

## Цель

Решить, готов ли экран к мержу: соблюдён ли дизайн-корпус, покрыты ли состояния,
не нарушены ли инварианты продукта.

Ревью ведётся по фактам. Замечание без конкретного значения, селектора или строки
замечанием не считается — оно неопровержимо и невыполнимо.

## Приоритет

1. Инварианты (`agent_docs/invariants.md`) — выше корпуса. Красивое решение,
   нарушающее I-7 или I-8, отклоняется без обсуждения вкуса.
2. Дизайн-корпус (`agent_docs/design/corpus.md`).
3. Общая дизайн-рекомендация — только с префиксом `Общая рекомендация:`.

Конфликт двух правил корпуса равного веса не примиряется самостоятельно: он выносится
владельцу.

## Порядок

### 1. Прочитать корпус

`agent_docs/design/corpus.md` целиком. Ревью без корпуса — вкусовщина.

### 2. Собрать факты

Для файла экрана (например `days/dayN/public/index.html`):

```bash
F=days/dayN/public/index.html
grep -oE '(margin|padding|gap)[^;]*;' "$F" | grep -oE '[0-9]*\.?[0-9]+rem' | sort -u   # шкала отступов
grep -oE 'font-size:[^;]*;' "$F" | sort -u                                             # размеры шрифта
grep -oE 'border-radius:[^;]*;' "$F" | sort -u                                         # радиусы
grep -cE ':hover|:active|:focus|\[disabled\]' "$F"                                     # правил состояний всего
grep -c 'focus-visible' "$F"                                                           # из них focus-visible
grep -nE 'prefers-color-scheme|prefers-reduced-motion' "$F"                            # темы и движение
grep -c 'tabular-nums' "$F"                                                            # числа в колонках
```

Зафиксировать числа. «Много разных отступов» — не факт; «21 уникальное значение при
шкале из 8» — факт.

### 3. Проверить по списку

**Шкалы.** Все отступы из шкалы 4px; ≤ 5 размеров шрифта на экране; радиусы только
из трёх токенов. Значения вне шкалы перечислить поимённо.

**Состояния интерактивных элементов.** Для каждой кнопки, поля, чипа и ссылки —
пять состояний. Отдельно проверить `:focus-visible` на **каждом** интерактивном
элементе: чаще всего он есть только у полей ввода, а у кнопок и чипов отсутствует.

**Состояния контента.** Пусто, загрузка, ошибка, частичный результат — все четыре
определены и достижимы. Пустое состояние объясняет причину (I-8).

**Цвет и контраст.** Обе темы. Основной текст ≥ 4.5:1, крупный текст и границы
элементов управления ≥ 3:1. Цвет не единственный носитель смысла. Не больше одного
акцента в поле зрения.

**Числа.** Всё, что сравнивают глазами (токены, счётчики, даты), — `tabular-nums`.

**Ритм и полоса чтения.** Проза ≤ 68ch. Отступы между блоками больше внутренних.

**Инварианты.** Ни одно правило вёрстки не заставляет показать больше, чем есть
(I-8), и не прячет источник (I-7).

**Внешние ресурсы.** Ни одного шрифта, скрипта или стиля с CDN: сторонний запрос
уносит адрес пользователя и задерживает первый рендер.

### 4. Вердикт

- `ГОТОВО` — нарушений корпуса нет либо они объяснены и приняты.
- `ПРАВКИ` — список конкретных правок; каждая с селектором и целевым значением.
- `ПЕРЕДЕЛАТЬ` — нарушен инвариант, отсутствует состояние контента или экран собран
  вне системы (шкал нет вовсе).

## Отчёт

Коротко и по делу, на языке владельца. Формат:

```text
Вердикт: ГОТОВО | ПРАВКИ | ПЕРЕДЕЛАТЬ
Факты: отступов N (шкала 8), размеров шрифта N, состояний N/M элементов, контраст …

Правки:
1. <селектор>:<строка> — <что> → <целевое значение из корпуса>
```

Не пересказывать корпус, не хвалить, не предлагать смежные улучшения. Только то,
что мешает мержу, и что с этим делать.

## Границы

Скилл ревьюит, а не переписывает: правки вносит автор UI. Автор экрана не ревьюит
свой экран — ревью ведёт другой экземпляр агента (роль `design`).
