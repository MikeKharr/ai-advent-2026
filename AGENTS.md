# Правила работы над проектом

> Для проектов, созданных из шаблона `2030ai/2030ai-project-template`: если в репозитории присутствует `agent_docs/setup-checklist.md` — пройти его и удалить.

## Описание проекта

- **Проект:** `ai-advent-2026` — веб-приложение AI Advent 2026. Пользователь вводит сферу (fintech, climate tech, robotics), приложение возвращает 3 главные свежие новости стартапов в этой сфере со ссылками на источники.
- **Цели пользователя/команды:** пройти задания AI-адвента и одновременно отработать полный цикл разработки — проектирование, архитектурные решения, разработку, документацию, тестирование — на маленьком проекте, чтобы перенести практики в основной проект HBK.SG.
- **Как используется:** публичный репозиторий, публичный HTTPS-адрес. Посетитель вводит сферу в поле, получает три карточки новостей. Аутентификации нет, данные пользователей не хранятся.
- **Контекст и ограничения:** Node 22 без runtime-зависимостей; LLM — Anthropic Messages API с server-side инструментом `web_search`; деплой — Docker Compose на одном VPS Vultr (Singapore) за Caddy. Публичный URL держит платный API-ключ, поэтому контроль расхода — обязательная часть продукта, а не опция.

## Принципы работы агента

> Эти принципы смещают баланс в сторону точности и минимализма за счёт скорости. Для тривиальных задач — здравый смысл.

### 1. Понять до начала действий

**Не додумывай. Не скрывай неуверенность. Озвучивай компромиссы.**

- Явно проговори допущения перед началом.
- Если задача допускает несколько прочтений — перечисли их и выбери самостоятельно с кратким обоснованием. Не выбирай молча.
- Если есть более простой путь — скажи об этом. Возражай аргументированно.
- Если что-то непонятно — остановись, назови что именно непонятно, спроси.

Формат вопросов: коротко и по делу. Контекст вопроса прикладывать отдельно (списком ссылок/цитат), чтобы пользователь мог ознакомиться при необходимости.

### 2. Минимум необходимого

**Минимальный объём решения, ничего спекулятивного.**

- Никаких возможностей сверх того, что просили.
- Никаких абстракций для одноразового результата.
- Никакой «гибкости» и «конфигурируемости», которые не запрашивались.
- Никакой защиты от сценариев, которые не могут произойти.
- Если получилось много, а можно было меньше — переделай.

Тест: сказал бы опытный коллега, что это переусложнено? Если да — упрости.

### 3. Точечные изменения

**Касайся только того, что нужно. Убирай за собой только своё.**

- Не «улучшай» соседний материал, форматирование, формулировки.
- Не пересобирай то, что не сломано.
- Подстраивайся под существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанное «мёртвое» — упомяни, не удаляй.
- Удаляй только то, что ТВОИ правки сделали ненужным. Чужое «мёртвое» не трогать.

Критерий: каждое изменение должно прослеживаться к запросу пользователя.

### 4. Работа от проверяемой цели

**Сформулируй критерий успеха. Доводи до проверки.**

Преобразуй задачу в проверяемую цель:

- «Добавить раздел» → «Описать, что должно появиться; убедиться, что оно есть и связано с остальным».
- «Починить баг» → «Воспроизвести шагами; убедиться, что воспроизведение перестаёт работать».
- «Привести в порядок» → «Зафиксировать состояние до; убедиться, что критерий после выполнен».

Многошаговые задачи — короткий план с проверками:

1. [Шаг] → проверка: [как убедиться]
2. [Шаг] → проверка: [как убедиться]

Сильные критерии успеха позволяют работать автономно.

## Автономность

- Работать самостоятельно и доводить задачу до конца.
- Не запрашивать согласование на рутинные решения. Согласование — только перед необратимыми действиями или действиями, влияющими на shared систему. Мерж в `main` и выкатка — по норме мержа по консенсусу ниже.
- При нехватке контекста — сначала вывести из имеющихся артефактов; если действительно не хватает — задать 1–2 коротких вопроса с приложенным контекстом отдельно.

За человеком всегда: **принятие ADR**, **изменения гейтов и правил процесса** (PR с защищёнными путями сливает только владелец) и **откат прода**. Мерж и выкатку делает агент при консенсусе гейтов; условия и список защищённых путей — ADR `2026-09-11-0513` и `agent_docs/guides/agent-roles.md`, «Мерж по консенсусу».

### Объём

- Задача, меняющая опыт посетителя (экран, тексты, поведение, доступность), с оценкой реализации больше 40 минут — только по решению владельца. Оценивает оркестратор до запуска, по полному объёму, без дробления.
- Прочие задачи (CI, безопасность, тесты, документы) агенты сами не открывают: только то, что входит в текущую задачу владельца, включая блокирующие находки её PR.
- Находки ревьюеров за рамками PR — в `agent_docs/backlog.md` с пометкой «Владельцу», в работу не берутся.
- Исключение — особый режим: владелец объявляет его явно и с рамками.

## Назначение AGENTS.md и границы

- AGENTS.md содержит только универсальные правила, применимые ко всем задачам в проекте.
- Специфические инструкции — в `agent_docs/`; не раздувать AGENTS.md.
- Все проектные документы — в `agent_docs/`, кроме `README.md`, `AGENTS.md`, `CLAUDE.md`.
- Событийные документы вести атомарно: одна итерация, решение, проверка или отчёт — один файл по правилам `agent_docs/guides/atomic-documents.md`.

## Роли агентов

- Роли определены в `.claude/agents/*.md`. Карта ролей и протокол передачи — `agent_docs/guides/agent-roles.md`. Оркестрация полного цикла — скилл `/day-cycle`.
- **Модель и усилие — свойство роли** (ADR `2026-09-10-0426`): высокоуровневое проектирование (`architect`: архитектура, потоки данных, проектирование гейтов, AI-харнесс) — fable/high; прочее проектирование и гейты ревью (`design`, `design-review`, `reviewer`, `compliance`) — opus/high; реализация и тесты — opus/medium; запись — opus/low. Задано во фронтматтере ролей, не в вызове.
- **Гейты мержа — по классу изменения** (ADR `2026-09-10-0426`): A — деньги/данные/ключи и workflow CI с `secrets.*`: reviewer + compliance + design-review при UI; B — обычный код и прочий конфиг CI: reviewer, design-review при UI; C — документы и лендинг: только механический CI. Сомнение — в сторону старшего класса. Класс пишется в описание PR, reviewer его подтверждает. Вето `compliance` действует поверх классов.
- **Автор кода никогда не ревьюит свой код.** `reviewer` обязан быть другим экземпляром агента, чем `backend`/`frontend`. После правок блокирующих находок работа возвращается **тому же экземпляру** ревьюера на перепроверку.
- `compliance` имеет право вето на изменения, затрагивающие API-ключ, расход средств и защиту от злоупотреблений.
- **UI:** раскладка от `design` до кода — для нового экрана или смены раскладки; перед мержем любого изменения UI — ревью ролью `design-review` по скиллу `/design-review` против `agent_docs/design/corpus.md` (ADR `2026-09-08-1110`, уточнено ADR `2026-09-10-0426`). Реализует `frontend`; экземпляры раскладки, реализации и ревью не пересекаются.

## Project-Local Skills

- Если проекту нужны локальные skills, источник истины: `.agents/skills/<name>/SKILL.md`.
- Platform mirrors: `.claude/skills/<name>`, `.codex/skills/<name>`, `.cursor/skills/<name>` должны быть symlink на `../../.agents/skills/<name>`.
- Skill metadata собственных скиллов проекта должна показывать ту же slash-команду, которую вызывает пользователь: `name: <command>`, description начинается с `/<command>`, первый H1 — `# /<command>`, `agents/openai.yaml display_name: "/<command>"`. На vendored-набор ниже это правило не распространяется.
- Не создавать новые slash-command файлы; полезные workflows оформлять как skills.
- Manifest всегда называется `SKILL.md`.
- В `.agents/skills/` установлен набор `addyosmani/agent-skills` (ADR `2026-09-07-2350`). Ключевые skills **предзагружены в роли** через фронтматтер `skills:` (ADR `2026-09-10-0426`): `architect` — spec-driven-development и planning-and-task-breakdown, `backend`/`frontend` — incremental-implementation и test-driven-development, `qa` — test-driven-development, `design` — frontend-ui-engineering, `design-review` — design-review, `reviewer` — code-review-and-quality, `docs` — documentation-and-adrs. Остальные использовать по фазам работы. Верхнеуровневый процесс — этот файл и `agent_docs/` (ADR, dev-history, snapshot, инварианты, роли); при конфликте инструкций skill с правилами проекта приоритет за правилами проекта.
- Набор vendored: файлы под `.agents/` не редактировать; они исключены из markdownlint. Обновление — `npx skills update` плюс ручное копирование общих чек-листов и допфайлов скиллов, которые установщик не переносит (процедура — в ADR `2026-09-07-2350`).
- **Обязательная проверка перед установкой или обновлением любого стороннего skill**: сканирование SkillSpector + семантическое ревью по скиллу `skill-inspector`; `REJECT` или необъяснённая HIGH/CRITICAL-находка — не устанавливать. Процедура, вердикты и работа с находками — ADR `2026-09-08-0205`; установка CLI — `agent_docs/guides/environment-setup.md`.
- Для любого стороннего скилла при конфликте его инструкций с правилами проекта приоритет за правилами проекта (например, временные отчёты — в `temp/`, а не в `/tmp`, как велит `skill-inspector`).

## При начале работы

- Свериться с разделом «Описание проекта» выше — это основной контекст.
- Прочитать `agent_docs/snapshot.md` — текущее состояние работы. Это первый файл, а не история.
- Прочитать `agent_docs/invariants.md` — жёсткие ограничения, которые нельзя нарушать.
- Открыть `agent_docs/development-history/README.md` и самостоятельно определить релевантную глубину просмотра записей по риску задачи, затронутым файлам и необходимости восстановить контекст.
- По карте `agent_docs/index.md` открыть только релевантные файлы.
- При проектной терминологии — свериться с `agent_docs/glossary.md`.

## Универсальные правила

- Следовать существующим паттернам и соглашениям проекта.
- Не использовать AGENTS.md как стайлгайд или справочник команд; для стиля — линтеры, форматтеры и существующие артефакты.
- Документы держать краткими; вместо копирования больших фрагментов — ссылаться на файлы и разделы.
- Обновлять затронутую документацию.
- **Приложения сданных дней (`days/dayN/`) не дорабатываются и не поддерживаются** без явного указания владельца (решение от 2026-09-08). Новые стандарты применяются к новым дням, ретроспективно старые не приводятся. Если появилась предпосылка тронуть прошлый день — спросить владельца, а не делать молча.
- Секреты не коммитить никогда. Ключ API живёт только в `.env` на сервере и в GitHub Secrets.

## Коммиты и ветки

Базовый шаблон правил этого не задаёт — правило добавлено здесь, потому что проект пишет код, а не только документацию.

- Ветки: `feat/<slug>`, `fix/<slug>`, `docs/<slug>`, `chore/<slug>`.
- Коммиты — Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`.
- В `main` только через PR. Прямой push в `main` запрещён.
- Если изменение опирается на ADR — сослаться на файл ADR в описании PR.
- Одна задача — один PR. Не смешивать рефакторинг с функциональностью.

## Чек-лист перед завершением задачи

- Требования выполнены, результат соответствует ожидаемому поведению.
- Каждое изменение прослеживается к исходному запросу (нет «попутных улучшений»).
- `agent_docs/snapshot.md` обновлён; закрытые пункты перенесены из `backlog.md` в `backlog-closed.md`.
- Документация обновлена; для нетривиальных изменений — отдельная запись в `agent_docs/development-history/YYYY-MM-DD-HHMM-title.md`.
- Если принято важное решение — добавлена отдельная запись в `agent_docs/adr/YYYY-MM-DD-HHMM-title.md` (шаблон: `agent_docs/templates/adr.md`).
- Сверено с `agent_docs/guides/dod.md`, критерии DoD выполнены или зафиксированы причины отклонений.
- Ни один инвариант из `agent_docs/invariants.md` не нарушен.
- Если менялся UI: ревью `/design-review` пройдено, вердикт `ГОТОВО`, отклонения от корпуса объяснены.
- Если тесты применимы и не запускались/не добавлены — указано почему.

## Признаки того, что правила работают

- Меньше лишних правок в diff'ах и материалах.
- Меньше переделок из-за переусложнения.
- Уточняющие вопросы — до начала, а не после ошибок.
