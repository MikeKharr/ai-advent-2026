# Сервис агентов

Отдельный сервис без публичного адреса: реестр агентов, их инструменты и
запуски с потоком событий для монитора. Первый агент — `news-analyst`,
аналитик новостей стартапов; первый инструмент — архив статей (перенесён
из дня 5). Решение и контракт — `agent_docs/adr/2026-09-09-0854-agent-service.md`,
эксплуатация — `agent_docs/operations.md`.

Ключей к моделям у сервиса нет: он ходит в роутер по ключу приложения
`agents`. День 6 ходит сюда по ключу `AGENT_KEY` и денег не тратит.

## Локальный запуск

```sh
AGENT_KEY=<ключ сервиса> \
ROUTER_APP_KEY=<ключ приложения agents у роутера> \
ROUTER_URL=http://127.0.0.1:8081 \
STORE_FILE=./data/store.json \
node server.js
```

Тесты: `node --test test/*.test.js` (57), включая контракт сервиса через
настоящий HTTP и полный запуск агента на заглушках архива и роутера.

## Контракт

| Метод и путь | Что |
|---|---|
| `POST /v1/runs` | `{ agent, input }` → `202 { runId }`; запуск асинхронный. В `input` необязательное поле `system` — свой промпт вместо реестрового (ADR `2026-09-09-1623`) |
| `GET /v1/runs/:id/events` | SSE: накопленные события, затем живые; последним — `end` со статусом и результатом или ошибкой |
| `GET /v1/runs/:id` | снимок: статус, события, результат |
| `GET /v1/agents` | реестр: имя, версия, назначение, класс задачи, инструменты, умолчания, потолки параметров `limits`; у всех, кроме агентов MCP, — ещё системный промпт, модели с живым пределом, готовые запросы и этапы `stages` (идентификатор, название, правило, промпт этапа с `sha8`); у агентов MCP — список серверов |
| `GET /v1/agents/:id/tools/archive` | состояние архива |
| `GET /v1/profiles` | все живые профили дня 11 по убыванию активности и потолок `cap` |
| `POST /v1/profiles` | `{ name }` → профиль; 400 на имени вне 1–40 знаков, 409 `profiles_full` при пяти живых |
| `GET /v1/profiles/:id` | профиль: настройки, правила, темы, живые диалоги и `lastSession`; чтение срок памяти **не** продлевает |
| `DELETE /v1/profiles/:id` | профиль со всей связанной памятью — одной транзакцией по девяти таблицам |
| `PUT /v1/profiles/:id/settings` | настройки агента за профилем; проверка теми же разборщиками, что вход запуска |
| `GET /v1/profiles/:id/sessions` | живые диалоги профиля и потолок `cap` |
| `POST /v1/profiles/:id/sessions` | `{ topicId? }` → новый диалог; 409 `sessions_full` при двадцати живых |
| `GET /healthz` | жив ли процесс; без ключа |

Всё под `/v1/` требует `Authorization: Bearer <AGENT_KEY>`. Готовый запуск
живёт в памяти `RUN_TTL_MINUTES` и удаляется; долгого хранения нет.

Сводка диалога (день 9, ADR `2026-09-11-1608`): необязательное поле
`input.summarizeAt` — порог N, целое 500–8000 и не больше `contextTokens`.
Когда реплики после последней сводки набирают N токенов, агент до ответа
сжимает прежнюю сводку и эти реплики в новую — всегда Haiku 4.5 классом
`summarize`, потолок ответа `⌈0,3 × N⌉` — и отдаёт модели `<summary>`, затем
`<dialog>` с репликами после неё. Отказ сводки запуск не валит: ответ идёт по
хвосту с предупреждением. `GET /v1/sessions/:id` отдаёт `summary { text,
tokens, sourceTokens, updatedAt, throughId, model, truncated }` или `null` и
`context { total, summaryTokens, freshTokens }` — что уйдёт модели со
следующим сообщением, без учёта окна модели; `DELETE` и уборка по сроку
сводку удаляют, а сводка, полученная после очистки, не записывается.
Исходник сводки ограничен `N + MAX_OUTPUT_TOKENS + 1000` токенами: старшие
реплики сверх потолка отбрасываются с предупреждением. В `totalTokens` сессии и запуска входят вызовы сводки; в
сводке ответа `totalTokens` — только сам ответ, цена сводки — в
`summarized.totalTokens`. Без поля поведение прежнее.

`GET /v1/agents` отдаёт промпт из реестра, а не последнюю правку:
окно передачи показывает агента, а не чужой запуск. Свой промпт действует
только на тот запуск, с которым пришёл; в событиях от него — факт подмены и
длина, без текста.

Агенты MCP (`mcp-agent`, `pipeline-agent`) системного промпта в описании **не отдают**: страницы дней 18–20 его не показывают и не правят, а ручка открыта всем дням — поверхность не расширяется (PR #269). Промпт при этом лежит в `config/agents.json` публичного репозитория, так что нераскрытие — сужение поверхности, а не защита.

## Модули

```text
config/agents.json     реестр: id, имя, версия, назначение, системный промпт,
                       инструменты, класс задачи роутера, умолчания параметров;
                       у агента без модели (день 19) промпта, класса задачи и
                       параметров модели нет и быть не должно; у агента с
                       инструментом mcp обязателен список servers — имена

                       sha256 сохранённого и прочитанного

                       планировщик дня 18 платит ROUTER_APP_KEY_SCHEDULER;

src/jobs/index.js      работы планировщика дня 18: проверка jobs.json, решение

src/jobs/store.js      запуски, часовые слоты и суточный счётчик стартов в

                       ленты сводок их не касается
```

## Переменные окружения

| Имя | Умолчание | Смысл |
|---|---|---|
| `AGENT_KEY` | — | ключ сервиса, обязателен; его предъявляет день |
| `ROUTER_APP_KEY` | — | ключ приложения `agents` у роутера, обязателен |
| `ROUTER_URL` | `http://router:8081` | адрес роутера |
| `STORE_FILE` | `/data/store.json` | файл архива на томе |
| `WINDOW_SIZE` | 1000 | сколько статей держим |
| `REFRESH_MIN_MINUTES` | 15 | не чаще этого опрашиваем ленты |
| `MAX_AGE_DAYS` | 180 | дольше этого статьи в архиве не хранятся |
| `MAX_OUTPUT_TOKENS` | 2048 | потолок пользовательского max_tokens |
| `ROUTER_TIMEOUT_MS` | 240000 | ожидание ответа роутера |
| `RUN_TTL_MINUTES` | 10 | сколько готовый запуск живёт в памяти |
| `PROFILE_TTL_DAYS` | 30 | профиль без действий живёт столько дней |
| `PROFILE_CAP` | 5 | живых профилей не больше |
| `PROFILE_SESSION_CAP` | 20 | живых диалогов на профиль не больше |
| `MCP_NEWS_URL` | — | адрес сервера MCP новостей; без него сервер выпадает из реестра |
| `MCP_STORE_URL` | — | адрес сервера MCP файлов; без него сервер выпадает из реестра |
| `MCP_DAY16_URL` | — | адрес службы MCP дня 16 третьим сервером; без него сервер выпадает из реестра |
| `MCP_KEY` | — | ключ службы дня 16; уходит только ей (копия значения из `mcp.env`) |
| `JOBS_FILE` | `/data/jobs.db` | запуски планировщика дня 18 на томе |
| `ROUTER_APP_KEY_SCHEDULER` | — | ключ приложения `scheduler`; без него планировщик выключен |
| `PORT` | 8082 | порт |

## Добавить агента

Запись в `config/agents.json` по образцу `news-analyst` и исполнитель по
образцу `src/agent.js`; в `server.js` — сопоставление записи исполнителю.
Агенту с инструментом `mcp` нужен ещё список `servers`: новый сервер в
`config/mcp-servers.json` сам собой никому не достаётся — его вписывают тем
агентам, которым он положен.
Новый инструмент — каталог в `src/tools/` с `name`, `describe()`, `run()`.
