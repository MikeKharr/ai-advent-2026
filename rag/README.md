## Две стратегии

| | фиксированная | структурная |
|---|---|---|
| граница | окно 1500 знаков, перекрытие 200, ближайший назад конец абзаца или строки; конца абзаца нет в пределах `WINDOW // 3` — окно закрывается по краю | markdown — заголовок; раздел длиннее `SECTION_LIMIT` = 3000 знаков режется по абзацам с той же цепочкой; код — файл целиком, если короче 3000, иначе по пустым строкам верхнего уровня |
| `section` | пусто | цепочка заголовков `A › B › C`, для кода — имя файла |
| что уходит в эмбеддинг | сам текст окна | `заголовок документа › цепочка` + текст |

Заголовки в фиксированной стратегии не учитываются намеренно — ни при
выборе границы, ни в метаданных, ни в тексте для эмбеддинга. Пустой
`section` здесь не пробел, а всё, что эта стратегия о документе знает:
именно на этой разнице и меряется сравнение.

Метаданные одинаковые у обеих: `source`, `title`, `section`, `chunk_id`,
`strategy`, `sha256`, `commit`.

### Дорезка: чего структурная стратегия не обещает

Ни разбиение по абзацам, ни разбиение по пустым строкам верхнего уровня
потолка не дают: сплющенный JSON — один блок на 70 КБ (замер до правки:
`макс: 69820`). Такой чанк ушёл бы в эмбеддер целиком, а тот обрезал бы
его по своему контексту молча — и мера сравнивала бы обрезку, а не
нарезку. Поэтому есть последний рубеж `_hard_split`: кусок длиннее 3000
дорезается по строкам. После него `макс: 3000` у обеих ветвей.

**Цена названа, а не вычтена:** дорезка режет по строкам, не глядя ни на
ограды кода, ни на списки, и потому сама даёт часть срабатываний
показателя «режет блок пополам».

Признак атрибуции назван, чтобы число не было на вкус: рез отнесён к
дорезке тогда и только тогда, когда граница **внутренняя для одного вызова
`_hard_split`**, то есть когда правый чанк — его продолжение (`continues`,
тот же признак, которым считается и сам показатель).

Два счёта попроще отвечают на другой вопрос. Если считать рез дорезным по
**левому** соседу, добавляются 4 границы **после последней** части — они
принадлежат уже разделу, а не дорезке (25 → 29); если по **любому** из
соседей, добавляется ещё 1 граница **перед первой** частью (29 → 30).

Здесь «сосед из дорезки» значит «чанк — любая часть многочастного вызова,
включая нулевую». При другом, столь же естественном прочтении — «только
продолжение, без нулевой части» — те же три счёта дают 25 / 20 / 29:
счёт по левому соседу тогда не завышает, а **теряет** внутренние границы
между частью 0 и частью 1. Оба прочтения внутренне непротиворечивы, и
именно поэтому признак здесь назван, а не подразумевается: без него число
меняется от прочтения, а не от кода.

Замер на ветке: у структурной 39 срабатываний, из них **25 — граница
дорезки**, 14 — сама структурная нарезка; продолжений дорезки 219 чанков из
2991. Числа слегка плывут от правки к правке: этот README сам лежит в
корпусе, то есть документ о замере меняет замер. Порядок и вывод от этого
не зависят.

### Как считается «режет блок пополам»

Ограда: нечётное число ``` в чанке. Список: чанк оборвался на пункте, а
следующий чанк того же файла начинается с пункта **и продолжает его**
(`Chunk.continues`). Признак `continues` обязателен: `_markdown_sections`
выбрасывает строку заголовка, и без него два **целых** списка в соседних
разделах читались бы как один разорванный. Фиксированная стратегия от
этого защищена построением — она заголовок не вырезает, — то есть ошибка
била ровно по одной из двух сравниваемых сторон и переворачивала знак
вывода (находка `reviewer` к PR #278). В метаданные `continues` не идёт:
набор полей задан ADR, а это внутреннее свойство нарезки.

## Индекс и инкремент

`IndexFlatIP` — полный перебор из C++. ANN (IVF, HNSW) на 3,5 тысячах
векторов требует обучения и теряет полноту ради скорости, которой некуда
деваться (ADR `2026-09-29-1639`, п. 2). Векторы нормируются, поэтому
скалярное произведение и есть косинус.

В томе на стратегию — пара `<стратегия>.faiss` и `<стратегия>.meta.json`.
`sha256` чанка считается от пары «стратегия + текст для эмбеддинга»:
при старте эмбеддятся только те чанки, которых в томе нет. Разъехавшуюся
пару файлов (`ntotal` не равен числу записей) читаем как «индекса нет» и
строим заново, а не ищем по ней молча.

В `meta.json` лежит и **имя модели**, которой собран индекс. Индекс чужой
модели читается как отсутствующий — всеми тремя местами загрузки: сборкой,
поиском и мерой. Векторы разных моделей одной размерности (768 у
`embeddinggemma` и её квантованных вариантов), поэтому смесь не даёт ни
ошибки, ни признака: индекс молча становится смесью двух пространств.
Аргумент модели у `VectorIndex.load` обязателен — умолчание пропускало
любой индекс.

## Мера сравнения

`eval/queries.json` — 100 вопросов, какие агент задаёт проекту на деле; у
каждого ожидаемые документы, у части — фраза, которая обязана быть в
найденном тексте. `metrics.py` считает Recall@5 и MRR@10 по документам,
долю запросов с фразой в первом чанке; `build.py` — число чанков, медиану
длины, долю чанков, режущих блок кода или список пополам, время сборки и
число вызовов эмбеддинга.

Граница меры названа заранее: вопросы пишут люди и роли этого проекта —
q01–q30 один человек, q31–q100 два экземпляра роли `qa` (решение владельца
2026-10-02, поправка к ADR `2026-09-29-1352`, п. 4), — и они отражают
привычки проекта, а не всех будущих клиентов;
документный recall не видит, обрезан ли ответ внутри чанка, — для этого и
введён третий показатель.

Что пути и фразы `queries.json` существуют в корпусе — держит
`test/test_eval.py`, а не внимательность автора.

## Локальный прогон

```
python -m unittest discover -s test -t .          # из каталога rag/
python corpus.py --root .. --out corpus           # копия корпуса
python build.py --corpus corpus --index index     # нужна Ollama
python eval/run.py --index index                  # нужна Ollama
```

Тесты Ollama не требуют: клиент проверяется на поднятом `http.server`,
который отвечает как `/api/tags`, `/api/pull` и `/api/embed`, и утверждения
идут о **журнале стенда** (`FakeOllama.requests` — путь и разобранное тело),
а не о коде ответа.

### Что проверено живым прогоном в заходе 3

Связка на машине разработчика: `ollama serve` 0.33.3, модель
`embeddinggemma:300m-qat-q4_0` (238 МБ, квантизация с учётом обучения,
307,58 M параметров). Замеры ниже сделаны на BF16
(`embeddinggemma:latest`, 621 875 917 байт) — модель сменена ADR
`2026-09-30-0957` уже после них, и повторять их на новой модели никто не
повторял.

1. **Контракт живой Ollama — подтверждён.** `/api/pull` без стрима
   отвечает `{"status":"success"}`; `/api/tags` даёт `models[].name` со
   значением `embeddinggemma:latest` — **имя всегда с тегом**, поэтому
   `has_model()` сверяет имя целиком, а не до двоеточия; `/api/embed`
   принимает `{"model","input":[…]}` и отвечает
   `{"embeddings":[[…]]}`.
2. **Контекст модели против длины чанка — чанки влезают, `SECTION_LIMIT`
   менять не надо.** Это был главный риск захода, и мерился он так: к
   тексту длины L дописывался маркер в хвост, и сравнивались векторы `v(L)`
   и `v(L + маркер)`. Совпадение до последнего знака значит, что хвост до
   модели не дошёл.
   - Порог обрезки — свойство **токенизатора**, и в знаках он зависит от
     текста. На текстах этого корпуса дихотомия до шага 25 знаков дала
     **6179 / 6200** знаков русского markdown и **6368 / 6385** знаков
     кода; `reviewer` на своём тексте получил **6831 / 6851**. Общее у всех
     трёх — 2048 токенов это порядка 3 знаков на токен, а не полтора, как
     можно было опасаться. Числом, на которое опирается вывод, надо брать
     наименьшее из наблюдённых, то есть 6179.
   - Самый длинный чанк корпуса — **3465 знаков** (структурная стратегия,
     `agent_docs/adr/2026-09-29-1350-day20-profiles-from-day15.md`); у
     фиксированной максимум ровно 1500. Запас до обрезки — **1,78×** по
     самому неблагоприятному из наблюдённых порогов (6179 / 3465); по
     порогу `reviewer` вышло бы 1,97×. Не «вдвое», а «почти вдвое».
   - Проверка **различает гипотезы**: маркер в НАЧАЛЕ при 12 000 и 30 000
     знаков даёт одно и то же ненулевое расхождение (0,138420), маркер в
     КОНЦЕ при тех же длинах — ровно ноль. Значит режется хвост, а голова
     сохраняется, и «векторы просто всегда разные» отпадает.
   - Контрольный прогон на худшем чанке с `truncate: false`: **200, влез
     целиком**; тот же запрос на 30 000 знаках — `400 the input length
     exceeds the context length`. То есть тихая обрезка существует, и
     именно её здесь не происходит.
   - Числа замера нарезки (заход 2: 2991 чанк, 39 резов) **пересчитывать
     не требуется**: они мерили нарезку, а обрезки нет.
3. **`embeddinggemma` тянется, размер вектора — 768.** Веса 622 МБ,
   контекст модели 2048 (и `OLLAMA_CONTEXT_LENGTH` его не двигает: у
   эмбеддера он прибит обучением). Код размерность не закладывает — берёт
   из первого ответа, и взял 768.
4. **Полный проход сборки на живой Ollama прошёл целиком**: 3009 чанков
   фиксированной стратегии за 163 с (189 вызовов) и 2991 структурной за
   114 с (187 вызовов), суммарно 278 с; том индекса — 31 МБ (`*.faiss` по
   9,2 МБ, метаданные 7,2 и 6,8 МБ). Пик памяти самого процесса `rag` —
   152 698 880 байт, то есть **146 МиБ**: потолок 512 МиБ взят втрое с
   запасом. Числа чанков — на состоянии корпуса в момент прогона; на
   голове ветки их **порядка 3050 и 3020** при 347 файлах, потому что этот
   PR добавил в корпус собственные файлы. **Точнее здесь сказать нельзя в
   принципе:** этот README сам входит в корпус, поэтому вписанное в него
   число чанков меняет число чанков. Два прогона на одном и том же head
   дали 3048/3020 и 3051/3024 — разошлись ровно на правку этого абзаца.
   Вывод от этого не меняется, а самый длинный чанк воспроизводится точно
   — те же 3465 знаков при 347 файлах в обоих прогонах.
5. **Память Ollama под этой моделью** (macOS, Metal; на linux/amd64 не
   мерено): **776 МиБ** сразу после загрузки на коротком входе,
   **1878–1884 МиБ** на чанках полной длины. Единица — мебибайты: `ps`
   отдаёт KiB, и потолок `mem_limit` тоже в мебибайтах, так что числа
   сравнимы напрямую. Расход не двигают ни размер батча (проверено
   1, 2, 4, 8, 16 — RSS 1878…1884 МиБ), ни `OLLAMA_NUM_PARALLEL` (1 против
   4 — 1870 против 1869 МиБ), ни `OLLAMA_CONTEXT_LENGTH`. Это про длину
   входа, а не про число входов.

### Что остаётся непроверенным после заходов 3 и 4 — список полный

1. **Расход памяти Ollama на linux/amd64.** Замер выше сделан на macOS с
   Metal, и перенести его на CPU-only линукс нечем: докера на машине
   замера нет, и направление неизвестности назвал `compliance`: Metal
   держит буферы в единой памяти, а CPU-only x86 учитывает их в обычном
   RSS, поэтому на linux/amd64 расход скорее **выше**, чем ниже.
   **Предупреждение сбылось 2026-10-02**, и это уже не непроверенное, а
   установленное: на прежнем потолке 2048 МиБ раннер llama.cpp убит
   cgroup-OOM на худшем чанке `structural` (1843 токена, журнал `ollama` —
   `signal: killed`), тогда как на Metal тот же класс входа брал ~1150 МиБ.
   Потолок поднят до `4g` (ADR `2026-10-02-1519`); число выведено, а не
   замерено, и непроверенным остаётся теперь оно. Если на
   сервере расход окажется больше, cgroup убьёт `ollama` (а не день —
   `oom_score_adj: 500`), и `restart: unless-stopped` поднимет **саму
   `ollama`**. **Сборку индекса это не возобновит**, и прежняя редакция
   этого пункта обещала обратное (находка `compliance`, Б1-бис): `run_build`
   ловит отказ один раз, пишет `state=failed` и заканчивает поток, процесс
   `rag` при этом жив, поэтому его собственный `restart` не срабатывает, а
   `/healthz` продолжает отдавать 200. Возобновление сегодня — только
   ручной рестарт контейнера `rag`; уже собранное переживает его с
   гранулярностью **стратегии**, а не чанка, и на первой сборке том пуст.
   Само отсутствие повтора заведено владельцу в `agent_docs/backlog.md`.
   **Расход памяти — первое, что надо посмотреть после первой выкатки.**
2. **Помещается ли всё это в свободную память — после апгрейда расчётно.**
   2026-10-02 VPS расширен до 8 ГБ, потолки теперь `ollama` 4096 + `rag` 512
   = 4608 МиБ (ADR `2026-10-02-1519`) против расчётных ~6500 свободных.
   **Расчётных, а не замеренных**: база «остальное брало ~1380 МиБ» снята на
   прежнем экземпляре хоста, который провайдер при апгрейде пересоздал, а
   `free -m` на новом не снимался — владелец решил взять 8 ГБ как данность.
   Разрешается одной командой на хосте, за владельцем. Есть ли на VPS swap —
   по-прежнему не проверялось. (Прежняя редакция этого пункта — про 2539
   свободных и сумму потолков 2560 — закрыта вместе с пунктом бэклога.)
3. **Время первой сборки на VPS.** Локальные 278 с — не перенос: там GPU
   Metal, здесь одно ядро x86 под `cpus: 1.0`. Оценка ADR (часы) остаётся
   арифметикой, и потолок `RAG_BUILD_TIMEOUT_SECONDS=43200` (12 часов)
   выбран как граница, а не как замер. Первый прогон его и проверит.
4. **Качество поиска и числа меры.** `Recall@5`, `MRR@10` и «фраза в
   первом чанке» на живых векторах **не считались**: локальный прогон
   строил индекс, но не мерил выдачу. Это заход 5.
5. **Цена первой выкатки по сети.** Образ `ollama/ollama` — 3,75 ГБ
   сжатого (сверено в реестре Docker Hub по digest 0.35.0), плюс 622 МБ
   весов модели с `ollama.com`. Сколько это займёт на канале VPS — не
   мерено, **а у шага выкатки `timeout-minutes: 10`**. Если первая выкатка
   упрётся в это время на `docker compose up -d`, повтор прогона доберёт
   образ со слоёв, уже лежащих на машине; менять общий потолок шага ради
   одного разового случая этот заход не стал.
6. **Поведение `/api/pull` при старте в проде.** Локально модель тянулась
   отдельной командой; в проде её тянет сама единица при старте, если
   `/api/tags` её не показал. Ветка проверена на стенде и на живой Ollama
   порознь, но не в связке «пустой том → первый старт контейнера».
   Неготовность эмбеддера при этом учтена **одним** механизмом: единица
   ждёт его до `RAG_OLLAMA_WAIT_SECONDS`. `healthcheck` у службы `ollama`
   защитой **не является** и здесь таковой не называется — его никто
   автоматически не читает (`condition: service_healthy` сознательно не
   подключён: он краснил бы выкатку всех единиц из-за одной службы). Окно,
   которое закрывает ожидание, — не разворачивание образа, а разрыв между
   стартом контейнера и тем, как `ollama` забиндит слушателя: `up -d`
   возвращается по старту, а не по готовности. Хватает ли на это 600 с —
   оценка, не замер.
7. **Что потеряет проход, прерванный по сроку.** Векторы незавершённой
   стратегии в том не попадают: сохраняет их только `VectorIndex.save` в

8. **Служба `ollama` работает от root внутри контейнера.** В конфигурации

   контейнера времени. Переселить процесс можно своим образом или `user:` с
   переносом `OLLAMA_MODELS`; ни то ни другое здесь не проверялось.
9. **Суточный потолок 500 не измерен** — см. «Поверхность MCP». Первые
   сутки работы его и проверят.
10. **Время ответа `project.search`** — ни на свободной машине, ни во время
   сборки не мерено. Отсюда и `RAG_QUERY_TIMEOUT_SECONDS=60`: число заведомо
   больше одного вызова и больше одного батча из шестнадцати чанков, но не
   замер.
11. **Память с загруженным индексом.** Метаданные обеих стратегий (7,2 и
   6,8 МБ JSON) живут загруженными рядом с пиком сборки в 146 МиБ. Потолок
   512 МиБ взят с запасом втрое от прежнего замера, но замера С ЗАГРУЖЕННЫМ
   индексом нет.
12. **Мёртвый `rag` не заметит выкатка, которая его не задевает.** Ожидание
   `healthy` в `deploy.yml:269` идёт только по единицам, изменённым этой
   выкаткой, а регулярка `rag` в `deploy-units.sh:65` включает `rag/`,
   `deploy/`, `.github/`, `agent_docs/`, `test/` и README трёх единиц. Значит
   выкатка, трогающая **только** `days/dayN/` или `site/`, пройдёт зелёной

   остался без `RAG_KEY`. Окно узкое: регулярка ловит почти всё дерево. Это
   остаточная правда возражения `compliance` против `required: false`
   (PR #282); сколько таких выкаток бывает на деле — не мерено.
13. **Ничто из захода 4 не проверено в проде.** Значения `RAG_KEY` на

   единица в проде не поднимается, и живой ответ `/rag` не наблюдался ни

   шагом «Проверка Caddyfile». Оба на PR #282.

   мутация `header.removeprefix("Bearer ")` оставляет весь прогон зелёным:

   нужен. Записано, потому что «прогон зелёный» здесь значит «не проверяется»,

## Как это работает в проде

Две службы в `deploy/compose.yml` и своя сеть `rag`: в ней только `caddy`,
`rag` и `ollama`. Ни дни, ни `router`, ни `agents`, ни серверы инструментов
в неё не входят — имя `ollama` у них не разрешается. До захода 4 это и есть
весь ответ на «кто может занять общее ядро эмбеддингом»: никто, кроме самой
единицы `rag`.

Потолки стоят у обеих новых служб и только у них: `ollama` — `mem_limit: 4g`
(ADR `2026-10-02-1519`, было `2g`),
`cpus: 1.0`, `oom_score_adj: 500`; `rag` — `512m`, `0.5`, `500`. `cpus: 1.0`
не про скорость, а про обещание соседям: сборка не займёт оба ядра машины.
`oom_score_adj` — про то, кого ядро выберет жертвой при тесноте: нового
жильца, а не день. Значения сверяет шаг «Потолки памяти и ядер у ollama и
rag» в `ci.yml`, причём точным сравнением: `mem_limit: 8g` — тоже потолок,
только на машине с 3,9 ГБ он ничего не значит.

Наружу открыты два адреса. `https://challenge.zpq.ai/rag/healthz` — без
ключа: его дёргает шаг «Проверка живого сайта» в `deploy.yml`. Ответ 200
значит «единица поднялась», а не «индекс готов»: состояние сборки лежит в
теле, и первая полная сборка идёт уже после зелёной выкатки. Рядом со
`state` там стоит `index` — то, что загружено в память и по чему идёт поиск
прямо сейчас; это РАЗНЫЕ вещи (см. «Поверхность MCP» ниже).

`https://challenge.zpq.ai/rag` — поверхность MCP, за ключом `RAG_KEY`.
Остаток суточного потолка на открытую ручку не идёт: прохожему он говорил бы,
пользуется ли службой кто-то прямо сейчас.

## Поверхность MCP

`POST /rag`, JSON-RPC 2.0, ревизия MCP `2025-11-25`, без сессий. Порядок
обработчика читается сверху вниз (`rag/serve.py`, `_dispatch`): путь вне
таблицы → ключ до чтения тела → метод → тело с потолком 64 КБ → окна
лимитера → RPC. Отказ по ключу и неизвестный путь дают **побайтно
одинаковый пустой 404** — решение владельца по `/mcp` (ADR
`2026-09-23-1844`, пп. 1–2).

**Один ответ на соединение.** Любой путь, способный отправить ответ,
обязан либо вычитать тело запроса, либо закрыть соединение — включая общий
`except`. «Тело есть» определяется по RFC 9112 §6: присутствует
`Transfer-Encoding` **либо** `Content-Length` > 0; несколько заголовков
`Content-Length` или нечисловое значение тоже считаются телом. Держит один
страж в `finally` у `_dispatch` (`rag/serve.py`) и перебор
`serve.ROUTES` × методы × состояния ключа × **обрамление тела** в
`test_serve.py::OneResponsePerConnectionTest`. Иначе невычитанное тело
разбирается как СЛЕДУЮЩИЙ запрос: отправитель получает второй ответ, а
рассинхронизированное соединение уходит обратно в пул `caddy → rag:8086`.

Экземпляров этого класса за ревью PR #282 нашлось шесть, и найдены они
шестью разными способами. Ось обрамления в переборе появилась последней и
не случайно: две первые оси перебирались, а обрамление было **константой**
(`content-length`) — ровно тем, на что была завязана реализация. Перебор
шёл по осям, где защита одинакова, и держал неподвижной ту, где она
различалась.

Два инструмента:

- `project.search {query, limit ≤ 10 (5), strategy}` → `{index: {commit,
  strategy, chunks}, results: [{source, title, section, score, text,
  truncated}]}`. Выдержка чанка режется до 2000 знаков, весь ответ — до
  32 КБ; урезанное называется полями `truncated` и `dropped`.
- `project.status {}` → состояние сборки, что загружено в память, остаток
  суточного потолка.

**Умолчание стратегии — структурная, и это выбор без числа.** Мера
стратегий — заход 5, на живых векторах её ещё не считали. Довод умолчания
слабый и назван слабым: структурная несёт цепочку заголовков в `section`,
то есть её результат читается без открытия файла. Аргумент `strategy`
существует ровно потому, что числа нет.

**Индекс отстаёт от рабочего дерева.** Он собран из корпуса, попавшего в
образ на последней выкатке `main`. Агент на ветке спросит про свою ветку, а
получит ответ про `main` — и по виду ответа это не отличить. Смягчение одно
и слабое: `index.commit` едет в каждый ответ поиска и в `project.status`,
то есть неверный ответ **можно** отличить от верного, если смотреть.

**Сборка не удалась — поиск может работать.** `state` описывает СБОРКУ,
`index` — то, что загружено. Если сборка отказала, а в томе лежит целая
пара файлов с прошлой выкатки, служба ищет по ней и называет её `commit`,
отличный от `commit` сборки. Это **не починка** дефекта «сборка не
возобновляется после единственного отказа» (он в `agent_docs/backlog.md`,
решение за владельцем), а то, что делает его последствие переживаемым. Ни
готового индекса, ни целой пары в томе — отказ инструмента с честным
текстом и **без вызова эмбеддера**.

**Суточный потолок `RAG_DAILY_EMBEDS` = 500 — ЧИСЛО НЕ ИЗМЕРЕНО.** Сколько
стоит один эмбеддинг запроса на одном ядре VPS — не мерено ни разу; 500
взято как начальное, а не посчитано, и выдавать его за обоснованное нельзя.
Чем его поправить после первых суток работы:

- смотреть `daily.used` в `project.status` на конец суток UTC. Упёрлись в
  потолок, а машина не страдала — число мало, поднимать;
- смотреть время ответа `project.search`, пока идёт сборка: поиск и сборка
  делят один слот Ollama (`OLLAMA_NUM_PARALLEL=1`), и запрос ждёт батч из
  шестнадцати чанков. Машина страдала задолго до потолка — число велико, и
  тогда его правит не потолок, а мера времени ответа;
- цена промаха в меньшую сторону: поиск останавливается до полуночи UTC.
  Это видно в отказе инструмента, а не молча.

Счёт живёт в `/data/usage.json` — в томе, а не в памяти: контейнер `rag`
перезапускается на каждом мерже документа, и счётчик в памяти обнулялся бы
ровно в те дни, когда вокруг больше всего работы. В файле дата и число, без
адреса (I-10). Нечитаемый файл читается как ноль и переписывается заново —
осознанный fail-open: этот потолок стережёт ядро общей машины, а не деньги,
и остановить поиск из-за битого JSON дороже, чем пропустить один день учёта.
О потере учёта в журнал уходит строка `usage_unreadable`.

## Клиент: `.mcp.json` в корне репозитория

```json
{"mcpServers": {"project": {"type": "http",
  "url": "https://challenge.zpq.ai/rag",
  "headers": {"Authorization": "Bearer ${RAG_KEY}"}}}}
```

Ключа в файле нет и быть не может (I-2): `${RAG_KEY}` подставляется из
окружения процесса в момент подключения. **Подстановка проверена
исполнением** 2026-09-30, а не взята из документации — в прочитанной
документации её не было вовсе. Прогон различал гипотезы: с заданной
переменной пробный сервер увидел значение, без неё — дословную строку
`Bearer ${…}`.

**Ключ кладётся в ДВА места одним действием.** На сервер —
`bash deploy/put-rag-key.sh`; в окружение ноутбука — то же значение туда,
откуда его видит Claude Code (профиль оболочки или менеджер секретов). Это
условие `compliance` к PR #282, и оно не про удобство: без переменной каждая
сессия из этого каталога шлёт на публичную ручку негодный ключ, а
`refusal_burst` срабатывает на 20 отказах с адреса за час — единственный
сигнал «перебирают» стал бы приходить от своего же ноутбука и перестал бы
что-либо значить.

Отсюда два следствия, о которых лучше знать заранее:

- **Сессия без `RAG_KEY` в окружении** пошлёт строку шаблона как ключ и
  получит пустой 404. В списке серверов это выглядит как неподключённый
  сервер — шум в каждом запуске из этого каталога, а в журнале службы —
  ложный сигнал о переборе (пункт «Владельцу» в `agent_docs/backlog.md`).
- **Сервер из `.mcp.json` требует одобрения** при первом запуске в этом
  каталоге; до одобрения к службе не уходит ни одного запроса (в том прогоне
  соединения не было; как общее правило поставщика не подтверждено).

Свежесть индекса держит выкатка, а не память человека: правка документа или
кода живой единицы поднимает `rag` в затронутых единицах — регуляркой
`rag='…'`, которая живёт в `ci.yml` (решает, пересобирать ли образ) и в
`.github/scripts/deploy-units.sh` (решает, выкатывать ли). Что эти две копии
совпадают, держит `test/test_corpus.py::CiRegexTest`; что вторая копия вообще
что-то поднимает — `test/deploy-units.test.js` в корне.
