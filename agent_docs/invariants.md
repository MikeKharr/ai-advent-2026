# Инварианты продукта

Жёсткие ограничения. Нарушение инварианта — баг, а не компромисс. Изменение инварианта требует ADR.

У каждого инварианта строка «держит:» — тест или шаг CI, которые краснеют при нарушении, роль, которая ловит его чтением диффа, либо честное «ничто» (ADR `2026-09-24-1230`, B3). Держатель — то, что названо в этой строке; сверено с репозиторием 2026-09-24 по именам тестов, шагов и ролей. **«Держит: роль» — не выполнение I-14:** роль ловит нарушение чтением диффа, то есть внимательностью, и при снятии держащей строки прогон остаётся зелёным. Такая строка называет, кто смотрит, а не что краснеет, и закрытым пунктом её читать нельзя.

## Секреты

- **I-1.** `ANTHROPIC_API_KEY` никогда не покидает сервер. Ключ не появляется в клиентском JS, в HTML, в ответах API, в логах и в сообщениях об ошибках.
  - держит: **ничего из кода на 2026-10-20.** Все четыре теста, которые держали этот инвариант, жили в `days/day13`, `days/day14`, `days/day15` и `days/day16` и удалены вместе с днями (ADR `2026-10-20-0737`). Ключ `ANTHROPIC_API_KEY` читают `router` и прежде читали дни 1–4; у роутера публичного адреса нет вовсе, и теста «ключ не появляется в ответе» у него нет. Остались роли `compliance` (чек-лист, I-1–I-3) и `reviewer` (п. 1 «Утечка секрета») — то есть внимательность. Это не закрытый пункт: держателя у I-1 сейчас нет, и его надо завести тому, кто первым откроет наружу ручку, читающую этот ключ.
- **I-2.** В репозитории нет реальных секретов. `.env` в `.gitignore`, коммитится только `.env.example` с пустыми значениями.
  - держит: шаг «Секреты не попали в репозиторий» (`.github/workflows/docs-guard.yml`) и `test/secrets-step.test.js`, исполняющий тело этого шага. Строку `.env` в `.gitignore` не проверяет ничто.
- **I-3.** Ключ не передаётся в чат, в issue, в PR и в любые внешние сервисы (облачные диски, почта, публикуемые страницы). Исключения — только API провайдера, выдавшего этот ключ, и два места хранения: GitHub Secrets и `.env` на сервере; других хранилищ нет. Ротация — при любом подозрении на утечку.
  - держит: по каналам передачи — роль `compliance` (чек-лист, I-1–I-3), и то чтением диффа: шаг секретов ловит ключ только в репозитории, а чат, PR и внешние сервисы не видит никто. **«Других хранилищ нет» и «ротация при любом подозрении» не держит ничто.** Ротацию агент держать и не может: ключ владельца, отзыв и выпуск — его действие.
  - **Ключ AI-ревью — другой ключ, и места у него свои** (решение владельца 2026-10-18, день 32): AI-ревью PR авторизуется ОТДЕЛЬНЫМ API-ключом Anthropic, выпущенным только для него, а не токеном подписки и не продовым ключом. У него **одно** место — GitHub Secret; на сервере он не нужен и туда не кладётся. Продовый `ANTHROPIC_API_KEY` в GitHub Secrets **не кладётся**: в секретах репозитория его нет (на 2026-10-18 там `SSH_HOST`, `SSH_KEY`, `SSH_USER` — и всё), и ревью он не обслуживает. Два ключа — две области поражения: утёкший ключ ревью стоит расхода на ревью, продовый — расхода приложения. Имя секрета — `ANTHROPIC_API_KEY_AI_REVIEW` (PR #349, head `5b2658a`), и **место появляется после мержа PR #349**: в `main` файла `ai-review.yml` ещё нет, а в секретах репозитория этого имени ещё нет.
    - держит: `ничто`. **После мержа PR #349** единственное имя секрета будет читать `.github/workflows/ai-review.yml`, то есть workflow не даст ревью молча взять другой ключ; до мержа этого файла в `main` нет, и не держит даже это. Ни «один ключ только для ревью», ни «продовый в GitHub не кладётся» не краснеют нигде и после мержа: положить лишний секрет в GitHub можно вне репозитория, и дифф этого не видит. Остаётся роль `compliance` чтением диффа и владелец, который кладёт секреты сам.

- **I-15.** `RAG_KEY` живёт только в перечисленных местах, и других нет. Места: `deploy/rag.env` на сервере — служба `rag` читает ключ на старте и без него не поднимается (`rag/serve.py`, `main`); `deploy/agents.env` на сервере — копия ТОГО ЖЕ значения, сервис агентов предъявляет его как клиент `/rag` (ADR `2026-10-04-0735`, п. 1); окружение ноутбука владельца — оттуда `.mcp.json` подставляет `${RAG_KEY}` клиенту Claude Code (ADR `2026-09-29-1639`, п. 5); GitHub Secret `RAG_KEY` — **место появляется после мержа PR #349**, его читает `.github/workflows/ai-review.yml` (ADR `2026-10-18-1147`, п. 2.3). Всё остальное — нарушение: `RAG_KEY` в `dayN.env`, в `router.env`, в любом ином файле `deploy/*.env`, в репозитории, в чате, в issue, в PR. Буфер обмена во время ротации — **транзит, а не место**: значение проходит через него по необходимости и затирается в конце прохода (чеклист ниже, шаг 7); местом он станет, если его там оставить. Значение `ci-dummy` в `ci.yml` местом хранения не является — это литерал стенда, а не ключ. Ротация — сразу во всех местах за один проход: `agent_docs/operations.md`, раздел «Ротация RAG_KEY».
  - держит: **перечень мест не держит ничто, кроме роли `compliance`** — чтением диффа и закрытым списком серверных команд (`/day-cycle`, фаза 9: копия `RAG_KEY` разрешена только из `rag.env` в `agents.env`, в прочих файлах запрещена). Этот ключ **не ловит** шаг «Секреты не попали в репозиторий» (`.github/workflows/docs-guard.yml`): он ищет префиксы ключей провайдеров, а `RAG_KEY` — случайная строка без префикса. Лишний файл на сервере, значение в чужом секрете CI или в окружении чужой машины не видит никто, и прогон от этого не краснеет. Ротацию агент держать и не может: ключ владельца, перевыпуск и раскладка по местам — его действие.

## Расход средств

- **I-4.** Ни один запрос не может вызвать API без прохождения rate limit и суточного лимита. Проверка лимита предшествует вызову, а не следует за ним. Порядок «лимит до вызова» исключений не знает.
  - держит: тесты «лимитер срабатывает ДО исполнения: отказанный вызов в сеть не ходит» (`mcp/test/service.test.js`), «исчерпанный лимит токенов — budget_exceeded с датой сброса, провайдер не вызывается» (`router/test/service.test.js`) и таблица маршрутов службы индекса на Python — у каждой ручки названо окно, запись без окна не даёт модулю загрузиться (`rag/test/test_serve.py::RouteTableTest`); роли `compliance` (чек-лист) и `backend` (граничное правило). **Чего здесь больше нет:** все тесты порядка, жившие в `days/**` — дни 1–5, 7–11, 13–16 и шов дня 20, — удалены вместе с днями (ADR `2026-10-20-0737`). Из двух мест, где платный вызов начинается сегодня, порядок под тестом только у роутера; у сервиса `agents` теста на «слот до вызова» нет вовсе — он был у экранов дней, а экранов больше нет.
  - **Исключение по окнам на адрес (`EVAL_KEY`, ADR `2026-10-05-1130`) снято вместе с днями 22–25** (ADR `2026-10-20-0737`): ключа `EVAL_KEY` в проекте не осталось ни в одном файле, и слово «ни один запрос» читается без исключений. Ключ оператора на сервере (`deploy/day2[2-5].env`) после удаления служб никем не читается — он в списке на уборку у владельца.
- **I-5.** Суточный лимит `MAX_DAILY_CALLS` — жёсткий. При исчерпании приложение отдаёт кэш и честное сообщение, но не вызывает API.
  - держит: тест «суточные суммы восстанавливаются из журнала после перезапуска» (`router/test/service.test.js`) и суточный потолок вызовов эмбеддинга службы индекса (тест «исчерпанный потолок останавливает до вызова эмбеддера», `rag/test/test_tools.py`, счёт в `/data/usage.json`); роль `compliance`. Тесты «потолок общий для всех адресов» и «часовое окно отпускает по сроку, суточный потолок — нет» жили в `days/day13`–`day15` и удалены вместе с днями (ADR `2026-10-20-0737`). **`MAX_DAILY_CALLS` после уборки не читает ни одна оставшаяся единица:** имя было у приложений дней; сверено грепом по дереву — остались только строка в `deploy/put-secrets.sh`, которая пишет его в никем не читаемый `secrets.env`, и ДРУГОЕ имя `CONTROL_MAX_DAILY_CALLS` у поверхности управления сервиса агентов. То есть инвариант сейчас без предмета, а суточный потолок держат бюджет приложения в роутере и `RAG_DAILY_EMBEDS` службы индекса. «Отдаёт кэш» относилось к дням 1–5 и предмета тоже не имеет.
- **I-6.** У каждого вызова есть `max_uses` для web_search и `max_tokens`. Безлимитных вызовов не бывает.
  - держит: тесты `router/test/router.test.js`: «rank_news: web_search реально уходит в запрос, поиск учтён в usage» (`max_uses`), «неизвестный класс уходит в other без исключения» и «потолок ответа задаётся вызывающим в пределах класса» (`max_tokens`); у агента — «maxTokens 2049 — отказ сервиса, роутер не вызывается» (`agents/test/layered.test.js`); роль `compliance`. Вызовов мимо роутера в проекте больше не осталось: ими были дни 1–4, и они удалены (ADR `2026-10-20-0737`).

## Достоверность

**I-7 – I-9 остались без предмета 2026-10-20** (ADR `2026-10-20-0737`).
Приложений, которые выдают новости, в проекте больше нет: дни 1–25 удалены
вместе со своими построениями, промптами и тестами. Формулировки ниже и вся
цепочка оговорок к ним («с дня 2 ответ — свободный текст», «с дня 11
неприменимы», «с дней 18–20 не держатся ничем», «с дня 22 неприменимы»)
оставлены как есть: это запись того, как гарантия слабела от дня ко дню, и
переписывать её под сегодняшний день значило бы потерять разбор. Читать их
нужно так: предмета у I-7 – I-9 сегодня нет, и появится он только с новым
приложением, которое начнёт утверждать что-то о внешнем мире. Единственный
живой остаток — вырезание ссылок не из подборки в `agents/src/agent.js` под
тестом, названным в строке «держит» у I-7; агент `news-analyst` в реестре
остался, экрана у него нет.

- **I-7.** Каждый пункт новостей несёт минимум одну рабочую ссылку на источник. Пункт без источника не показывается.
  - держит: тест «предупреждения: обрезанный ответ, вырезанные ссылки, ленты без ответа» (`agents/test/agent.test.js`) — ссылка не из подборки вырезана; роли `compliance` и `frontend`. Построение дня 1 (`parseFeed` отбрасывает запись без ссылки) удалено вместе с днями (ADR `2026-10-20-0737`).
- **I-8.** Приложение не выдумывает новости, чтобы заполнить три карточки. Если значимых новостей меньше — показывается меньше, с пояснением в поле `note`.
  - держит: роли `compliance` (чек-лист) и `design`. Теста нет: гарантия — промптом, а промпт с дня 6 заменяет посетитель (абзацы ниже).
- **I-9.** Дата в карточке — дата события из источника, а не дата запроса.
  - держит: **ничто.** Единственным держателем было построение дня 1 (`days/day1/rss.js`, `digest.js`, `sanitizePicks` в `anthropic.js`) под тестами `days/day1/test/rss.test.js`; день удалён (ADR `2026-10-20-0737`), и карточек с датами в проекте не осталось.

I-7–I-9 сформулированы для карточек дня 1 и держатся построением. В дне 2 ответ —
свободный текст с параметрами пользователя (ADR `2026-09-07-2330`, принят): гарантия
I-7 сужена до «ссылка, присутствующая в ответе, ведёт на статью из лент» (белый список,
ссылка не из списка вырезается), пункт без ссылки возможен при малом `max_tokens`;
I-8 и I-9 держатся промптом (модель получает только проверенный список с датами)
и честным `note` при пустом результате.

**С дня 6 промпт перестал быть постоянным.** Посетитель может заменить системный
промпт агента для своего браузера (ADR `2026-09-09-1623`), поэтому I-8 и I-9 —
единственные инварианты, которые держались промптом, — для такого запуска не
гарантированы: сняв словами «отвечай только по этим материалам», можно получить
выдуманный ответ. I-7 это не затрагивает: белый список ссылок — код на сервере,
и ссылка не из подборки вырезается независимо от промпта. Запуск с заменённым
промптом помечен: событие «Взял ваш системный промпт» в мониторе, признак
`systemOverridden` в ответе и строка «системный промпт» в записи ленты.

**С дня 15 правится не один промпт, а пять.** Посетитель меняет для профиля
промпты сводки, ответа, проверки инвариантов, пополнения памяти и формулировщика
(ADR `2026-09-23-0646`, таблица `profile_prompts`); правка действует у всякого,
кто занял тот же профиль, и живёт 30 дней. Оговорка о I-8 и I-9 из абзаца выше
распространяется на все пять, а правка промпта проверки выключает единственную
настоящую проверку дня 14: вердикт становится «не разобран» или `unchecked`.
Это выбор посетителя, он помечен в журнале и в ответе. I-10 цел — в
`profile_prompts` и `run_prompts` нет ни адреса, ни иных признаков устройства.

**С дня 11 I-7 – I-9 неприменимы вовсе** (ADR `2026-09-15-2024`, п. 1):
агент дня 11 новостей не выдаёт, архива статей и белого списка источников
у него нет, ссылки в его ответе ничем не проверяются. Страница дня говорит
это прямо; здесь записано, чтобы инвариант не считали нарушенным молча.

**С дней 18–20 I-7 и I-8 не держатся ничем, и это записано здесь, а не
подразумевается** (ADR `2026-09-28-0736`; находка `compliance`, PR #237).
Хост MCP выдаёт новости снова — работа планировщика дня 18 просит свежие
новости со ссылками, — но архива статей и белого списка источников у него
нет: материалы приходят от сервера `mcpnews` (Hacker News Algolia), а не из
проверенной подборки. Поэтому ссылку, которой в ответах инструментов не
было, **не вырезает ничто** — механизма дня 2 здесь нет, и I-7 в прежней
форме неприменим. I-8 держится промптом реестра `mcp-agent` («данные бери
только из ответов инструментов; если инструмент не ответил — скажи прямо»),
то есть ровно так же, как со дня 2, — а у дня 20 задание пишет посетитель
свободным текстом, и снять этим заданием ограничение промпта можно. I-9
неприменим по той же причине, что и I-7: даты в ответе ничем не сверяются.
Отдельно: результаты инструментов — недоверенные данные, и в дне 20 текст с
чужих серверов уходит модели (ADR, «Последствия», об инъекции через
результаты инструментов). Держит: ничто; цепочка дня 19 новостей от своего
имени не утверждает вовсе — она показывает равенство `sha256`.

**С дня 22 I-7 – I-9 неприменимы, и это записано здесь, а не
подразумевается** (ADR `2026-10-04-0735`; находка `compliance`, PR #302).
Агент `rag-agent` новостей не выдаёт вовсе: он отвечает о самом проекте по
фрагментам его корпуса, найденным `project.search`. Новостей, дат события и
ссылок на источники в его ответе нет, поэтому I-7 и I-9 в прежней форме не о
нём. Что у него есть вместо ссылки — **путь файла в репозитории**, и
названный моделью путь **не сверяет ничто**: ни с выдачей поиска, ни с
деревом. Механизма дня 2 (белый список, вырезание) здесь нет: `guardLinks` и
`stripUnknownLinks` в `agents/src/rag-agent.js` не импортируются вовсе,
поэтому и выдуманную http-ссылку в свободном тексте **не вырезает ничто** —
ровно как у дней 18–20.
I-8 — «не выдумывать, чтобы заполнить» — держится **только промптом**
реестра («отвечай только по этим фрагментам; если ответа в них нет — ровно
фраза „В найденных фрагментах ответа нет“»). Признак `refused` ответа
запуска ловит эту фразу дословно, то есть форму, а не смысл; проверка
`cited` прогона сравнения (ADR, п. 6) — замер на десяти вопросах, а не
держатель. Смягчающее, которое надо называть вместе с этим: промпт дня 22
посетитель **не заменяет** — он в реестре агентов, а `parseInput` принимает
только вопрос и режим. Оговорка дней 6–15 о заменённом промпте к нему не
относится, и это сильнее, чем у дней 18–20. Отдельно: фрагменты корпуса —
недоверенные данные, и в корпусе лежит код этого же сервиса, то есть во
фрагмент может попасть дословный шаблон блока указаний. Держит: форма блока
(метка обезвреживается, вопрос стоит последним) — и больше ничто.

## Данные пользователя

- **I-10.** Запросы пользователей не хранятся в связке с IP дольше окна rate limit. Кэш ключуется нормализованной сферой, не пользователем.
  - держит: тест «адрес не живёт дольше часового окна (I-10)» (`mcp/test/limits.test.js`); роли `compliance` и `data`. Два других теста жили в `days/day16` и `days/day20` и удалены вместе с днями (ADR `2026-10-20-0737`). Лимитер службы индекса на Python свои окна ведёт в памяти процесса, и теста на срок жизни адреса у него нет.

**С дня 7 переписка с агентом хранится на сервере** (ADR `2026-09-09-1906`):
сессия определяется cookie, тексты сообщений живут в SQLite на томе агента
30 часов без новых сообщений и удаляются кнопкой «очистить». I-10 при этом
не нарушен: в записи нет ни адреса, ни иных признаков устройства — только
идентификатор сессии, роли, тексты и числа сводки. Связка «запрос ↔ адрес»
по-прежнему живёт не дольше окна лимитера.

**С дня 11 у посетителя есть устойчивый псевдонимный идентификатор**
(ADR `2026-09-15-2024`): cookie профиля `day11_pid` живёт **30 дней** и
связывает диалоги одного посетителя между сессиями, а за профилем
копится досье — правила о предпочтениях и процессах и факты по темам,
записанные моделью из разговоров. Это шире прежней сессии на 30 часов:
I-10 запрещает связку с IP, но не запрещает такой связки диалогов между
собой, и здесь она есть намеренно. Смягчающее, которое надо называть
вместе с этим: **идентификатор ничего не защищает** — профили открыты,
любой посетитель может занять, прочитать, пополнить и удалить любой из
них, поэтому досье не принадлежит человеку и не доказывает, что диалоги
вёл один и тот же человек. Ни адреса, ни иных признаков устройства в
записи по-прежнему нет.

## Документация

- **I-11.** Источник истины для решений — git.
  - держит: ничто.
- **I-12.** Принятые ADR не редактируются. Изменение решения — новый ADR со статусом «Заменяет ...».
  - держит: ничто. Правило записано у роли `docs`, но `agent_docs/adr/` не входит в защищённые пути (`agent_docs/guides/agent-roles.md`, «Мерж по консенсусу»), и правку принятого ADR никакой шаг с диффом не сверяет.
- **I-13.** Терминология не множится. Предмет, уже названный в проекте, называется тем же словом — в документах, в сообщениях владельцу, в комментариях кода. Новое понятие вводится, только когда старого нет; вводится один раз, с определением, и заносится в `agent_docs/glossary.md`. Синоним «для красоты» — дефект: владелец вынужден спрашивать, о чём речь, и теряется связь между документом и разговором.
  - держит: ничто.

## Защита

- **I-14.** Защита приезжает с держателем. Правило безопасности или расхода — строка конфигурации, проверка в коде, лимит — вводится в том же PR, что тест или шаг CI, который краснеет при снятии держащей строки. Нарушение: защита есть, а мутация «убрать строку» оставляет прогон зелёным; это баг, а не долг. Заметить: прогнать мутацию до ревью; раздел «Что держит» описания PR пуст или называет не тест и не шаг (ADR `2026-09-24-1230`, C1 и A1).
  - держит: ничто на 2026-09-24. Роль `qa` требует негативный тест на каждый лимит (граничное правило) — часть I-14, не весь. Шаг `docs-guard` «Разделы доказательств заполнены» (A1 того же ADR) держателем **не станет**: он проверяет присутствие и непустоту разделов, а не то, что там назван тест, и при снятии держащей строки не краснеет — это сказано в его собственном комментарии. Вписывать его сюда нельзя: инвариант о держателях сломался бы о собственную строку. Настоящего держателя у I-14 пока нет, и он потребует отдельной работы. Известные нарушения — в `agent_docs/backlog.md`, «Владельцу»: `header_up X-Forwarded-For {client_ip}` в `deploy/caddy/Caddyfile` и постоянное время сверки ключа в `mcp/src/service.js`.

- **I-16.** Секрет, заведённый агентом, существует только вместе со знанием владельца. Агент заводит секрет (`gh secret set`) сам, передавая значение только через stdin — из файла, из окружения или порождённым на месте; значение не появляется в аргументах команды, в выводе, в чате, в PR и в истории shell. Если значение порождено агентом и больше нигде не лежит, секрет считается заведённым только после подтверждения владельца: агент даёт команду, кладущую значение в буфер обмена (`pbcopy`), и вопрос «Сохранил в менеджере паролей?» с вариантами «Сделал / Не сделал / Другое»; до ответа «Сделал» секрет не используется в выкатке и не докладывается как готовый, после — буфер затирает сам агент сразу же, `printf '' | pbcopy`. Файл-посредник живёт **вне рабочего дерева** (`mktemp` вне клона) и удаляется в том же проходе; значение в файле внутри рабочего дерева — запрещённое место; буфер обмена — транзит (как в I-15), затираемый в конце прохода; менеджер паролей владельца местом системы не является вовсе — там значение лежит постоянно, и это знание владельца вне проекта, которым не распоряжаются ни агент, ни репозиторий. Агент заводит только **новое** имя: до вызова `gh secret set` он сверяется с `gh secret list`, и имя, которое там уже есть, — ротация, то есть действие владельца. Уровень — только `--repo MikeKharr/ai-advent-2026` и его `--env`; `--org`, `--user` и чужой репозиторий — никогда. Если у ключа есть перечень мест (I-15), новое место вписывается в перечень в том же проходе. Ключи, выпускаемые в чужих консолях (Anthropic Console, панели провайдеров), выпускает владелец по пошаговой инструкции агента. Удаление и ротация существующих секретов — владелец. Нарушение: секрет в хранилище, о котором владелец не знает или который не сохранил; имя, перезаписанное агентом вместо ротации владельцем; значение, оставшееся в файле рабочего дерева или в буфере. Заметить: имя в `gh secret list`, по которому в разговоре нет «Сделал» (ADR `2026-10-18-2132`).
  - **Это о секретах GitHub.** Секреты на сервере (`deploy/*.env`) кладёт владелец через `deploy/put-secrets.sh`, и закрытый список серверных команд (`/day-cycle`, фаза 9) этот инвариант не расширяет.
  - держит: роль (оркестратор); **держателя кодом нет** — подтверждение факт разговора, а не строка репозитория, и ни одна проверка не краснеет от секрета, заведённого без ответа «Сделал». Передачу через stdin тоже не держит ничто: значение в аргументе команды видно только в транскрипте, в дифф оно не попадает. То же у сверки с `gh secret list` до вызова, у уровня `--repo`/`--env` и у затирания буфера — всё это команды сессии, и прогон от их пропуска не краснеет. Единственное, что может покраснеть, — значение, забытое **в рабочем дереве**: его ловит шаг «Секреты не попали в репозиторий» (`.github/workflows/docs-guard.yml`), и то лишь если значение похоже на образец из `KEY_SAMPLES`.
