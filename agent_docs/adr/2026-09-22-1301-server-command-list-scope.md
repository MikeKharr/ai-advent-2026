# [2026-09-22 13:01] Предмет закрытого списка серверных команд: руки агента, а не содержимое выкатки

Файл: `agent_docs/adr/2026-09-22-1301-server-command-list-scope.md`

## Статус

Принято (решение владельца 2026-09-22; принятие — мерж этого PR
владельцем). Уточняет ADR `2026-09-11-1230` в части «любой `exec` в
контейнеры прода — без исключений»: запрет остаётся, но его предмет —
команды агента по ssh, не строки в `deploy.yml`.

## Контекст

В PR #201 шаг выкатки использует `docker compose exec -T caddy caddy
validate` и `… caddy reload`. Закрытый список в `/day-cycle`, фаза 9,
называл любой `exec` в прод-контейнеры запрещённым без исключений, и
буквальное чтение запрещало такой шаг.

Оба гейта разобрали это и пришли к одному: запрет не распространяется на
строки в `deploy.yml`.

- `compliance`, по тексту ADR `2026-09-11-1230`: предмет объявлен трижды —
  «доступ агента к серверу **по ssh**», «закрытый список того, что **агент
  делает на сервере сам**», «агент выполняет **по ssh без окна**». В том же
  списке запрещено «всё, что меняет состояние прода» — включая `git` в
  каталоге сервера — и тут же сказано «выкатка — только через `main` и
  `deploy.yml`». Если бы список управлял содержимым выкатки, она нарушала
  бы собственное решение по пяти пунктам.
- `reviewer`, по области риска: ADR сам называет, от чего защищает —
  «изменение прода мимо CI и мимо владельца» и «секреты сервера в
  транскрипте». Удалённый скрипт выкатки уже сегодня делает `git reset
  --hard`, `sed -i` по `.env`, `docker compose up -d`, `docker image
  prune`, `docker inspect`; каждая была бы запрещена, если бы список
  распространялся на выкатку.

Граница, которая живёт только в записи одной итерации, будет переспорена
при следующем чтении списка.

## Решение

Предмет списка — команды, которые **агент запускает сам** по ssh, сочиняя
их по своему усмотрению; между его решением и продом нет ни одного гейта
(окно подтверждения снято ADR `2026-09-11-0513`). Строка в `deploy.yml` —
не агент, а `main`.

Строка считается лежащей на стороне `main` при всех четырёх условиях:

1. команда — литерал в ревьюируемом файле, без единой подстановки;
2. достижима только мержем в `main` с гейтами класса A (ни
   `pull_request`, ни `pull_request_target` — форк исполнение не
   контролирует);
3. не печатает значений из `deploy/*.env` и секретов;
4. не универсальная лазейка: `exec … node -e`, `exec … sh -c`,
   `exec … bash` и `exec` с аргументом из переменной запрещены где бы они
   ни лежали, включая workflow — они возвращают произвольное исполнение и
   отменяют смысл первого условия, потому что файл перестаёт описывать то,
   что выполняется.

Правка `deploy.yml`, добавляющая команду в прод-контейнер, — класс A,
гейт `compliance` обязателен.

Сам список команд агента не расширяется: правка описывает предмет, а не
добавляет строки.

## Обоснование

Проверка, которая держит правило от самоосвобождения: строка в выкатке не
даёт агенту ничего, чего у него не было, — удалённый скрипт и так
исполняется с доступом к докеру. Та же строка в закрытом списке дала бы
**агенту** новую способность. Вся асимметрия в этом.

Четвёртое условие закрывает обход: `exec … sh -c` в workflow формально
был бы литералом, но вернул бы произвольное исполнение и сделал бы первые
три условия бессодержательными.

## Последствия

Положительные:

- Список говорит, о чём он, и не запрещает выкатке то, что она уже делает.
- Норма живёт в действующей инструкции (`/day-cycle`, фаза 9), а не в
  записи итерации.

Отрицательные и риски:

- Условия проверяет человек или гейт глазами, механизма нет: `exec` с
  подстановкой в workflow ловит только `compliance` на ревью класса A.
- Граница «агент / `main`» держится, пока `deploy.yml` недостижим из
  `pull_request_target`; смена триггеров выкатки требует пересмотра этого
  решения.
