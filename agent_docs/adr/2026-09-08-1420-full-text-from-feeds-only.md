# [2026-09-08 14:20] Полный текст статей берём только из лент, с бюджетом на объём

Файл: `agent_docs/adr/2026-09-08-1420-full-text-from-feeds-only.md`

## Статус

Принято (задание дня 3 от владельца, сессия 2026-09-08)

## Контекст

Задание дня 3: хранить не список новостей, а полный текст статьи, потому что
запрос пользователя формулируется шире тематики — «какие суммы раундов»,
«кто инвесторы», «сравни подходы». По заголовкам на такое не ответить.

Отсюда два вопроса, на которые задание ответа не даёт: **откуда брать текст**
и **сколько его отдавать модели**.

Замер восьми лент проекта 2026-09-08 (длина текста первой записи):

| Лента | content:encoded | description |
|---|---:|---:|
| Crunchbase News | 6746 | 260 |
| EU-Startups | 4202 | 545 |
| Entrackr | — | **3894** |
| Inc42 | 2756 | 128 |
| Tech.eu | 2587 | 203 |
| Pandaily | 2168 | 192 |
| TechCrunch | — | 433 |
| Sifted | — | — |

Шесть лент из восьми отдают статью целиком в том же запросе, которым мы уже
ходим за лентой. TechCrunch кладёт анонс, Sifted — только заголовок.

## Решение

1. **Текст берётся только из ленты:** `content:encoded`, а где его нет —
   `description` (случай Entrackr). За страницами статей приложение не ходит.
2. **Текстом считается материал длиннее 800 символов.** Ниже — это анонс;
   такие материалы уходят в подборку с явной пометкой «только анонс», чтобы
   модель не приняла урезанный тизер за короткую статью.
3. **Три потолка на объём:** 6000 символов на статью; 120 000 символов на
   запрос суммарно (~30K токенов, ~$0.03 за вызов), дальше материалы идут
   только заголовком; 1–15 статей с источника при значении по умолчанию 5.
4. **Число материалов с полным текстом видно пользователю** — в ленте тегом и
   в `note`, если текст есть не у всех.
5. Поле `format` дня 4 переименовано в `prompt`: теперь это сам запрос вместе
   с требованиями к формату, а не описание оформления.

## Обоснование

**Почему не обходить страницы статей.** RSS издание публикует само и для того,
чтобы его читали агрегаторы, — это опубликованный интерфейс. Обход страниц
меняет три вещи разом: нагрузку (240 запросов к чужим сайтам на обновление
кэша вместо 8), хрупкость (вёрстка меняется, антибот-защита срабатывает,
нужен свой экстрактор HTML без зависимостей) и правовую рамку. Выигрыш —
две ленты из восьми. Размен не стоит того, а граница «берём только то, что
издание положило в ленту» проверяема и объяснима.

**Почему бюджет, а не просто лимит статей.** Длина статьи различается в разы:
Crunchbase отдаёт 6.7К символов, Pandaily 2.2К. Лимит по числу статей при
таком разбросе не ограничивает ни цену, ни попадание в окно модели. Бюджет
в символах ограничивает и то и другое напрямую.

**Почему 120 000 символов.** Это ~30K токенов: вчетверо меньше окна Haiku 4.5,
то есть остаётся запас на системный промпт и ответ, и ~$0.03 за вызов по
входу. Без потолка пятнадцать статей с восьми лент дали бы ~220K токенов —
за пределами окна модели и вдесятеро дороже.

**Почему по умолчанию 5 статей с источника, а не 30.** В дне 4 в модель уходил
заголовок с анонсом (~75 токенов на материал), здесь — статья (~900 токенов).
Тридцать статей с источника означали бы упор в бюджет на первых же изданиях:
пользователь задавал бы число, которое ни на что не влияет.

## Последствия

Положительные:

- на вопросы по существу статьи можно ответить — ради этого день и делается;
- ни одного запроса к чужим сайтам сверх тех восьми, что и так делались;
- расход ограничен сверху конструкцией, а не аккуратностью пользователя;
- честная пометка «только анонс» не даёт модели выдать тизер за статью.

Отрицательные:

- **Два издания из восьми участвуют неполноценно.** TechCrunch и Sifted
  попадают в подборку заголовками; на запрос «что пишет TechCrunch о X»
  ответ будет беднее, и это видно пользователю, но не лечится.
- **Запрос дороже дня 4 примерно вдвое** (~$0.03 против ~$0.018 при значениях
  по умолчанию) и может достигать ~$0.05 при 15 статьях с источника. Потолок
  суток при `MAX_DAILY_CALLS=50` — порядка $1.5–2.5.
- **Кэш лент потяжелел**: восемь лент с текстами это ~1–2 МБ в памяти процесса
  вместо десятков килобайт. Для контейнера с 1 ГБ неощутимо, но при десятке
  дней на одном сервере за этим придётся следить (пункт уже в бэклоге).
- **Поверхность промпт-инъекции выросла в разы.** Раньше в контекст попадали
  заголовки, теперь — тысячи символов чужого текста. Защита прежняя (снятие
  разметки до срезания угловых скобок, обёртка `<candidates>` с явным
  указанием, что это данные, белый список ссылок), но нагрузка на неё выше,
  и полной гарантии эта защита не даёт.
- **Обрыв бюджета не виден в середине списка**: материалы после исчерпания
  идут заголовками, и пользователь узнаёт об этом из `note`, а не из позиции
  конкретной статьи.

## Альтернативы рассмотрены

- **Ходить за страницами статей.** Даёт полный текст у всех восьми лент, включая
  TechCrunch и Sifted. Отклоняется: 240 запросов к чужим сайтам на обновление
  кэша, собственный экстрактор HTML без зависимостей, ломкость при смене вёрстки
  и антибот-защите, другая правовая рамка — ради двух лент из восьми.
- **Два вызова: выбрать по заголовкам, потом дочитать выбранное.** Дёшево по
  входу и позволило бы больше статей. Отклоняется: удваивает задержку и число
  вызовов (то есть суточный лимит), а главное — модель выбирает по заголовку
  до того, как узнала запрос по существу, и как раз широкий вопрос («где
  упоминаются суммы») по заголовкам не решается.
- **Отдавать текст без потолка, полагаясь на лимит статей.** Проще в коде.
  Отклоняется: длина статей различается втрое, поэтому лимит по числу не
  ограничивает ни цену, ни попадание в окно модели.
