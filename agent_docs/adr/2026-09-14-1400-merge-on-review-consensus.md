# [2026-09-14 14:00] Мерж PR по консенсусу гейтов класса, без отдельного слова владельца

Файл: `agent_docs/adr/2026-09-14-1400-merge-on-review-consensus.md`

## Статус

Принято (владельцем 2026-09-10): «не спрашивай меня про допустимость
bash / zsh команд — я их всё равно не очень понимаю, выполняй, если есть
консенсус; также и в отношении PR». И: «отправляй пуш-нотификации при
новых релизах».

Уточняет ADR `2026-09-13-1800` в одной части: человеческий гейт «слово на
деплой» (фаза 9 `/day-cycle`, п. 3 поправки о `gh pr merge`) заменяется
консенсусом обязательных гейтов класса. Остальное в ADR `2026-09-13-1800`
в силе; сам он не правится (I-12).

## Контекст

- Приложения стоят на публичном адресе `challenge.zpq.ai`, деплой
  триггерится пушем в `main`. Любой мерж в `main` — продакшн-выкатка: даже
  docs-PR пересобирает и выкатывает атлас (`operations.md`, «Атлас проекта»).
- По ADR `2026-09-13-1800` каждый мерж ждал слова владельца. Владелец
  прямо говорит, что не разбирается в shell-командах и PR на уровне,
  который делал бы это слово содержательной проверкой: гейт превращался в
  формальный клик, а работа стояла до него.
- Содержательную проверку уже делают гейты класса: reviewer, compliance с
  правом вето, design-review для UI, механический CI.

## Решение

1. **Мерж PR — по консенсусу обязательных гейтов класса** (ADR
   `2026-09-13-1800`) при зелёном CI, без отдельного согласия владельца:
   - A — reviewer + compliance (+ design-review при UI);
   - B — reviewer (+ design-review при UI);
   - C — механический CI.
   Консенсус — ни одной открытой блокирующей находки у каждого гейта
   класса. Вето compliance блокирует мерж поверх класса.
2. **За владельцем остаются:** принятие ADR; продуктовые развилки;
   ввод новых секретов (`deploy/put-secrets.sh` руками владельца);
   решения, которые гейты вынесли ему (два круга перепроверки без снятия
   блокирующих, неснятое вето).
3. **После каждой выкатки — push-уведомление владельцу:** что выкачено
   (PR, единица), итог проверки `healthz`.
4. Окно подтверждения `gh pr merge` в Claude Code остаётся: правила `ask`
   в `.claude/settings.json` не менялись. Убрать их может только владелец
   через `/permissions`; агент их не правит и не обходит.

## Обоснование

Слово владельца на мерж дублировало гейты, не добавляя проверки: владелец
сам говорит, что содержательно дифф не оценивает. Держат качество
механические контроли и независимые ревью-экземпляры; вето compliance
сохраняет защиту ключа и расхода. Push-уведомление возвращает владельцу
видимость выкатки без блокировки.

## Последствия

- Цикл дня доходит до прода без ожидания владельца, кроме ADR и
  продуктовых развилок.
- Правило «пока выкатка идёт или ждёт в очереди, следующий PR не мержить»
  (`operations.md`, «Атлас проекта») остаётся и соблюдается агентом перед
  каждым мержем.
- Мерж — с явным текстом коммита (`gh pr merge N --squash --subject …
  --body …`) и проверкой `git log -1 --format=%B` после: иначе GitHub
  дописывает `Co-authored-by` с адресом машины (`operations.md`, «Мерж PR»).
- Ответственность за ошибку мержа смещается на гейты. Слепое пятно,
  общее для ревьюеров, больше не ловится чтением владельца
  (`guides/agent-roles.md`, последний раздел) — компенсируется
  механическими контролями и уведомлением после выкатки.
- Пока правила `ask` не сняты, мерж по-прежнему упирается в окно
  подтверждения — оно больше не означает содержательное согласие.
