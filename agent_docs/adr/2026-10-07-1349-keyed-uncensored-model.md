# [2026-10-07 13:49] Модель без отказов на ноутбуке владельца — в списке дня 11, запуск только по именному ключу

Файл: `agent_docs/adr/2026-10-07-1349-keyed-uncensored-model.md`

## Статус

Предложено. Класс будущей реализации — A (`router/config/**` защищённый путь,
ключи и разрешения, правка сданного дня 11 по явному указанию владельца);
перед принятием — гейт `compliance` с правом вето по защите от злоупотреблений.

Решения владельца 2026-10-07, дословно, в порядке получения:

1. «Для чего ставим модель без цензуры?» → «На сайте, но только для меня».
2. «Какую сборку качать?» → «huihui Q6_K, 22,4 ГБ».
3. Уточнение: «по п2 можно дать для всех (не ограничивать только мной —
   владельцем)».
4. «давайте делать только по ключу, действительно не нужно оставлять доступ
   для всех (хотя модель и доступна публично)».
5. «Где будет экран для модели по ключу?» → «В списке дня 11 под ключом».
6. «Ключи: один общий или свой на каждого человека?» → «Именные ключи».
7. «Помнить ли ключ в браузере между визитами?» → «Нет».
8. «Суточный лимит запросов на один ключ?» → «2000 - как защита от абьюза
   MCP модели».
9. «День 11 сохраняет переписку в открытые профили. Как быть с ответами
   модели без отказов?» → «овтеты читает любой посетитель но вход по ключу».

Дополняет ADR `2026-09-08-1748` (§1 механизмы выбора, §10 ключи приложений),
`2026-09-08-1824` (явный выбор провайдера), `2026-09-15-1448` (поле
`explicitOnly`) и `2026-09-16-1038` (список моделей дня 11); ничего в них не
заменяет. Правка дня 11 — по решению 5 (`AGENTS.md`, «Универсальные правила»).

## Решение

Модель `hf.co/huihui-ai/Huihui-Qwen3.8-27B-abliterated-GGUF:Q6_K` подключается
к роутеру вторым провайдером на той же Ollama ноутбука, что `mac-qwen3`, и
появляется в списке моделей дня 11. **Запуск с ней проходит только с именным
ключом**, который выдаёт владелец; **ответы ложатся в открытые профили дня 11
как у остальных моделей** и читаются любым посетителем без ключа. Ключ
ограничивает запуск, не чтение. Две преграды, каждая со своим тестом:

### 1. Роутер: провайдер виден одному приложению

Запись `mac-qwen3-abliterated` в `router/config/providers.json`: `kind: ollama`,
тот же `baseUrl`, что у `mac-qwen3`, `maxConcurrency: 1`, `explicitOnly: true`,
цена 0, и **новое поле `apps: ["agents"]`** — список идентификаторов приложений
(`router/config/apps.json`), которым провайдера можно назвать по имени.

Проверка — в ветви явного выбора (`router/src/router.js`, `explicit`) и в
`providerLimits`: приложение не из списка получает `refused` со стадией
`policy` и текстом «провайдер доступен не этому приложению», а в `/v1/models`
записи не видит. Сегодня такой границы нет: явный `provider` сверяется только
с ярусами класса (ADR `2026-09-08-1824`, п. 3), и класс `news_answer`
приложения `day5` включает ярус `self-hosted` — без поля `apps` день 5 мог бы
вызвать новую модель прямым `provider`, минуя любой ключ.

Общая ёмкость ноутбука уже держится: `router/src/health.js:26` считает
`inflight` по хосту из `baseUrl`, две записи на одном адресе делят один слот —
две генерации на ноутбуке параллельно не пойдут (проверено по исходнику).

### 2. Сервис агентов: именной ключ до создания запуска

- Переменная **`MODEL_KEYS`** в `deploy/agents.env`: `имя:значение` через
  запятую (`mike:…,guest1:…`). Имя — метка для журнала и лимита, не секрет;
  значение — 24 случайных байта в base64url, без `:` и `,`.
- Запуск `layered-agent` с `model: mac-qwen3-abliterated` обязан нести
  заголовок **`x-model-key`**; день 11 пробрасывает его в `POST /v1/runs` и
  нигде не хранит. Сверка — по свёрткам за постоянное время, форма
  `days/day22/limits.js` (`EVAL_KEY`, ADR `2026-10-05-1130`). **Пустая или
  отсутствующая `MODEL_KEYS` — возможности нет вовсе**: запись из списка
  исчезает, любой заголовок, включая пустой, — отказ.
- Без заголовка или с чужим значением — `403` с текстом «модель доступна
  только по ключу», роутер не вызывается. Предъявленное значение не принимает
  ни одна функция журнала (структурный запрет, образец
  `agents/src/control/key.js`).
- Проверка стоит на **модели запуска**, а не на настройке профиля: день 11
  шлёт `model` в теле каждого запуска (`days/day11/public/index.html`,
  `chosenModel()`), и `PUT /v1/profiles/:id/settings` с этой моделью ключа не
  требует — сохранённая без ключа настройка даёт честный `403` на запуске,
  пока модель не сменят.
- **Суточный потолок на имя ключа — 2000 запусков** (решение 8), в памяти
  `agents`, отказ `429` с датой сброса; сбрасывается перезапуском — та же
  честная граница, что у I-5. Порядок: лимитер дня на адрес → ключ → потолок
  ключа → роутер; ключ меняет, **кому** доступна модель, а не что стоит
  раньше (I-4).

### 3. Список дня 11 — и только дня 11

Новый список `DAY11_MODELS = [...LAYERED_MODELS, <запись с keyed: true>]` в
`agents/src/params.js`; его читают `layered.js` (разбор запуска, `describe`,
настройки) и путь настроек дня 11 в `service.js`. `LAYERED_MODELS` не
меняется: его разделяют `staged.js` и `parseReviewModel` дней 13–15, и
прибавка туда вывела бы модель на три экрана, которых решение 5 не называет.
Урок ADR `2026-09-16-1038` — тот список, задуманный для дня 11, позже
унаследовали дни 13–15.

Экран дня 11: у записи с `keyed: true` под переключателем появляется поле
ключа; значение живёт в памяти вкладки и уходит заголовком с каждым запуском;
после перезагрузки вводится заново (решение 7); `localStorage`,
`sessionStorage` и cookie не трогаются. Подпись записи называет модель
прямо: «без встроенных отказов, ответы видны всем в профиле».

### 4. Что хранится и куда уходит

Ответы — в `messages` диалога профиля, 30 дней (`agents/src/sessions.js`);
профили открыты, любой посетитель может занять профиль и прочитать переписку
(`invariants.md`, «С дня 11…»). Сводка истории при переполнении контекста
идёт **в `anthropic-haiku`** (`agents/src/llm.js:391`, `layered.js:283`) —
то есть текст, порождённый моделью без отказов, уходит в Anthropic под
платным ключом владельца. Факты досье и темы пишет этап пополнения
(`policy.replenish`); его провайдер по исходнику не сверял.

### 5. Расход и журнал

Деньги — 0 у записи; бюджет приложения `agents` ($10/сутки) тратит только
сводка. Бюджет модели — **время ноутбука**: один слот хоста на оба провайдера,
запрос держателя ключа задерживает посетителя `mac-qwen3` на свой дедлайн
профиля `laptop`. Через день 11 потолок 2000 недостижим: у дня свой
`MAX_DAILY_CALLS` 50 на все адреса вместе и 5 в минуту / 30 в час на адрес
(`days/day11/env.js`), а при ~8 ток/с и одном слоте ноутбук физически даёт
сотни ответов в сутки, не тысячи. 2000 — ловушка на утечку ключа и
автоматизацию, не ограничитель ресурса.

Роутер пишет `provider` на каждый вызов и строку учёта без промптов (ADR
`2026-09-08-1748`, п. 8) — без изменений. `agents` добавляет в событие
создания запуска **имя ключа**, значение — никогда. Лог Ollama на ноутбуке —
строки `[GIN] … | адрес | POST "/api/generate"` без тел (проверено по
`/opt/homebrew/var/log/ollama.log`).

Память ноутбука: 128 ГиБ (`sysctl`), сборка Q6_K — 22,4 ГБ (карточка модели),
KV-кэш `q8_0` (`launchctl print`). Обе модели помещаются; переключение, если
Ollama выгрузит одну, стоит загрузки ~20 с — она в дедлайне профиля (ADR
`2026-09-08-1748`, «Таймауты»). `OLLAMA_MAX_LOADED_MODELS` в службе не задан.

### 6. Ключи — только руками владельца

Новый секрет на сервере — владелец (`AGENTS.md`, «Автономность»); закрытый
список `/day-cycle` `MODEL_KEYS` не знает, и копировать его агенту некуда.
Выдача, отзыв и ротация — правка строки `MODEL_KEYS` в `agents.env` и
`docker compose up -d agents` (перечитывает `env_file`), обе — владелец.
Отзыв одного имени не трогает остальных.

### 7. Что проверяет реализация (тест-приманки)

- `router/test`: явный `provider: mac-qwen3-abliterated` от `day5` и `smoke`
  → `refused`/`policy`, адаптер не вызван; от `agents` — вызов уходит;
  `/v1/models` для `day5` записи не содержит. Мутация: убрать проверку `apps`
  — красный.
- `agents/test`: запуск дня 11 с моделью без заголовка, с пустым, с чужим →
  `403`, роутер не вызван; с верным → роутер вызван с этим `provider`; пустая
  `MODEL_KEYS` → записи нет в `describe()` и `403` на любой заголовок;
  2001-й запуск имени за сутки → `429`; `staged-agent` с этой моделью → 400
  «Неизвестная модель» (список дней 13–15 не изменился). Мутации: убрать
  сверку, ветвь пустой переменной, счётчик, развести списки — каждая красная.
- `days/day11/test`: заголовок `x-model-key` доходит до `/v1/runs` стенда и
  не появляется ни в журнале дня, ни в ответе.
- Живая проверка после выкатки: запрос без ключа с подменённым `model` через
  публичный адрес → `403`; с ключом владельца → ответ с
  `provider: mac-qwen3-abliterated#1` в событиях запуска.

## Обоснование

Ключ проверяет сервер, не интерфейс: UI показывает поле, но прямой запрос к
API дня с подменой `model` упирается в ту же проверку в `agents`. Две преграды
защищают от разного: поле `apps` — от любого другого приложения роутера
(сегодня, в будущем, при ошибке в `agents`), ключ — от посетителя публичного
адреса. Список отдельный, потому что решение владельца называет день 11, а
общий список уже один раз расползся на три дня.

Хранение в открытых профилях — решение владельца (9), принятое со знанием,
что читать будет любой; ADR фиксирует цену, а не спорит с выбором.

Довод «модель и так лежит на Hugging Face» ответственности за выдачу с
`zpq.ai` не снимает: там лежат веса, здесь — работающий сервис под доменом
владельца, и каждый ответ исходит от него и остаётся на нём 30 дней.

**Проверено лично** 2026-10-07: устройство выбора провайдера, `explicitOnly`,
ярусы классов и отсутствие границы «приложение → провайдер»
(`router/src/router.js:146-176`, `router/src/config.js`); общий слот хоста
(`health.js:26,51`); авторизация роутера по ключам приложений без ролей
(`service.js:36-44`); пути списка моделей дня 11 (`layered.js:111-118, 168`,
`service.js:245`, `staged.js:276, 312, 375`, `registry.js:105`); `model` в
теле каждого запуска дня 11 (`index.html:1418`); проброс заголовков дня 11 в
`agents` (`days/day11/server.js:210, 637`); лимиты дня 11 (`env.js`);
провайдер сводки (`llm.js:391`); карточка модели: Apache-2.0, база
`Qwen/Qwen3.8-27B`, Q6_K 22,4 ГБ, предупреждения «safety filtering has been
significantly reduced», «Users must ensure their usage complies with local
laws»; лицензия базы Apache-2.0 без пунктов о допустимом использовании;
политика контента Hugging Face запрещает контент, продвигающий разработку
оружия, CSAM и вредоносный код, — к репозиторию весов, не к развёртыванию;
память и переменные службы Ollama; форма лога Ollama.

Неподтверждённым остаётся всё, что собрано по документации поставщика:
умолчание `OLLAMA_MAX_LOADED_MODELS`, размер `qwen3.8:27b` на диске, скорость
Q6_K на M3 Max — Ollama на ноутбуке в момент проверки не отвечала (служба не
поднимается: Tailscale остановлен, `bind: can't assign requested address` в
логе; значит `mac-qwen3` посетителям сейчас недоступен — смежная находка).
Провайдер пополнения фактов не сверен. Юридические оценки ниже — не
консультация, а перечень того, что владельцу стоит проверить.

## Последствия

Положительные: запуск модели недостижим без ключа ни из UI, ни прямым
запросом, ни другим приложением роутера; расход денег у самой модели нулевой;
границы держатся тестами, а не внимательностью (I-14); отзыв одного имени не
трогает остальных.

Отрицательные:

- **Ответы модели без отказов становятся публично читаемыми на `zpq.ai`
  без ключа.** Любой посетитель, заняв профиль, читает переписку 30 дней;
  ключ ограничивает только запуск. Держатель ключа может получить инструкции
  по оружию, наркотикам, вредоносному коду, тексты сексуального характера с
  участием несовершеннолетних — отказов у модели нет по построению, промпт и
  фильтр этого не меняют, — и всё это ляжет в профиль, открытый каждому. Кнопка
  «очистить» есть у любого посетителя, обязанности нажать её — ни у кого.
  Ответственность — на владельце домена, в трёх юрисдикциях: сервер в
  Таиланде (Computer Crime Act), ноутбук там, где владелец (сейчас — РФ,
  законы о запрещённой информации), домен владельца. Выдал ключ — отвечаешь
  за того, кому выдал.
- **Текст модели без отказов уходит в Anthropic.** Сводка истории дня 11 идёт
  в `anthropic-haiku` под платным ключом владельца; политика использования
  Anthropic применяется к ключу, а не к тому, кто породил текст. Это цена
  решения 5 — развилка ниже.
- **Правка сданного дня.** День 11 получает поле ключа, проброс заголовка,
  новый список и тесты; норма «сданные дни не дорабатываются» для него снята
  решением 5 один раз, не навсегда.
- **Ноутбук — общий ресурс.** Запрос держателя ключа задерживает посетителя
  `mac-qwen3`; второго слота нет; ~22 ГБ плюс KV держатся в памяти при
  `keep_alive 30m`.
- **Потолок 2000 через день 11 не работает как ограничитель**: раньше срабатывает
  `MAX_DAILY_CALLS` 50 дня, общий для всех моделей и адресов. Держатели
  ключа делят эти 50 с посетителями Haiku и Kimi.
- **Третья копия сверки ключа из окружения** после `EVAL_KEY` и
  `CONTROL_KEY`; общий модуль не вводится (дни сданы), три места ротации.
- **Ещё один секрет без держателя ротации** (I-3) — только владелец, без
  напоминания. Утечка ключа у приглашённого делает модель публичной до
  отзыва, а отзыв — ручная правка и `docker compose up -d agents`, который
  обрывает запуски всех дней, идущих через этот сервис.
- **Поле `apps` — вторая ось разрешений рядом с `classes`**: записи без поля
  ведут себя как прежде, и забыть поле у следующей закрытой модели легко.

## Решения владельцу

1. **Куда идёт сводка диалога с этой моделью.** Сейчас — в `anthropic-haiku`.
   Рекомендация — для запусков с `keyed`-моделью сжимать историю ею же
   (локально, бесплатно, текст не покидает ноутбук); цена — медленнее и
   второй вызов на том же слоте. Альтернатива «как есть» оставляет платный
   ключ Anthropic под текстом модели без отказов; не рекомендую.
2. **Потолок дня 11 (`MAX_DAILY_CALLS` 50) оставить.** Рекомендация — да:
   он держит расход Haiku и Kimi на том же экране; поднимать ради локальной
   модели — значит поднимать и для платных.

## Альтернативы рассмотрены

- **(а) Публично как есть.** Отклонено владельцем (решение 4); по существу —
  ответственность без контроля круга лиц.
- **(б) Публично с мерами.** Системный промпт «не отвечай о…» — не защита:
  отказы сняты на уровне весов, промпт — просьба, а задание посетитель пишет
  свободным текстом. Фильтр входа/выхода: локальный — вторая модель на том же
  слоте и второй дедлайн; облачный (`guard_prompt` ловит инъекции, не темы) —
  платный вызов и отправка текста поставщику ради модели, выбранной за
  локальность. Лимиты, предупреждение, журнал — не мешают получить запрещённое,
  только реже и с записью. Отклонено.
- **(в) Только владелец** — частный случай: одна запись в `MODEL_KEYS`.
- **Отдельный экран без хранения переписки** (по образцу дня 22). Снял бы
  первое из последствий целиком. Отклонён владельцем (решение 5: «в списке
  дня 11»).
- **Не сохранять ответы этой модели в профиль.** Снял бы публичную читаемость
  при том же экране. Отклонён владельцем (решение 9: «ответы читает любой
  посетитель»).
- **Один общий ключ.** Отклонён владельцем (решение 6).
- **Прибавить запись в `LAYERED_MODELS`.** Короче на один список, но выводит
  модель на дни 13–15, которых решение 5 не называет; отклонено.
- **Второй ключ приложения роутера (`agents-keyed`)** вместо поля `apps`:
  ещё один секрет владельцу, а какой ключ предъявить, решает тот же код
  `agents` — точка отказа не сдвигается; отклонено.
- **Список разрешённых провайдеров у приложения** (`apps.json`) вместо поля
  у провайдера: эквивалентно; закрытость — свойство модели, и читаться она
  должна рядом с `explicitOnly`; отклонено.
