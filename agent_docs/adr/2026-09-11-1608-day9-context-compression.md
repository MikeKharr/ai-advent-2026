## Контекст

Задание дня 9: хранить для сессии сводку (summary), при накоплении N токенов
новых реплик сжимать сводку и реплики в новую сводку, подставлять её в
запрос перед свежими репликами, показывать токены контекста и сводки,
дать контрол N, сравнить качество и расход с режимом без сжатия.

Что есть сейчас (ADR `2026-09-09-1906`, `2026-09-09-2134`):

- Переписка — SQLite на томе агента (`agents/src/sessions.js`). В модель
  уходит **хвост**: целые реплики от свежих к старым, пока помещаются в окно
  контекста; старое отбрасывается (`tail`, поле `dropped`).
- Окно = `min(заданное, 40 % предела входа модели)` (`agents/src/llm.js`,
  `effectiveContext`): на Haiku 3000 при заданных 3000, на Qwen 1720.
  «3000 токенов» из задания — умолчание `contextTokens` в реестре агента
  (`agents/config/agents.json`), не предел модели; страница дня 8 ставит 2000.
- Токены реплик уже лежат в базе: реплика пользователя — оценка той же
  формулой, что у роутера; реплика агента — `usage.outputTokens` провайдера.
  `count_tokens` не используется, и вводить его незачем: роутер считает
  бюджет оценкой, точный счёт дал бы лишний вызов на каждое сообщение.
- Запрос к роутеру — две строки, `system` и `input`; диалог — размеченный
  блок `<dialog>` внутри `input` перед `<request>` и `<candidates>`
  (`buildInput`).

**Экономии токенов на Haiku почти не будет.** Подборка статей занимает
90 %+ входа: в живом замере дня 8 контекст 362 из 26 265 токенов, при
полном окне — 3000 из ~28 000. Сжатие диалога на 20–30 % экономит не больше
2–3 % входа и стоит отдельного вызова модели; в деньгах на Haiku итог
отрицательный. Ценность сводки — **память**: сейчас реплики за окном
отбрасываются молча, со сводкой они остаются в сжатом виде. На малых
моделях (Groq, ноутбук; окно 1720–2080) диалог занимает до 40 % входа, и
там сводка держит память заметно дольше, но деньги там и так почти нулевые.
Сравнение «до/после» поэтому меряется **отдельно по диалоговой части и по
полному запросу**, иначе результат — ноль по построению.

## Решение

### 1. Параметр запуска `summarizeAt`, дни 6–8 не меняются

Новое необязательное поле входа `summarizeAt` — целое, порог N. Без поля
агент ведёт себя как сегодня, байт в байт: таблица сводок не читается и не
пишется, `input` собирается прежним `buildInput`. Дни 6–8 поле не
присылают. Проверка на границе (`params.js`): 500 ≤ N ≤ 8000 и N меньше
заданного окна `contextTokens`.

### 2. Сводка — строка в базе сессии

```sql
CREATE TABLE IF NOT EXISTS summaries (
  session_id    TEXT PRIMARY KEY,
  text          TEXT NOT NULL,
  tokens        INTEGER NOT NULL,   -- usage.outputTokens вызова сводки
  source_tokens INTEGER NOT NULL,   -- прежняя сводка + реплики, что вошли
  through_id    INTEGER NOT NULL,   -- последняя реплика, вошедшая в сводку
  model         TEXT,
  updated_at    INTEGER NOT NULL
);
```

Одна строка на сессию, перезаписывается при каждой суммаризации. Удаляется
в `clear` вместе с сообщениями и, значит, уборкой по сроку (30 часов).
Отдельного решения о хранении нет: сводка — операция над уже хранимым
контекстом сессии (владелец, 2026-09-11). Поставщику ничего нового не
уходит: тексты реплик и так уходят ему при каждом сообщении.

«Свежие реплики» — сообщения с `id > through_id` без записей об ошибках.
`GET /v1/sessions/:id` отдаёт `summary: { text, tokens, sourceTokens,
updatedAt }` или `null`.

**Допущение (владелец не ответил):** сводка видна пользователю — свёрнутый
блок «Сводка разговора» в чате дня 9 над свежими репликами. Без этого
сравнивать качество сжатия нечем.

### 3. Порядок запуска

До обращения к архиву (память поднимается раньше подборки с дня 8):

1. Поднять сводку и свежие реплики; посчитать `fresh` — сумму их `tokens`.
2. Если `fresh ≥ N_eff` — суммаризация: один вызов роутера с прежней
   сводкой и свежими репликами; результат — новая сводка, `through_id` —
   последняя из вошедших реплик; `fresh` становится пустым. События
   `llm_call` / `llm_result` с классом задачи сводки, затем `planning`
   «Сжал историю: A → B токенов (C %)». Один вызов на запуск.
3. Отказ суммаризации (роутер, бюджет, обрыв) запуск **не валит**: сводка
   остаётся прежней, свежие реплики идут хвостом как сегодня, событие
   `warning` «Историю не сжал». Вызов, дошедший до провайдера, считается
   оплаченным.
4. `input`: тема → блок `<summary>` с пометкой «сводка прежней части этого
   разговора» → `<dialog>` со свежими репликами → `<request>` →
   `<candidates>`. Хронология: сначала что было до, потом что говорили
   после, потом что спрашивают сейчас. В контракте роутера «системный блок
   или первое сообщение» неразличимы — обе строки; порядок задаёт агент.
5. В сводке ответа и в `context`: `summaryTokens`, `freshTokens`,
   `summarized: { sourceTokens, tokens, ratio } | null`. `totalTokens`
   сессии **включает** вызовы суммаризации: они стоили денег.

Текущий запрос пользователя частью истории не является и в сводку идёт
только со следующего запуска.

### 4. Ловушка роста сводки и её решение

При коэффициенте r = 0,75 и пороге N без учёта сводки каждая суммаризация
сжимает `S + N`: `S₁ = 0,75·N = 1500`, `S₂ = 0,75·(1500 + 2000) = 2625`,
`S₃ = 3469`, … Неподвижная точка `S* = r·N / (1 − r) = 3N = 6000` токенов —
вдвое больше окна 3000. Без потолка сводка за три цикла вытесняет из окна
сначала свежие реплики, потом саму себя, и память кончается там, где
должна была начаться.

**Правило:** сводке отводится то, что остаётся от окна после N свежих
реплик.

- `W` — действующее окно (`effectiveContext`, как сегодня).
- `N_eff = min(N, ⌊W / 2⌋)` — порог, который действует; показывается рядом
  с полем, как сегодня показывается действующее окно.
- `cap = W − N_eff` — потолок сводки в токенах.
- Целевой объём сводки = `min(⌈0,8 × source⌉, cap)`; он же —
  `answerTokens` вызова, жёсткий потолок. В промпт идёт целевой объём
  словами и просьба держать 70–80 %, когда потолок не мешает.

Следствие, которое надо принять осознанно: **при окне 3000 слабое сжатие
не выполняется** арифметически. `N_eff = 1500`, `cap = 1500`: первая сводка —
1200 из 1500 (80 %), вторая — 1500 из 2700 (56 %), дальше 1500 из 3000
(50 %) навсегда. «70–80 %» выполнимы, только если `cap ≥ S* = 3N`, то есть
`W ≥ 4N`: при N = 2000 — окно 8000, где сводка сходится к 6000 и держит
75 %. На Haiku это в пределах 40 % от 40 000
(16 000), на моделях Groq и ноутбуке окно 1720–2080 и сжатие будет сильным
при любом решении. Выбор окна дня 9 — вопрос 1 владельцу.

Рассмотренные варианты:

- **(а) Потолок сводки с принудительно более сильным сжатием** — принято,
  в форме `cap = W − N_eff`: число выводится из окна и N, а не задаётся
  отдельно, и свежие реплики до N всегда помещаются рядом со сводкой.
- **(б) 70–80 % только для новых реплик, старую сводку сильнее.**
  `S* = 0,75·N / (1 − r_old)`; чтобы уложиться в 1500 при N = 2000, нужно
  `r_old = 0` — сводку пришлось бы стирать. Не работает при этих числах.
- **(в) Считать сводку в N.** Сходится (`S = 0,75·N = 1500` постоянно), но
  свежим репликам остаётся 500 токенов, сводка делается через раз, и это
  противоречит заданию.
- **(г) Дать сводке расти до окна, дальше усечение.** Память исчезает после
  третьей суммаризации; это худший вариант.

### 5. Класс задачи роутера и потолок ответа

Владелец назвал класс `summarize`. Ярусы этого класса — `self-hosted` и
`cloud-frontier` (`router/config/classes.json`), а явный провайдер вне ярусов
класса получает отказ (`router/src/router.js`, «провайдер вне ярусов
класса»). Значит для пользователя, выбравшего модель Groq, сводка через
`summarize` не сделается; добавить `cloud-cheap` в `summarize` — открытое
решение владельца в `backlog.md` (уводит класс с Haiku для приложения
`smoke`), и решать его побочно здесь нельзя.

Предлагается **новый класс `dialog_summary`**: ярусы `self-hosted`,
`cloud-cheap`, `cloud-frontier`; `requires: text_generation`; `thinking:
none`; `answerTokens: 500`; `maxAnswerTokens: 6400` (0,8 × наибольшего N);
`dataClass: public`. Класс добавляется приложению `agents` в
`router/config/apps.json`. Вызов — с явным `provider` = модель чата, роутер
замену не подбирает (как для `news_answer`). Это две правки конфигурации
роутера без кода. Вопрос 2 владельцу.

### 7. Сравнение

Фиксированный сценарий: 10 реплик с фактами в начале (регион, компания,
формат ответа), затем три проверочных вопроса о ранних фактах («о чём я
спрашивал первым», «какую компанию я называл», «в каком формате просил»).
Три режима на Haiku, значения по умолчанию, кроме названных:

| Режим | Окно | N | Что проверяет |
|---|---:|---:|---|
| A. Полная история | 8000, сжатие выкл. | — | верхняя планка качества |
| B. Усечение (день 8) | как в дне 9, сжатие выкл. | — | что теряется сейчас |
| C. Сводка | как в дне 9 | 2000 | что даёт сжатие |

Оценивает человек: 9 ответов на проверочные вопросы, шкала
«помнит / частично / не помнит». Расход — три числа на режим: токены
диалоговой части (сводка + реплики) на сообщение, `usage.inputTokens`
на сообщение, сумма `totalTokens` сценария с вызовами суммаризации.
Результат — запись в `agent_docs/development-history/` с таблицей.

**Цена.** Сообщение на Haiku при умолчаниях дня 8 — ~$0,043
(ADR `2026-09-09-2134`). Вызов сводки: вход ~3700 (сводка + реплики +
промпт), выход до `cap` при слабом сжатии — 1500–2800 токенов по $5 за
миллион, то есть **$0,01–0,018 за сводку**: выход впятеро дороже входа, и
слабое сжатие делает сводку дорогой. Сценарий: 3 × 13 сообщений × $0,043 +
около четырёх сводок ≈ $1,75 — почти весь суточный бюджет приложения `agents` в
$2, общий с днями 6–8. Решение владельца: лимиты не трогать; упёрлись —
досчитываем на следующий день UTC.

### 9. Критерии приёмки

1. Запуск с `summarizeAt`: при `fresh ≥ N_eff` агент один раз зовёт роутер
   классом сводки с прежней сводкой и свежими репликами, сохраняет строку
   `summaries`, и `input` содержит `<summary>` → `<dialog>` только с
   репликами после `through_id` → `<request>`. Тест с поддельным роутером.
2. `answerTokens` вызова сводки = `min(⌈0,8 × source⌉, W − N_eff)`; в сводке
   ответа — фактический `ratio`; обрезание потолком — событие `warning`.
3. Без `summarizeAt` — поведение прежнее: тесты `agents/test/*` проходят без
   правок, `summaries` не пишется, `days/day7` и `days/day8` не тронуты.
4. `GET /v1/sessions/:id` отдаёт `summary`; `DELETE` и уборка удаляют её.
5. `totalTokens` сессии включает вызовы сводки.
6. Отказ вызова сводки: запуск завершается ответом по усечённому хвосту с
   `warning`; сводка в базе не меняется.
7. Страница: контрол N с проверкой на обеих сторонах, действующий порог и
   потолок, «в контексте X · сводка Y», блок сводки, событие сжатия.
8. Запись сравнения с таблицей трёх режимов по качеству и трём числам
   расхода существует.

## Обоснование

Параметр вместо новой версии агента — потому что поведение отличается
одним шагом, а реестр, промпт и инструменты те же; дни 6–8 остаются
байт в байт без ветвления по номеру дня. Потолок сводки выводится из окна
и N, а не задаётся третьим числом: тогда у страницы два контрола, а не
три, и свежие реплики до N всегда помещаются. Сводка до ответа в том же
запуске — один путь кода и честная задержка на экране; фоновая сводка
после ответа быстрее для пользователя, но экран и база расходились бы до
следующего сообщения. Новый класс роутера вместо `summarize` — чтобы не
решать попутно открытый вопрос о ярусе `cloud-cheap`.

## Последствия

- На Haiku день 9 **дороже** дня 8, а не дешевле: каждая сводка —
  $0,01–0,018 сверх сообщения, экономия входа — доли процента. Выигрыш —
  память за пределами окна, не деньги. Задание обещает экономию токенов;
  в записи сравнения это будет показано числами, а не сглажено.
- При окне 3000 сжатие в реальности сильное (50 % и ниже), вопреки выбору
  владельца «70–80 %». Слабое сжатие требует окна ≥ 4N; на Haiku окно 8000
  отнимает у подборки до ~12 статей из 40 и прибавляет до 8000 входных
  токенов (~$0,008) на сообщение.
- Сводка — пересказ моделью: факты могут искажаться, и искажение
  закрепляется в базе и наследуется всеми следующими сводками. Усечение
  теряло реплики целиком, но не переписывало их.
- Появляется второй вызов модели в запуске: задержка ответа растёт на
  2–5 с на Haiku и на минуты на ноутбуке при каждой суммаризации.
- Суточный бюджет `agents` общий с днями 6–8; сравнение дня 9 съедает его
  почти целиком, и в этот день дни 6–8 могут получить отказ по бюджету.
- Ещё одна таблица и ещё одно поле контракта запуска, которые сервис
  агентов обязан поддерживать для одного дня.
- Две правки конфигурации роутера (класс и разрешение приложению) —
  класс A с вето compliance.

## Альтернативы рассмотрены

- **Править день 8.** Отклонено владельцем: сданные дни не дорабатываются.
- **Сжатие до 20–30 % исходника.** Стандартное чтение «сжатия 70–80 %»,
  сводка сходится к `N/3 ≈ 670` токенов и помещается в любое окно; владелец
  выбрал слабое сжатие.
- **Сводка после ответа, в фоне.** Быстрее для пользователя, но два пути
  кода и рассинхрон экрана с базой до следующего сообщения.
- **Всегда Haiku для сводок.** Дёшево и предсказуемо, но ломает принцип
  явного выбора модели и тратит деньги за пользователя, выбравшего
  бесплатную модель.
- **Класс `news_answer` для сводок.** Ни одной правки роутера, но журнал
  расхода врал бы о назначении вызова.
- **Точный счёт `count_tokens`.** Лишний вызов на сообщение, только для
  Anthropic, а бюджет роутера всё равно считается оценкой.
- **Проверка объёма сводки и повтор.** Второй платный вызов ради
  процента; потолок `answerTokens` держит верхнюю границу бесплатно.

## Вопросы владельцу

1. **Окно дня 9.** (1) 3000 как страховка — тогда действующий порог 1500,
   потолок сводки 1500, и сжатие фактически 50 % и сильнее; (2) **8000 по
   умолчанию на дне 9** — «70–80 %» выполняются при N = 2000, цена
   ~$0,008 на сообщение и до 12 статей меньше в подборке на Haiku; на Groq
   и ноутбуке окно всё равно 1720–2080. Рекомендую (2): иначе выбранное
   слабое сжатие существует только в промпте.
2. **Класс роутера.** (1) `summarize`, как назвал владелец, — тогда сводка
   для моделей Groq невозможна, пока не решён вопрос о `cloud-cheap`;
   (2) **новый класс `dialog_summary`** со всеми тремя ярусами и
   `maxAnswerTokens: 6400`. Рекомендую (2).
3. **Показ сводки пользователю.** Допущение — свёрнутый блок в чате.
   Подтвердить или скрыть; без показа сравнение качества сжатия делается
   только по проверочным вопросам.
