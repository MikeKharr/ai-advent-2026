# [2026-09-11 16:08] День 9: сводка диалога вместо усечения — суммаризация при N токенов

Файл: `agent_docs/adr/2026-09-11-1608-day9-context-compression.md`

## Статус

Принято (решение владельца, 2026-09-11, PR #118).

Решения владельца от 2026-09-11, на которых стоит запись: новый `days/day9`
плюс сервис `agents/` за новым параметром запуска, дни 6–8 не меняются; N —
сумма токенов реплик после последней сводки, сама сводка в N не входит;
окно контекста 3000 остаётся страховкой, как в дне 8; N = 2000 по
умолчанию; сводка делается до ответа в том же запуске; сводка — часть
данных сессии, живёт и удаляется вместе с ней; сравнение прогоняется
полностью на Haiku без повышения лимитов.

Три поправки владельца при принятии, дословно: «summary должно занимать
20–30 % от N; при N 2000 токенов summary будет 400–600 токенов. Оставить N
по умолчанию 2000» — то есть 70–80 % из задания есть степень сжатия, а
размер сводки — 0,2–0,3 × N, а не 70–80 % исходника, как читал черновик;
«делай summary всегда Haiku 4.5» — независимо от модели чата; сводка
показывается пользователю свёрнутым блоком в чате. Вопросы черновика об
окне 8000 и о новом классе роутера этим закрыты.

## Контекст

Задание дня 9: хранить для сессии сводку (summary), при накоплении N токенов
новых реплик сжимать сводку и реплики в новую сводку, подставлять её в
запрос перед свежими репликами, показывать токены контекста и сводки,
дать контрол N, сравнить качество и расход с режимом без сжатия.

Что есть сейчас (ADR `2026-09-09-1906`, `2026-09-09-2134`):

- Переписка — SQLite на томе агента (`agents/src/sessions.js`). В модель
  уходит **хвост**: целые реплики от свежих к старым, пока помещаются в окно
  контекста; старое отбрасывается (`tail`, поле `dropped`).
- Окно = `min(заданное, 40 % предела входа модели)` (`agents/src/llm.js`,
  `effectiveContext`): на Haiku 3000 при заданных 3000, на Qwen 1720.
  «3000 токенов» из задания — умолчание `contextTokens` в реестре агента
  (`agents/config/agents.json`), не предел модели; страница дня 8 ставит 2000.
- Токены реплик уже лежат в базе: реплика пользователя — оценка той же
  формулой, что у роутера; реплика агента — `usage.outputTokens` провайдера.
  `count_tokens` не используется, и вводить его незачем: роутер считает
  бюджет оценкой, точный счёт дал бы лишний вызов на каждое сообщение.
- Запрос к роутеру — две строки, `system` и `input`; диалог — размеченный
  блок `<dialog>` внутри `input` перед `<request>` и `<candidates>`
  (`buildInput`).

**Экономии токенов на Haiku почти не будет.** Подборка статей занимает
90 %+ входа: в живом замере дня 8 контекст 362 из 26 265 токенов, при
полном окне — 3000 из ~28 000. Даже сжав диалог впятеро, сэкономить можно
единицы процентов входа, и это стоит отдельного вызова модели; в деньгах
на Haiku итог отрицательный. Ценность сводки — **память**: сейчас реплики за окном
отбрасываются молча, со сводкой они остаются в сжатом виде. На малых
моделях (Groq, ноутбук; окно 1720–2080) диалог занимает до 40 % входа, и
там сводка держит память заметно дольше, но деньги там и так почти нулевые.
Сравнение «до/после» поэтому меряется **отдельно по диалоговой части и по
полному запросу**, иначе результат — ноль по построению.

## Решение

### 1. Параметр запуска `summarizeAt`, дни 6–8 не меняются

Новое необязательное поле входа `summarizeAt` — целое, порог N. Без поля
агент ведёт себя как сегодня, байт в байт: таблица сводок не читается и не
пишется, `input` собирается прежним `buildInput`. Дни 6–8 поле не
присылают. Проверка на границе (`params.js`): 500 ≤ N ≤ 8000 и N меньше
заданного окна `contextTokens`.

### 2. Сводка — строка в базе сессии

```sql
CREATE TABLE IF NOT EXISTS summaries (
  session_id    TEXT PRIMARY KEY,
  text          TEXT NOT NULL,
  tokens        INTEGER NOT NULL,   -- usage.outputTokens вызова сводки
  source_tokens INTEGER NOT NULL,   -- прежняя сводка + реплики, что вошли
  through_id    INTEGER NOT NULL,   -- последняя реплика, вошедшая в сводку
  model         TEXT,
  updated_at    INTEGER NOT NULL
);
```

Одна строка на сессию, перезаписывается при каждой суммаризации. Удаляется
в `clear` вместе с сообщениями и, значит, уборкой по сроку (30 часов).
Отдельного решения о хранении нет: сводка — операция над уже хранимым
контекстом сессии (владелец, 2026-09-11). Поставщику ничего нового не
уходит: тексты реплик и так уходят ему при каждом сообщении.

«Свежие реплики» — сообщения с `id > through_id` без записей об ошибках.
`GET /v1/sessions/:id` отдаёт `summary: { text, tokens, sourceTokens,
updatedAt }` или `null`.

Сводка видна пользователю — свёрнутый блок «Сводка разговора» в чате дня 9
над свежими репликами (решение владельца, 2026-09-11). Без этого
сравнивать качество сжатия было бы нечем.

### 3. Порядок запуска

До обращения к архиву (память поднимается раньше подборки с дня 8):

1. Поднять сводку и свежие реплики; посчитать `fresh` — сумму их `tokens`.
2. Если `fresh ≥ N` — суммаризация: один вызов роутера классом `summarize`
   к Haiku с прежней сводкой и свежими репликами; результат — новая сводка,
   `through_id` — последняя из вошедших реплик; `fresh` становится пустым.
   События `llm_call` / `llm_result` с классом `summarize` и провайдером
   `anthropic-haiku`, затем `planning` «Сжал историю: A → B токенов (C %)».
   Один вызов на запуск.
3. Отказ суммаризации (роутер, бюджет, обрыв) запуск **не валит**: сводка
   остаётся прежней, свежие реплики идут хвостом как сегодня, событие
   `warning` «Историю не сжал». Вызов, дошедший до провайдера, считается
   оплаченным.
4. `input`: тема → блок `<summary>` с пометкой «сводка прежней части этого
   разговора» → `<dialog>` со свежими репликами → `<request>` →
   `<candidates>`. Хронология: сначала что было до, потом что говорили
   после, потом что спрашивают сейчас. В контракте роутера «системный блок
   или первое сообщение» неразличимы — обе строки; порядок задаёт агент.
5. В сводке ответа и в `context`: `summaryTokens`, `freshTokens`,
   `summarized: { sourceTokens, tokens, ratio } | null`. `totalTokens`
   сессии **включает** вызовы суммаризации: они стоили денег.

Текущий запрос пользователя частью истории не является и в сводку идёт
только со следующего запуска.

### 4. Размер сводки и почему она не растёт

Размер сводки задаётся от N, а не от исходника: целевой объём в промпте —
0,2–0,3 × N словами, жёсткий потолок `answerTokens = ⌈0,3 × N⌉`. При
N = 2000 это 400–600 токенов; исходник каждой суммаризации — прежняя
сводка плюс свежие реплики, около 2600 токенов, и степень сжатия выходит
75–85 % — те самые «70–80 %» задания.

Роста нет по построению: сводка любого поколения не больше 0,3 × N, и
сводка со свежими репликами занимают не больше 1,3 × N = 2600 токенов —
помещаются в окно 3000 без потолков и пересчётов. Проверка одна: N не
больше заданного окна `contextTokens` (сервер и форма). На моделях с
меньшим окном (Groq, ноутбук: 1720–2080) окно по-прежнему страховка —
самые старые свежие реплики могут выпасть из запроса раньше, чем `fresh`
дойдёт до N; они не потеряны, они войдут в следующую сводку.

Черновик записи читал «70–80 %» как размер сводки от исходника; при таком
чтении сводка сходилась к `r·N / (1 − r) = 3N = 6000` токенов — вдвое
больше окна — и требовала потолка с принудительным сжатием, действующего
порога `N_eff = min(N, ⌊W/2⌋)` и окна 8000. Варианты (а) потолок сводки,
(б) сильнее сжимать только старую сводку, (в) считать сводку в N, (г) дать
расти до окна — **сняты решением владельца** о размере 0,2–0,3 × N.

### 5. Сводку делает всегда Haiku 4.5 классом `summarize`

Решение владельца: сводка — всегда Anthropic Haiku 4.5, какую бы модель
пользователь ни выбрал для чата. Вызов идёт существующим классом
`summarize` с явным `provider: anthropic-haiku`: ярусы класса —
`self-hosted` и `cloud-frontier` (`router/config/classes.json`), Haiku —
`cloud-frontier`, явный провайдер в ярусе класса проходит, и роутер замену
не подбирает (как для `news_answer`). Политика яруса `self-hosted` впереди
облака на явный провайдер не действует, поэтому ноутбук сводки не получит.

Две правки конфигурации роутера без кода: `summarize` добавляется в
`classes` приложения `agents` в `router/config/apps.json` (сейчас там
только `news_answer`); у класса `summarize` появляется `maxAnswerTokens:
2400` — 0,3 × наибольшего N (8000); без него потолок класса равен
умолчанию 500 и `answerTokens = 600` при N = 2000 получит отказ.

### 6. Страница дня 9

Копия дня 8 с изменениями: контрол N (число, 500–8000, шаг 100, умолчание

### 7. Сравнение

Фиксированный сценарий: 10 реплик с фактами в начале (регион, компания,
формат ответа), затем три проверочных вопроса о ранних фактах («о чём я
спрашивал первым», «какую компанию я называл», «в каком формате просил»).
Три режима на Haiku, значения по умолчанию, кроме названных:

| Режим | Окно | N | Что проверяет |
|---|---:|---:|---|
| A. Полная история | 8000, сжатие выкл. | — | верхняя планка качества |
| B. Усечение (день 8) | как в дне 9, сжатие выкл. | — | что теряется сейчас |
| C. Сводка | как в дне 9 | 2000 | что даёт сжатие |

Оценивает человек: 9 ответов на проверочные вопросы, шкала
«помнит / частично / не помнит». Расход — три числа на режим: токены
диалоговой части (сводка + реплики) на сообщение, `usage.inputTokens`
на сообщение, сумма `totalTokens` сценария с вызовами суммаризации.
Результат — запись в `agent_docs/development-history/` с таблицей.

**Цена.** Сообщение на Haiku при умолчаниях дня 8 — ~$0,043
(ADR `2026-09-09-2134`). Вызов сводки на Haiku: вход ~2800 (сводка до 600 +
реплики ~2000 + промпт) по $1 за миллион, выход до 600 по $5 за миллион —
**около $0,006 за сводку**, примерно седьмая часть сообщения. Сценарий:
3 × 13 сообщений × $0,043 + около четырёх сводок ≈ $1,70 — почти весь
суточный бюджет приложения `agents` в $2, общий с днями 6–8. Решение владельца: лимиты не трогать; упёрлись —
досчитываем на следующий день UTC.

### 9. Критерии приёмки

1. Запуск с `summarizeAt`: при `fresh ≥ N` агент один раз зовёт роутер
   классом `summarize` с `provider: anthropic-haiku` независимо от модели
   чата, с прежней сводкой и свежими репликами, сохраняет строку
   `summaries`, и `input` содержит `<summary>` → `<dialog>` только с
   репликами после `through_id` → `<request>`. Тест с поддельным роутером.
2. `answerTokens` вызова сводки = `⌈0,3 × N⌉` (600 при N = 2000); в сводке
   ответа — фактический `ratio`; обрезание потолком — событие `warning`.
3. Без `summarizeAt` — поведение прежнее: тесты `agents/test/*` проходят без
   правок, `summaries` не пишется, `days/day7` и `days/day8` не тронуты.
4. `GET /v1/sessions/:id` отдаёт `summary`; `DELETE` и уборка удаляют её.
5. `totalTokens` сессии включает вызовы сводки.
6. Отказ вызова сводки: запуск завершается ответом по усечённому хвосту с
   `warning`; сводка в базе не меняется.
7. Страница: контрол N с проверкой на обеих сторонах, действующий порог и
   потолок, «в контексте X · сводка Y», блок сводки, событие сжатия.
8. Запись сравнения с таблицей трёх режимов по качеству и трём числам
   расхода существует.

## Обоснование

Параметр вместо новой версии агента — потому что поведение отличается
одним шагом, а реестр, промпт и инструменты те же; дни 6–8 остаются
байт в байт без ветвления по номеру дня. Размер сводки от N, а не от
исходника, — единственное чтение, при котором сводка не растёт и у
страницы два контрола, а не три. Сводка до ответа в том же запуске — один
путь кода и честная задержка на экране; фоновая сводка после ответа
быстрее для пользователя, но экран и база расходились бы до следующего
сообщения. Всегда Haiku — предсказуемое качество пересказа и секунды
вместо минут на ноутбуке; цена сводки при этом на порядок меньше цены
сообщения.

## Последствия

- На Haiku день 9 **дороже** дня 8, а не дешевле: каждая сводка — ~$0,006
  сверх сообщения, экономия входа — единицы процентов. Выигрыш — память за
  пределами окна, не деньги. Задание обещает экономию токенов; в записи
  сравнения это будет показано числами, а не сглажено.
- Сводка в 400–600 токенов из ~2600 — пересказ моделью с потерей деталей:
  факты могут искажаться, и искажение закрепляется в базе и наследуется
  всеми следующими сводками. Усечение теряло реплики целиком, но не
  переписывало их.
- Пользователь, выбравший бесплатную модель Groq или ноутбук, всё равно
  тратит деньги Anthropic на каждую сводку, и его реплики уходят
  поставщику, которого он для чата не выбирал. Данные те же, что и так
  уходят Haiku по умолчанию, но принцип явного выбора модели
  (ADR `2026-09-08-1824`) для сводки не действует.
- Появляется второй вызов модели в запуске: задержка ответа растёт на
  2–4 с при каждой суммаризации.
- Суточный бюджет `agents` общий с днями 6–8; сравнение дня 9 съедает его
  почти целиком, и в этот день дни 6–8 могут получить отказ по бюджету.
- Ещё одна таблица и ещё одно поле контракта запуска, которые сервис
  агентов обязан поддерживать для одного дня.
- Две правки конфигурации роутера (`maxAnswerTokens` класса `summarize` и
  разрешение класса приложению `agents`) — класс A с вето compliance.
  Потолок 2400 у класса общий: приложение `smoke` тоже сможет попросить
  до 2400 токенов ответа в этом классе.

## Альтернативы рассмотрены

- **Править день 8.** Отклонено владельцем: сданные дни не дорабатываются.
- **Сводка 70–80 % исходника.** Чтение черновика; сводка растёт к 3N и
  требует потолка и окна 8000. Снято поправкой владельца: 70–80 % — степень
  сжатия, размер — 0,2–0,3 × N.
- **Сводка после ответа, в фоне.** Быстрее для пользователя, но два пути
  кода и рассинхрон экрана с базой до следующего сообщения.
- **Та же модель, что в чате, для сводок.** Держит принцип явного выбора
  модели, но класс `summarize` не пускает ярус `cloud-cheap` (модели Groq),
  а ноутбук делал бы сводку минутами. Владелец выбрал всегда Haiku.
- **Новый класс роутера `dialog_summary` со всеми ярусами.** Нужен был
  только при «той же модели»; с Haiku хватает существующего `summarize`.
- **Класс `news_answer` для сводок.** Ни одной правки роутера, но журнал
  расхода врал бы о назначении вызова.
- **Точный счёт `count_tokens`.** Лишний вызов на сообщение, только для
  Anthropic, а бюджет роутера всё равно считается оценкой.
- **Проверка объёма сводки и повтор.** Второй платный вызов ради
  процента; потолок `answerTokens` держит верхнюю границу бесплатно.
