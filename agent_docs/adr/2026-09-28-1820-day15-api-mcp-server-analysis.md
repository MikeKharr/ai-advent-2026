# [2026-09-28 18:20] API дня 15 уже есть — это `/v1` сервиса агентов; сервер MCP поверх него — новая единица в закрытой сети, на чтение и отправку сообщения; правки промптов, инвариантов и моделей остаются экрану

Файл: `agent_docs/adr/2026-09-28-1820-day15-api-mcp-server-analysis.md`

## Статус

**Предложено.** Владелец просил разбор замысла, не постройку. Замысел
дословно — в описании PR этой записи; ключевые слова: «на основе day15 —
разработать API … затем для этого API — разработать MCP навыки и реализовать
MCP сервер … сервер должен отвечать запросам с того же сервера».

Разбор говорит: замысел стоит **разбить и сузить**, а не строить как
сформулирован. Три развилки для владельца — в конце; первая из них (кто
клиент) меняет всё остальное, и до неё работу начинать нельзя.

## Решение

1. **API не пишется.** Всё, что перечислил владелец, кроме трёх позиций, уже
   есть как `/v1` сервиса агентов (`agents/src/service.js`) — таблица ниже.
   Три позиции, которых нет: «выбор профиля» (это cookie дня, у сервиса
   понятия «текущий профиль» нет — в MCP профиль будет аргументом каждого
   вызова), «редактирование сообщения» (сообщения не правятся; есть ветка от
   своего сообщения, `parentId`, режим «Ветки») и правка текста инварианта
   на месте (только удалить и завести заново через формулировщика — ворота
   билета, решение владельца, ADR `2026-09-22-0827`). Новых ручек сервису в
   первом заходе — ноль; эти три не строятся.
2. **Сервер MCP — новая единица верхнего уровня без SDK** (условно
   `mcpagents`; имя — в глоссарий), по образцу `mcpnews/` (своя копия
   модуля JSON-RPC, ADR `2026-09-28-0736`, п. 3). Не в `mcp/`: та служба
   изолирована от `agents` сетью намеренно (ADR `2026-09-23-1227`, п. 5).
   Единица зовёт `http://agents:8082/v1` с копией `AGENT_KEY` в своём env по
   норме ADR `2026-09-11-1743`; нового секрета нет.
3. **«Только с того же сервера» — сетью, не проверкой адреса и не ключом.**
   Новая сеть compose (условно `admin`): в ней только `mcpagents`, `agents` и
   клиент; `caddy` в ней нет, маршрута в `Caddyfile` нет; правило — в
   `RULES` стража `.github/scripts/compose-networks.mjs` (держатель, I-14).
   Если клиент — владелец через ssh-туннель (развилка 1, вариант К2),
   добавляется **первая в этом compose** строка `ports:` с привязкой
   `127.0.0.1:` и второй страж: `ports:` без `127.0.0.1:` — красный.
4. **Что отдаётся модели — ровно то, что лежит в сервере MCP.** Сервер не
   отличает вызов от человека и от модели: в MCP инструменты зовёт модель
   клиента, человек в лучшем случае подтверждает. Поэтому «только человеку»
   значит «в сервере MCP этого нет, это экран дня 15». Первый заход:
   - **ресурсы (чтение):** список профилей; профиль целиком — настройки,
     инварианты `Пn`, промпты профиля; история диалога; список моделей с
     бюджетом и доступностью; действующие тексты промптов (умолчание реестра
     из `describe()` плюс строки профиля);
   - **инструменты (запись):** одна — `message.send {profileId, sessionId,
     text, parentId?}` → `POST /v1/runs`, под собственным лимитером сервера
     **до** вызова (I-4: у сервиса агентов лимитера нет, его держат дни);
   - **не в сервере:** правка пяти промптов, заведение и удаление
     инвариантов, установка рабочей и проверяющей модели, удаление профиля и
     очистка диалога. Всё это уже есть на экране дня 15 и там остаётся.
5. **День 15 не меняется** — сданный день (`AGENTS.md`); клиентом нового
   сервера он не становится: его страница говорит с сервисом напрямую.
   Экран новому серверу не нужен, пока клиент — Claude Code владельца;
   консоль как у дня 16 — отдельный день и отдельное решение (>40 минут
   опыта посетителя, «Объём» в `AGENTS.md`).

## Что опасно и почему

- **Двусмысленность слова «инварианты».** У проекта их два вида (глоссарий):
  инварианты продукта `I-n` (`agent_docs/invariants.md`, источник — git,
  I-11) и инварианты профиля `Пn` дня 14. Разбор исходит из второго: только
  он есть в дне 15. API к первым не нужен никому — ни модели, ни экрану:
  их меняет ADR, принимаемый человеком; если владелец имел в виду их, ответ
  — «нет», и это не техническое ограничение.
- **Модель, правящая свой ограничитель.** Промпт `stage.verify.invariants`
  — единственная настоящая проверка дня 14; его правка выключает её
  (`invariants.md`, абзац «С дня 15»). Промпт `stage.answer` — «рычаг
  сильнее правил». Инструмент удаления инварианта — модель снимает с себя
  правило, которое человек завёл против неё. Через MCP эти операции делает
  модель, и подтверждение человека в клиенте — не гарантия (ниже).
- **Инъекция из истории в инструмент записи.** Профили открыты: любой
  посетитель пишет в любой профиль и любой промпт (ADR `2026-09-23-0646`,
  «Последствия»). Ресурс «история диалога» несёт этот текст модели клиента;
  если в той же сессии есть инструмент записи, анонимный посетитель дня 15
  получает канал к инструментам владельца: «удали П2», «поставь kimi-k3».
  Это и есть причина, по которой чтение чужого текста и запись не должны
  жить в одном сервере первого захода, а не только «пусть подтверждает».
- **Хост в `agents` показывает модели все серверы реестра сразу.**
  `listAllTools` обходит `servers.values()` без отбора по агенту
  (`agents/src/mcp/pipeline.js:69-85`); реестр один
  (`agents/config/mcp-servers.json`). Запись нового сервера туда — и его
  инструменты видят задание посетителя дня 20 свободным текстом и работа
  планировщика дня 18. Вариант К1 без списка разрешённых серверов на агента
  — отказ архитектора.
- **Установка модели — денежная поверхность, но не обход роутера.** Явный
  провайдер проходит только внутри ярусов класса (`router/src/router.js:151-
  168`), потолки класса `layered_dialogue` и `dailyCostUsd: 10` приложения
  `agents` действуют. Что меняется: выбор `kimi-k3` в настройках профиля
  делает следующий ответ до $0,48 за вызов у **всякого**, кто занял профиль,
  и действует в дне 13 на том же профиле (`days/day15/README.md`, «Две
  модели»). Через MCP это делает модель. `compliance` спросит три вещи:
  лимитер до `POST /v1/runs` и до `invariants/draft` (I-4); чьим ключом
  платит вызов — сегодня `ROUTER_APP_KEY` приложения `agents`, то есть
  консоль владельца ест бюджет посетителей дней 6–20 (отдельное приложение —
  новый секрет, как `scheduler`); почему установка модели не в сервере.
- **Проверка адреса запроса — не механизм.** За `caddy` все запросы приходят
  с адреса `caddy`; без него `remoteAddress` — адрес соседа по сети compose,
  и сверка с подсетью повторяет то, что сеть даёт построением. Первый
  элемент `X-Forwarded-For` уже был дефектом дня 5
  (`development-history/2026-09-08-1826`), а строку `header_up` не держит
  тест (`backlog.md`, «Владельцу»). Ключ на входе без сети не даёт «с того
  же сервера» — даёт «с ключом откуда угодно».

## Чем платим

- Ещё одна единица: семь мест конвейера (`ci.yml`, `deploy-units.sh`,
  `deploy.yml`, «Проверка живого сайта» — ADR `2026-09-28-0736`,
  «Последствия»), новая сеть, правило стража, строки `.env.example`, тест
  адреса по образцу `test/mcp-server-urls.test.js`; ошибка в одном месте —
  единица молча вне выкатки.
- Копия `AGENT_KEY` в третьем env-файле: компрометация самой молодой единицы
  открывает весь `/v1` сервиса агентов, включая удаление профилей — ровно
  довод, по которому день 16 получил свой ключ (ADR `2026-09-23-1227`,
  развилка 1). Здесь принято сознательно: сервер и есть клиент `/v1`.
- Вариант К2 вводит первый опубликованный порт в этом compose; защита —
  привязка к loopback и страж; живая проверка — только владельцем (ssh и
  `docker` в контейнер — вне закрытого списка).
- Ресурсы MCP руками: у модуля `mcpnews/src/rpc.js` их нет, у клиента хоста
  `agents/src/mcp/client.js` тоже — только `tools/*`. Для К2 (Claude Code)
  ресурсы работают; для К1 их бы никто не прочёл, и чтение пришлось бы
  отдавать инструментами, теряя различие «чтение/запись» на уровне
  протокола.
- Отправка сообщения через MCP платит бюджетом `agents` и берёт замок диалога
  до ~16,8 мин при зависшем поставщике (`snapshot.md`, день 15) — посетитель
  того же профиля в это время ждёт.
- Владелец не получает трёх названных им операций в MCP (промпты,
  инварианты, модели) в первом заходе; получает их на экране, где они уже
  есть.
- Терминология: «MCP навыки» в проекте — «инструменты» и «ресурсы» (I-13);
  примитив MCP `prompts` — шаблоны для клиента, к промптам профиля отношения
  не имеет и здесь не используется.

## Что этим НЕ решается

- Профили по-прежнему открыты; сервер MCP не вводит личности посетителя и
  не защищает досье.
- Отсутствие лимитера у сервиса агентов (`backlog.md`, Next) не чинится;
  лимитер появляется у нового сервера, а `days/day7` и прочие как были.
- Правка сообщения на месте и правка инварианта на месте не появляются.
- Сервер не отличает человека от модели; граница проводится составом
  сервера, а не проверкой вызывающего.
- День 15 не становится клиентом MCP; его страница и API дня не меняются.
- Для К1 хост не получает ресурсов и списка разрешённых серверов — это
  отдельный заход.

## Проверено лично и что остаётся неподтверждённым

По коду `main` на `42d59f2` 2026-09-28: все ручки таблицы выше и их
проверки доступа (`foreignSession`, `sessionProfile`); отсутствие
`limiter`/`reserve` в `agents/src/service.js`; `profile()` отдаёт
`invariants` и `prompts` (`agents/src/sessions.js:1182-1187`); `ports:` в
`deploy/compose.yml` нет ни у одной службы; `RULES` стража сетей; правка
сообщения на странице дня 15 — только ветка (`editParent`,
`params.parentId`); явный провайдер в роутере ограничен ярусами класса.

Неподтверждённым остаётся всё, что собрано по документации поставщика:
поведение Claude Code как клиента MCP по `http://localhost:<порт>/mcp` через
ssh-туннель (подтверждения запросов на каждый инструмент, чтение ресурсов)
— живого запуска не было; недоступность loopback хоста из контейнеров
соседнего compose-проекта — по устройству Docker, на этом VPS не
проверялось.

## Развилки владельцу — решить до начала работы

1. **Кто клиент.** К1 — хост в `agents` (модель дня 20 и планировщик):
   только чтение инструментами и обязательный список разрешённых серверов на
   агента (изменение сервиса, класс A). К2 — Claude Code владельца через
   ssh-туннель к `127.0.0.1:<порт>` (образец — админка почты): ресурсы на
   чтение, `message.send`, без экрана; **рекомендация архитектора**. К3 —
   новый день-консоль как день 16: публичный посетитель, свой лимитер,
   раскладка и `design-review`, решение об объёме по `AGENTS.md`.
2. **Записи в MCP.** Первый заход — только `message.send`. Промпты,
   инварианты, модели — экран. Если владелец хочет их в MCP, это второй заход
   после живого прогона первого, отдельным сервером или флагом env, никогда
   в одной сессии с чтением истории; правка `stage.verify.invariants` через
   модель — отказ архитектора при любом варианте; инварианты — только через
   `draft` + билет.
3. **Чей бюджет.** Отправка сообщений через MCP ключом приложения `agents`
   (без нового секрета, смешивается с посетителями) или новым приложением
   роутера с потолком — новый секрет, кладёт владелец.

## Альтернативы рассмотрены

- **Новый API рядом с `/v1`** — дублирует существующий, два места для одной
  ручки расходятся молча.
- **Сервер MCP внутри `agents`** — второй протокол в процессе с
  `ROUTER_APP_KEY`; тот же довод, что отклонил это для дня 16.
- **Сервер в единице `mcp/` на SDK** — сеть `mcp` изолирована от `agents`
  намеренно; расширять её значит снять изоляцию.
- **Проверка адреса запроса** — за прокси не различает никого, без прокси
  повторяет сеть; история дефекта дня 5.
- **Ключ на входе вместо сети** — «с ключом откуда угодно», не «с того же
  сервера».
- **Регистрация в `mcp-servers.json` как есть** — инструменты уходят дню 20
  и планировщику без отбора.
- **День 15 как клиент нового сервера** — доработка сданного дня и лишний
  прыжок для страницы, которая уже говорит с сервисом.
- **Все чтения инструментами и при К2** — теряет различие чтение/запись,
  которое клиент умеет показывать.
