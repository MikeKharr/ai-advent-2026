# [2026-09-28 18:20] Поверхность управления инструментами агентов: отдельный API с перечнем операций и отказом по умолчанию, сервер MCP над ним в закрытой сети, клиент — код новых дней

Файл: `agent_docs/adr/2026-09-28-1820-day15-api-mcp-server-analysis.md`

## Статус

**Предложено.** Вторая редакция того же дня после двух решений владельца
по первой: (1) **отдельный API для MCP нужен** — «это делается для управления
инструментами агентов — там должен быть принципиально другой подход к
безопасности и работе»; вывод первой редакции «API не пишется, обернуть
`/v1`» отклонён; (2) **клиент — приложения новых дней**, то есть код дня, а
не модель и не Claude Code владельца. Замысел владельца дословно — в описании
PR #249. Что изменилось против первой редакции — по ходу текста помечено
«было:».

Не оспорено и остаётся: «с того же сервера» — сетью, не проверкой адреса и
не ключом; правка проверяющего промпта через модель не проектируется.

## Решение

1. **Поверхность управления — второй слушатель процесса `agents`**
   (`agents/src/control/`, порт 8086, свой ключ `CONTROL_KEY`), не путь
   внутри `/v1` и не обёртка над ним. Было: обернуть `/v1`. Почему второй
   слушатель, а не отдельная единица: данные — SQLite на томе `agents_data`,
   делить файл базы между контейнерами нельзя; почему не в `/v1`: у него
   разрешение по умолчанию «всё под `AGENT_KEY`», и одна поверхность не
   может иметь два режима отказа. Порт виден во всех сетях `agents` — это
   закрывает ключ, а не сеть: `CONTROL_KEY` не лежит ни в одном `dayN.env`,
   `AGENT_KEY` — не у сервера MCP; поверхности не пересекаются ключами.
2. **Что значит «другой подход к безопасности» — шесть свойств, каждое с
   держателем (I-14):**
   - *отказ по умолчанию:* диспетчер — таблица операций; путь, метод или
     имя вне таблицы — один и тот же 404 без проброса в `/v1`; держит тест
     «операция вне перечня — 404, обработчик `/v1` не вызван»;
   - *операции названы перечислением:* закрытый список в
     `agents/src/control/ops.js` — имя, вид (чтение/запись), признак «платная»,
     схема аргументов, что под ней в `/v1`/`sessions`; новая операция — строка
     в ADR и PR класса A, а не «раз есть в `/v1`»;
   - *своя проверка каждого аргумента на границе, без доверия вызывающему:*
     сервер MCP — сосед по сети, не доверенная сторона; `profileId`,
     `sessionId`, `promptId`, `num`, тексты и билет проверяются здесь теми же
     разборщиками домена (`parsePrompt`, `parseSettings`, `checkTicket`) и
     проверкой «диалог принадлежит профилю» — до обращения к хранилищу;
     держит негативный тест на каждую операцию;
   - *свой учёт:* таблица `control_log (at, op, profile_id, outcome, ms,
     paid)` в SQLite `agents` — без текстов, без адресов (I-10), срок 30 дней
     уборкой; строка журнала процесса на каждый вызов;
   - *свой лимитер до платной операции:* окно на весь ключ (клиент один, адреса
     посетителя у поверхности нет намеренно — как у службы `mcp`,
     `backlog.md`) и суточный потолок `CONTROL_MAX_DAILY_CALLS`; отказ — до
     `createRun` и до формулировщика (I-4); держит тест «без слота — 429,
     роутер не вызван»;
   - *свой ответ:* поверхность собирает свой JSON из названных полей, не
     проксирует тела `/v1` (образец — ADR `2026-09-23-1227`, п. 5); ключей
     и адресов в ответах нет (тест I-1 по образцу дня 16).
3. **Сервер MCP — новая единица `mcpagents` без SDK** (имя условное, в
   глоссарий), копия модуля JSON-RPC `mcpnews/src/rpc.js` плюс `resources/list`
   и `resources/read` (в модуле их нет — проверено). Чтения — **ресурсы**
   (`profiles`, `profile/{id}`, `history/{profileId}/{sessionId}`, `models`,
   `prompts/{profileId}`), записи — **инструменты**. Зовёт
   `http://agents:8086` с `CONTROL_KEY`. Примитив MCP `prompts` (шаблоны
   клиента) не используется — к промптам профиля отношения не имеет (I-13:
   «MCP навыки» в проекте — инструменты и ресурсы).
4. **Клиент — код дня, прямым JSON-RPC, как консоль дня 16**
   (`days/day16/server.js:145`), **не через хост в `agents` и не в
   `mcp-servers.json`.** Было: развилка К1/К2/К3. Реестр хоста один и
   отбора по агенту нет (`agents/src/mcp/pipeline.js:69-85`); запись
   `mcpagents` туда отдала бы операции управления заданию посетителя дня 20
   и планировщику дня 18. Держит тест «`mcp-servers.json` не содержит
   `mcpagents`» — сетью это не закрыть: `agents` в сети `control` по п. 5.
5. **Сеть `control`: `agents`, `mcpagents`, дни-клиенты.** Сеть `tools` не
   годится: её правило `only: [mcpnews, mcpstore]`, и день в ней получил бы
   прямой путь к `mcpnews`/`mcpstore` мимо хоста и трейса. `mcpagents` —
   только в `control`; `caddy` — нет; маршрута в `Caddyfile` нет; `ports:`
   нет. Правило в `RULES` стража `compose-networks.mjs`. Проверка адреса
   запроса отвергнута по-прежнему: за `caddy` все запросы с одного адреса,
   без него `remoteAddress` повторяет сеть; первый элемент `X-Forwarded-For`
   уже был дефектом дня 5 (`development-history/2026-09-08-1826`).
6. **Перечень операций первого дня** — по списку владельца, каждая с тем, что
   под ней (таблица «Что уже есть» ниже — карта, не контракт):

   | Операция | Вид | Платная | Под ней |
   |---|---|---|---|
   | `profiles` | ресурс | нет | `sessions.profiles()` |
   | `profile/{id}` — настройки, `Пn`, промпты профиля | ресурс | нет | `sessions.profile()` |
   | `history/{profileId}/{sessionId}` | ресурс | нет | `sessions.history()` с проверкой принадлежности |
   | `models` | ресурс | нет | `describe().models` |
   | `prompts/{profileId}` — действующие тексты: умолчание реестра ⊕ профиль | ресурс | нет | `describe().stages` + `profile().prompts` |
   | `message.send {profileId, sessionId, text, parentId?}` | инструмент | да | `createRun` агента `prompt-agent` |
   | `prompt.set {profileId, promptId, text}`, `prompt.reset` | инструмент | нет | `savePrompt`/`deletePrompt` |
   | `invariant.draft {profileId, text}` | инструмент | да | `invariants.draft` |
   | `invariant.accept {profileId, text, ticket}` | инструмент | нет | `invariants.accept` — ворота билета не обходятся |
   | `invariant.delete {profileId, num}` | инструмент | нет | `deleteInvariant` |
   | `models.set {profileId, model?, reviewModel?}` | инструмент | нет | `saveStagedSettings` под `parseSettings` |

   Нет в перечне и не появится «потому что есть»: создание и удаление профиля,
   очистка диалога, переключение головы ветки, журнал CSV, тексты промптов
   запусков, ручки планировщика. «Выбор профиля» — состояние клиента (cookie
   дня), у поверхности его нет: профиль — аргумент каждого вызова.
   «Редактирование сообщения» — ветка `parentId` в `message.send`, правки на
   месте нет. Правка инварианта на месте — нет: `delete` + `draft` + `accept`.
7. **День 15 не меняется** и клиентом не становится (сданный день). Клиент —
   новый день, номер по заданию; его экран — раскладка и `design-review`.

## Что уже есть — карта того, что новый API делает под собой

| Позиция владельца | Сегодня | Где |
|---|---|---|
| просмотр профилей | есть | `GET /v1/profiles` |
| выбор профиля | cookie `day15_pid` дня; у сервиса нет | `days/day15/server.js:32` |
| редактирование сообщения | нет; ветка `parentId` в режиме «Ветки» | `days/day15/public/index.html:5139-5348` |
| редактирование промптов | есть, 5 идентификаторов | `PUT/DELETE /v1/profiles/:id/prompts/:promptId` |
| редактирование инвариантов | заведение через билет и удаление; правки на месте нет | `POST …/invariants/draft`, `POST …/invariants`, `DELETE …/invariants/:num` |
| текущие промпты и инварианты | есть | `GET /v1/agents` (`describe()`, `staged.js:364`), `GET /v1/profiles/:id` |
| история сообщений | есть | `GET /v1/sessions/:id?profile=` |
| установка основной и проверочной модели | есть, поле настроек профиля | `PUT /v1/profiles/:id/settings?agent=prompt-agent` |
| список моделей | есть | `models` в `describe()` (`LAYERED_MODELS`) |

Всё под `AGENT_KEY`, без публичного маршрута, в сети `default`. Поверхность
управления зовёт не эти ручки по HTTP, а те же функции хранилища и агента
изнутри процесса — иначе `CONTROL_KEY` пришлось бы дополнять `AGENT_KEY`, и
разделение ключей исчезло бы.

## Что опасно и почему — заново, для клиента-кода

- **Инъекция из истории снимается на этом пути и возвращается на любом
  другом.** Было: текст посетителя из ресурса «история» попадал модели
  клиента рядом с инструментом записи. Код дня вызывает инструменты
  детерминированно, модели текст не показывает — канала нет. Он появляется
  в тот момент, когда какой-то день отдаст ресурсы этой поверхности модели
  (через хост или свой цикл): тогда п. 4 (не в реестре) и правило «модель не
  получает `prompt.set`/`invariant.delete`» — обязательны. Правка
  `stage.verify.invariants` через модель не проектируется при любом клиенте
  — это модель, выключающая единственную проверку над собой.
- **Клиент-код — это анонимный посетитель дня.** Профили открыты; всё, что
  умеет поверхность, умеет любой посетитель через страницу — ровно как на
  экране дня 15 сегодня, не шире. Новое не в правах посетителя, а в
  поверхности: дефект кода дня (например, аргумент со страницы, пробитый
  в `profileId`) даёт полный перечень операций. Поэтому проверка аргументов —
  на поверхности, не на странице (п. 2), и перечень — короткий.
- **Две поверхности к одним данным.** Экран дня 15 пишет через `/v1`,
  новый день — через управление; разборщики общие, но проверки «диалог
  принадлежит профилю» и «запуск идёт — писать нельзя» существуют в двух
  местах. Расхождение молчаливо; держит общий модуль разборщиков и тест на
  каждую операцию, не внимательность.
- **`models.set` — денежная поверхность, не обход роутера.** Явный провайдер
  проходит только внутри ярусов класса (`router/src/router.js:151-168`),
  `dailyCostUsd: 10` приложения `agents` действует. Что меняется: `kimi-k3`
  делает следующий ответ до $0,48 у всякого на том же профиле и действует в
  дне 13 (`days/day15/README.md`). `compliance` спросит: лимитер до платных
  операций (п. 2), чей ключ платит (развилка 1), почему `models.set` в
  перечне — ответ: потому что запросил владелец и это равно экрану.
- **Два слова «инварианты».** Поверхность знает только инварианты профиля
  `Пn`. Инварианты продукта `I-n` живут в git (I-11) и меняются ADR; API к
  ним не проектируется никому.
- **Порт 8086 виден из `default`, `cron`, `tools`.** Держит только
  `CONTROL_KEY`; копия его в `dayN.env` — запрещённая копия (закрытый список
  `/day-cycle`). Держатель на «ключ не утёк в чужой env» — тот же, что у
  `MCP_KEY`: перечень разрешённых копий, проверка `grep -o '^[A-Z_]*='`.

## Чем платим

- **Второй ключ и вторая поверхность в одном процессе:** `CONTROL_KEY`
  порождается на сервере агентом по образцу `MCP_KEY` (строка закрытого
  списка — часть этого ADR) и копируется в `mcpagents.env`; список копий
  растёт на две строки.
- **Ещё одна единица и сеть:** семь мест конвейера (ADR `2026-09-28-0736`,
  «Последствия»), правило стража, тест адреса по образцу
  `test/mcp-server-urls.test.js`; ошибка в одном — единица молча вне выкатки.
- **Перечень операций дублируется по форме** в `ops.js` и в списке
  инструментов/ресурсов `mcpagents`; сверяет тест «имена инструментов
  сервера = операции записи поверхности», иначе разъедутся.
- **Ресурсы MCP руками** — ~100 строк к модулю; клиент дня тоже пишется
  руками (второй после дня 16).
- **Отдельный бюджет — не строка конфигурации:** ключ роутера у машины
  запусков — `env.ROUTER_APP_KEY` (`agents/src/llm.js:896`); свой ключ для
  операций управления — протаскивание через `createRun` по образцу
  `mcp-agent` (`agents/src/mcp/agent.js`, выбор в точке входа), 2–3 ч, и
  `APP_KEY_*` кладёт владелец.
- `message.send` держит замок диалога до ~16,8 мин при зависшем поставщике
  (`snapshot.md`, день 15) — посетитель дня 15 на том же профиле ждёт.
- Владелец получает не «всё, что умеет сервис», а перечень; каждая новая
  операция — ADR-строка и PR класса A с `compliance`.

## Что этим НЕ решается

- Профили открыты; личности посетителя поверхность не вводит.
- Лимитер у `/v1` не появляется (`backlog.md`, Next); он — у поверхности
  управления и у дня.
- Правка сообщения и инварианта на месте не появляются.
- Поверхность не отличает человека от кода дня и от модели; граница —
  перечень и клиент, а не проверка вызывающего.
- День 15 и его API не меняются.
- Хост в `agents` ресурсов читать не умеет; если день захочет дать модели
  эти данные — отдельный ADR со своим разбором инъекции.

## Проверено лично и что остаётся неподтверждённым

По коду `main` на `42d59f2` 2026-09-28: ручки таблицы и их проверки
доступа; отсутствие `limiter`/`reserve` в `agents/src/service.js`;
`profile()` отдаёт `invariants` и `prompts` (`sessions.js:1182-1187`); один
слушатель в `agents/server.js:211`; `ROUTER_APP_KEY` в `llm.js:335,896`;
`RULES` стража сетей и правило `tools`; `listAllTools` без отбора; модуль
`mcpnews/src/rpc.js` и клиент хоста без `resources/*`; прямой клиент дня 16;
порождение `MCP_KEY` на сервере — строка закрытого списка `/day-cycle`;
явный провайдер в роутере ограничен ярусами.

Неподтверждённым остаётся всё, что собрано по документации поставщика:
форма `resources/list`/`resources/read` и URI-схем ревизии `2025-11-25` —
по спецификации, не по живому клиенту; здесь клиент наш, и несовместимость
всплыла бы только с чужим.

## Развилки владельцу — решить до начала работы

1. **Чей бюджет у `message.send` и `invariant.draft`:** ключ `agents`
   (без действий владельца, расход сливается с посетителями дней 6–20) или
   приложение роутера `control` со своим потолком — `APP_KEY_CONTROL` кладёт
   владелец, плюс 2–3 ч протаскивания ключа. Рекомендация: своё приложение —
   учёт «свой» иначе не свой.
2. **`prompt.set` для `stage.verify.invariants`:** в перечне (равно экрану
   дня 15, выключает единственную проверку с пометкой) или вне его (день не
   сможет править проверку). Рекомендация: вне — до дня, который это
   обоснует.
3. **Срок и состав `control_log`:** без текстов и адресов, 30 дней. Что уходит
   в него — операция, профиль, исход, миллисекунды, признак оплаты.
4. **Имя единицы и сети** (`mcpagents`, `control`) — в глоссарий; и номер
   дня-клиента по заданию.

- **Обернуть `/v1` в MCP** — отклонено владельцем: наследует разрешение по
