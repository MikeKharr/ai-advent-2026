Восемь дней прожиты на фреймворке из шаблона `2030ai` с ролями

максимизировать долю результатов, доставляемых без обращения к человеку,

Что показала практика дней 6–8:

- Сессии запускаются из каталога `hbk-template`, а не из репозитория:

  general-purpose, хук форматирования применяет **чужой** конфиг Biome и

- Протокол передачи ролей описан в `agent-roles.md`, но не исполняем

фронтматтер роли штатно поддерживает `model` (`fable`/`opus`/`sonnet`/

альтернативы.

## Решение

### 1. Модель и усилие — свойство роли, в фронтматтере

Каждая роль в `.claude/agents/*.md` получает `model` и `effort`:

| Роли | Модель | Усилие | Почему |
|---|---|---|---|
| `architect`, `compliance`, `reviewer`, `design` (ревью) | `fable` | high | Проектирование и гейты: цена ошибки — переделка или инцидент |
| `backend`, `frontend`, `data`, `qa`, `platform`, `design` (раскладка) | `opus` | medium | Линейная работа по готовым критериям — выбор владельца |
| `docs`, `product-analyst` | `opus` | low | Запись и структурирование уже принятых решений |
| Поисковые (`Explore`) | `haiku` | — | Найти файл — не решение |

Разделение `design` на два уровня решается вторым файлом роли
(`design-review.md` с `model: fable`), не усложнением одного.

### 2. Скиллы Османи — предзагружаются в роли, а не вспоминаются

Сейчас `AGENTS.md` просит использовать `.agents/skills/` «в первую
очередь», но роль может забыть. Фронтматтер `skills:` внедряет скилл в
контекст роли принудительно:

| Роль | Предзагрузка |
|---|---|
| `architect` | `spec-driven-development`, `planning-and-task-breakdown` |
| `backend`, `frontend` | `incremental-implementation`, `test-driven-development` |
| `qa` | `test-driven-development` |
| `reviewer` | `code-review-and-quality` |
| `docs` | `documentation-and-adrs` |
| `design` | `frontend-ui-engineering` (ревью — по `/design-review`, как сейчас) |

Это и есть «приоритет Османи в кодинге»: его практики перестают быть
рекомендацией и становятся частью промпта роли. Верхнеуровневый процесс
(ADR, dev-history, snapshot, инварианты) остаётся за правилами проекта —
приоритет при конфликте не меняется.

### 3. Гейты — по классу изменения, а не по одному списку для всего

Сегодня любой PR формально проходит одинаковый набор. Вводится три класса:

| Класс | Что | Гейты |
|---|---|---|
| A. Код с деньгами/данными: `router/`, `agents/`, лимитеры, ключи | как день 8 | reviewer + compliance (вето) + design при UI; ADR при значимом решении |
| B. Обычный код дня без изменения расхода | новый экран, правка логики | reviewer; design-ревью при UI; compliance только если дифф касается env/лимитов/ключей |
| C. Документы, конфиг CI, лендинг | dev-history, snapshot | механические проверки CI (markdownlint, docs-guard); ревью не требуется |

Что убирается как избыточное: двойной проход `design` для **правок**
существующих экранов (раскладка до кода остаётся обязательной только для
новых экранов и смены раскладки); три ревью для docs-PR (день 8 уже мержил
PR 46 без них — класс C это узаконивает).

Что добавляется как недостающее:

- **Перепроверка — тем же экземпляром.** После правок блокирующих находок
  автор возвращает работу тому же ревьюеру через SendMessage; правило
  переезжает из памяти сессии в `agent-roles.md`.
- **Скриншот-проверка и контраст в CI** — уже в бэклоге, поднимается в
  приоритете: механический гейт дешевле ролевого.
- **Человеческих гейтов остаётся два** — принятие ADR и слово на выкатку.
  Всё остальное — агентные и механические гейты. Это прямое следствие
  «70% problem» Османи: последние 30% — ответственность не человека-
  оператора, а состязательных ревью и падающих закрыто проверок; человек
  остаётся на решениях, не на верификации.

### 4. Оркестрация — скилл, а не переписка

Протокол передачи из `agent-roles.md` оформляется проектным скиллом
`.agents/skills/day-cycle/SKILL.md`: фазы (аналитик → архитектор → ADR-гейт
→ реализация → три ревью параллельно → правки → перепроверка теми же
экземплярами → PR → CI → слово владельца → деплой → dev-history), для
каждой фазы — роль, модель и критерий выхода. Основная сессия ведёт
оркестрацию сама (subagents в одной сессии); Agent Teams и внешние
оркестраторы не вводятся.

### 5. Рабочее окружение: репозиторий открывается как свой проект

- Сессии Claude Code / VS Code запускаются из
  `~/Projects/ai-advent-2026`, не из `hbk-template`. Это возвращает роли,
  скиллы и правила проекта в автозагрузку и убирает чужой Biome-хук.
- В репозиторий добавляется `.claude/settings.json`: allowlist разрешений
  для рутинных команд (`node --test`, `docker compose` на сервере через
  `ssh advent@…`, `gh pr`/`gh run`, `npx markdownlint-cli2`), чтобы
  классификатор не рвал автономные прогоны. Режим разрешений по умолчанию
  не ослабляется: allowlist точечный, деструктивные действия по-прежнему
  спрашивают.
- Форматирование — свой `biome.json` проекта или отказ от формат-хука;
  чужой конфиг не применяется.

## Обоснование

- Ярусность моделей — проверенная практика самой крупной коллекции агентов
  и прямой запрос владельца; штатный механизм (`model`/`effort` во
  фронтматтере) не требует ни одной внешней зависимости.
- Предзагрузка скиллов заменяет надежду дисциплиной: промпт роли и есть
  место, где практика либо присутствует, либо нет.
- Классы изменений узаконивают то, что фактически уже происходит
  (docs-PR #46 без трёх ревью), и снимают лишние прогоны — не ослабляя
  гейты там, где деньги и данные.
- Отказ от внешних оркестраторов — «минимум необходимого»: масштаб проекта
  — один владелец и один день за итерацию; subagents в одной сессии этот
  масштаб покрывают, что и показали дни 6–8.

## Последствия

Отрицательные и риски — честно:

- **Ревью на fable дороже ревью на модели сессии не станет, но и дешевле
  не станет.** Экономия придёт только от среднего яруса (реализация,
  документы) и от класса C. Если окажется, что fable-ревью медленнее и
  не находит больше, чем opus high, ярус пересматривается — критерий:
  два дня подряд без уникальных находок fable против opus.
- **Классы изменений требуют честной классификации.** Соблазн назвать
  диффа классом C, когда он трогает env, — реальный; страховкой остаётся
  вето compliance на всё, что касается ключей и расхода, независимо от
  класса.
- **`effort: medium` на кодинге может дать больше циклов правок** после
  ревью. Если правок станет заметно больше — поднять до high, это одна
  строка.
- **Предзагрузка скиллов удлиняет контекст роли** (полный текст скилла, не
  описание). Для ролей с двумя скиллами это приемлемо; больше двух — не
  предзагружать.
- Переезд сессий в свой каталог потребует один раз перенастроить привычку
  запуска и перенести релевантную память.

## Альтернативы рассмотрены

- **Внешние оркестраторы (claude-flow, Multiclaude, Microsoft Conductor).**
  Дают параллельные сессии и дашборды, но приносят зависимость, свой
  конфиг и свои дыры безопасности; масштаб проекта их не окупает.
- **Agent Teams (встроенные, экспериментальные).** Peer-to-peer общение
  теммейтов полезно для больших параллельных работ; флаг экспериментальный,
  включение отложено до задачи, которая в subagents не помещается.
- **Один общий `CLAUDE_CODE_SUBAGENT_MODEL` вместо фронтматтера.** Проще,
  но убивает саму идею ярусов: либо все роли дорогие, либо все дешёвые.
- **Ослабить человеческий гейт ADR ради автономии.** Отклонено: день 8
  показал ровно обратное — принятие ADR владельцем поймало неверный расчёт
  цены. Автономия наращивается снятием механических препятствий, не
  снятием решений с владельца.
