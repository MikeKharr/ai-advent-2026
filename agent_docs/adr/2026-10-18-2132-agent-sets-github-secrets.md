# [2026-10-18 21:32] Секреты GitHub заводит агент — под подтверждение владельца

Файл: `agent_docs/adr/2026-10-18-2132-agent-sets-github-secrets.md`

## Статус

Принято владельцем 2026-10-19.
Заменяет `2026-09-11-1743` в части «новые секреты — только владелец»
(его п. «Агент заводит и новые секреты через `put-secrets.sh` — Отклонено»).
Заменяет `2026-10-18-1147` в части «`gh secret set` выполняет владелец»
(его п. 2 и раздел «Ручные шаги и проверки»).
Во всём остальном оба предшественника в силе: норма мержа защищённых путей и
копия `AGENT_KEY` — у первого, план недели дней 31–35 и устройство ревью по
токену подписки — у второго. Серверных секретов замена не касается.

Источник — разговор с владельцем 2026-10-19, дословно:

> я бы предпочел разрешить тебе добавлять ключи и секреты. В свою очередь ты
> должен при создании ключа убедиться что я его увидел, т.е. вывести в
> интерфейсе c action (например ты: запусти команду и получи такой то ключ в
> буфер, сохрани в менеджере паролей. Варианты ответа сделал / не сделал /
> другое)

На предложенную формулировку инварианта владелец ответил «Да».

## Контекст

До этого решения любой новый секрет был действием владельца: AGENTS.md
(«За человеком всегда: … новые секреты на сервере») и `/day-cycle`, фаза 9
(«Новый секрет — на сервер до мержа, только через `deploy/put-secrets.sh`
руками владельца»). Правило вводилось для серверных секретов (ADR
`2026-09-11-1230`, `2026-09-11-1743`), но читалось шире и упиралось в
секреты GitHub: день 32 остановился на том, что `gh secret set
CLAUDE_CODE_OAUTH_TOKEN` и `gh secret set RAG_KEY` должен выполнить владелец
руками (ADR `2026-10-18-1147`), хотя у агента есть и доступ `gh`, и способ не
показать значение (`stdin`).

Два разных случая смешивались в одном запрете:

1. **Секрет GitHub.** Агент может завести его сам, не увидев и не показав
   значения: `printf '%s' "$v" | gh secret set NAME`. Риск — не в команде, а в
   том, что порождённое агентом значение нигде больше не лежит: сессия
   кончится, и секрет останется в хранилище без владельца.
2. **Секрет на сервере.** Там дело не в удобстве, а в закрытом списке
   серверных команд: список правится только ADR, который принимает владелец
   (ADR `2026-09-11-1230`, `2026-09-16-0907`), и `deploy/put-secrets.sh` в нём
   не лежит.

## Решение

1. **Секреты GitHub (`gh secret set`) заводит агент** — значение только через
   `stdin`, и, если значение порождено агентом и больше нигде не лежит,
   секрет считается заведённым только после подтверждения владельца, что он
   сохранил значение в менеджере паролей. Правило целиком — инвариант **I-16**
   в `agent_docs/invariants.md`, раздел «Защита»; здесь оно не повторяется.
2. **Серверные секреты (`deploy/*.env`) остаются за владельцем** без
   изменений: `deploy/put-secrets.sh` руками владельца, закрытый список
   серверных команд не расширяется. Этот ADR его не трогает.
3. **Ключи в чужих консолях** (Anthropic Console, панели провайдеров) и
   **удаление/ротация существующих секретов** — владелец.

## Обоснование

Запрет держался за то, что значение не должно появиться в транскрипте, а не за
то, что агент не вправе обратиться к хранилищу. Передача через `stdin` снимает
первое, не затрагивая второго. Остаётся настоящий риск — секрет, о котором
владелец не знает; его закрывает не запрет на `gh secret set`, а требование
подтверждения с вариантами ответа, которое владелец и сформулировал.

Два носителя значения в этом требовании — разной природы, и смешивать их
нельзя. **Буфер обмена — транзит:** значение проходит через него и затирается
в конце прохода (так же сказано про буфер в I-15). **Менеджер паролей
владельца — не транзит и не место системы:** там значение лежит постоянно, и
именно в этом смысл ответа «Сделал» — знание владельца существует вне
проекта, и ни агент, ни репозиторий им не распоряжаются.

Серверные секреты не трогаются, потому что там ограничение другой природы:
закрытый список серверных команд — предмет отдельного ADR, и расширять его
попутно нельзя.

## Последствия

- **Агент заводит только новые имена.** Имена, уже существующие в секретах
  репозитория на 2026-10-18 (`gh secret list`: `RAG_KEY`,
  `ANTHROPIC_API_KEY_AI_REVIEW`, `SSH_HOST`, `SSH_KEY`, `SSH_USER`) агент не
  трогает: перезапись существующего имени — ротация, а ротация по I-16 за
  владельцем. У `RAG_KEY` это не формальность: по I-15 значение обязано
  совпадать в четырёх местах, и перезапись только в GitHub рассогласовала бы
  его с `deploy/rag.env` — то есть сломала бы `/rag` в проде.
- **Дню 32 это уже ничего не даёт:** оба секрета ревью владелец завёл сам
  2026-10-18 (`RAG_KEY` и `ANTHROPIC_API_KEY_AI_REVIEW`), а
  `CLAUDE_CODE_OAUTH_TOKEN` предметом быть перестал — авторизацию ревью
  токеном подписки заменил отдельный ключ API — вечерний ADR дня 32,
  `review-auth-and-model`, п. 1 (в `main` его ещё нет, он идёт с PR дня 32).
  Правило работает со следующего нового секрета, а не задним числом.
- Появился новый останов с вопросом: порождённый агентом секрет держит выкатку
  до ответа «Сделал». Молчаливое ожидание запрещено (`AGENTS.md`, «Останов —
  всегда с сигналом»).
- **Держателя кодом у I-16 нет.** Подтверждение — факт разговора, а не строка;
  ни одна проверка не краснеет от секрета, заведённого без ответа «Сделал».
  Это честная граница, а не долг к закрытию в этом PR (I-14 о держателях
  говорит про правила, вводимые кодом).

## Ручные шаги и проверки (для ADR о переезде)

Переезда нет. Из защит снимается одна — «новый секрет кладёт только
владелец» — и только для секретов GitHub. Взамен вводится подтверждение
владельца по I-16; для серверных секретов защита остаётся как была.

## Альтернативы рассмотрены

- **Оставить как было, владелец кладёт все секреты.** Отклонено владельцем:
  это его время на действие, которое агент выполняет без доступа к значению.
- **Разрешить агенту и серверные секреты заодно.** Отклонено: расширение
  закрытого списка серверных команд — отдельное решение владельца, и
  попутно оно не принимается.
- **Разрешить без подтверждения.** Отклонено: порождённое агентом значение,
  никуда не записанное владельцем, — секрет без владельца.
- **Держатель кодом: проверять, что у каждого имени в `gh secret list` есть
  ответ «Сделал».** Отклонено как невозможное: ответ живёт в разговоре, а не
  в репозитории, и `gh secret list` агенту доступен не в CI.
