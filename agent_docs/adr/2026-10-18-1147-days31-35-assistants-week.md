### 1. День 31 — локальный stdio-сервер MCP `mcpgit` и скилл `/project-help`

1. **Сервер — новый каталог `mcpgit/` в корне, без Dockerfile, без
   `package.json`**: `server.mjs` на `node:readline` поверх stdin/stdout,
   своя копия JSON-RPC по образцу `mcpnews/src/rpc.js` (ревизия
   `2025-11-25`, `initialize`, `tools/list`, `tools/call`, `isError` у отказа
   инструмента). Два инструмента, оба без аргументов: `git.branch` —
   `git rev-parse --abbrev-ref HEAD`; `git.changed` — имена файлов из
   `git status --porcelain` и `git diff --name-only main...HEAD`. Команды —
   литералы через `execFile`, ввода от модели нет, поверхности для
   подстановки нет. Каталог сервера — `CLAUDE_PROJECT_DIR`, иначе `cwd`.
   **Ветка — локальная по построению:** процесс живёт в сессии Claude Code
   на ноутбуке, в образы и `compose.yml` не входит; на VPS его нет.
2. **Граница зависимостей укладывается без правки карты.** Шаг «Граница
   runtime-зависимостей» в `ci.yml` читает каждый `package.json` и
   `requirements.txt` дерева; у `mcpgit/` манифеста нет — умолчание «ноль»
   выполнено пустотой. Единицей выкатки каталог не становится: шаг «Имена
   единиц выкатки» смотрит каталоги с `Dockerfile`, а матрица `ci.yml` и
   `deploy-units.sh` знают единицы по закрытому списку имён и `days/`.
3. **Тесты — в корневом `test/mcpgit.test.js`**: он идёт шагом «Данные
   страницы прогресса» в `docs-guard.yml` (`node --test test/*.test.js`) на
   каждом PR, как и прочие тесты уровня проекта там же (`deploy-hostkey`,
   `compose-*`, `rag-route-lock`). Матрица `ci.yml` каталог вне своего
   списка имён не видит, и добавлять его туда — правка `.github/**` ради
   двух инструментов; не делается. Тест поднимает сервер дочерним процессом в
   временном git-репозитории с известной веткой и проверяет оба ответа и
   отказ на неизвестный метод.
4. **Подключение — вторая запись в `.mcp.json`:** `"mcpgit": {"type":
   "stdio", "command": "node", "args": ["${CLAUDE_PROJECT_DIR:-.}/mcpgit/server.mjs"]}`.
   Имена инструментов в сессии — `mcp__mcpgit__git_branch`,
   `mcp__mcpgit__git_changed` (точка → подчёркивание, как у
   `mcp__project__project_search` сегодня).
5. **Команда — project-local skill `/project-help`**, не `/help`: встроенная
   `/help` занята, и хотя документация поставщика допускает замещение
   встроенной команды проектным скиллом в терминале, владелец выбрал новое
   имя. Форма — по правилам `AGENTS.md`, «Project-Local Skills»:
   `.agents/skills/project-help/SKILL.md` (`name: project-help`, описание с
   `/project-help`, H1 `# /project-help`), `agents/openai.yaml` с
   `display_name: "/project-help"`, симлинки в `.claude/skills/`,
   `.codex/skills/`, `.cursor/skills/`. Тело: взять ветку и изменённые файлы
   у `mcpgit`, спросить `project.search` (`limit` 5), прочитать названные
   файлы по пути, ответить со ссылками на файл и раздел; ответа в корпусе
   нет — сказать это, не достраивать (I-8). `allowed-tools` — три
   инструмента MCP и `Read`.
6. **Что это даёт сверх Claude Code как он есть — честно: форму задания.**
   Ветку и список файлов Claude Code получает `Bash`-ом за одну строку;
   `project.search` уже подключён. Ценность дня — показать протокол
   (stdio-сервер без SDK рядом с HTTP-серверами проекта) и собрать три
   источника в одну команду. Видео записывает владелец.

### 2. День 32 — `.github/workflows/ai-review.yml` на официальном действии

1. **Триггер — `pull_request` (`opened`, `ready_for_review`), не
   `pull_request_target`.** На публичном репозитории GitHub не выдаёт
   секреты запускам от PR из форков — ревью идёт только по веткам этого
   репозитория, и это **граница доверия всего дня**: любой, кто может
   запушить ветку (владелец и агенты под его токеном), может править и сам
   workflow в своём PR, потому что `pull_request` исполняет файл workflow из
   PR. Это новый класс доступа к секретам: до сих пор `secrets.*` читала
   только выкатка по `push` в `main` за гейтами. Цена названа в
   «Последствиях»; смягчение — ценность обоих секретов (п. 2.3, 2.6).
   `synchronize` не включается: одно ревью на PR, а не на каждый коммит
   (развилка Р3). Фильтр `paths` — код живых единиц, `deploy/`, `.github/`;
   PR класса C без кода ревью не получают.
2. **Авторизация модели — `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}`**.
   Токен печатает `claude setup-token` у владельца: срок год, планы Pro /
   Max / Team / Enterprise, «только запросы к модели»; расход идёт в
   подписку, а не в биллинг API. Кладёт владелец (`gh secret set`, ввод
   скрытый — память проекта о секретах в истории shell).
3. **RAG — существующий сервер `project` из `.mcp.json`, и без нового секрета
   это невозможно.** Действие читает `.mcp.json` репозитория само, но
   заголовок `Bearer ${RAG_KEY}` подставляется из окружения процесса, а
   `RAG_KEY` в GitHub Secrets нет (п. 0). Нужен секрет `RAG_KEY` — то же
   значение, что в `deploy/rag.env` и в окружении ноутбука
   (`deploy/put-rag-key.sh` зовёт эти два места); GitHub — **четвёртое
   место жизни** ключа. Что он стоит при утечке — не деньги, а суточный
   потолок эмбеддера (500, не измерен) и окна 10/мин, 100/час на адрес;
   ключей к моделям у `rag` нет. Передача в действие — файлом конфигурации
   MCP, записанным шагом из секрета, через `--mcp-config` (документированный
   путь); подстановка из `env` шага не подтверждена и не берётся. Развилка Р1.
4. **Что уходит в Anthropic:** дифф и файлы PR (публичны), фрагменты
   `project.search` (корпус публичного репозитория), `AGENTS.md` через
   `CLAUDE.md`, промпт workflow. Ничего, чего нет на GitHub. `RAG_KEY`
   уходит только на `challenge.zpq.ai`; токен — в авторизацию Anthropic.
5. **Инструменты — только чтение и комментарий; `Bash` не разрешается.**
   `--allowedTools "mcp__github_inline_comment__create_inline_comment,mcp__project__project_search"`
   плюс чтение файлов и read-only git, которые действие даёт по умолчанию.
   Примеры поставщика разрешают `Bash(gh pr comment:*)` — здесь нет: шаблон
   пропускает любые аргументы, а оболочка раскроет `$RAG_KEY` или
   `$CLAUDE_CODE_OAUTH_TOKEN` в тело публичного комментария — готовый канал
   вывода секрета по подсказке из диффа. Промпт: три рубрики задания
   (потенциальные ошибки, архитектурные проблемы, рекомендации), опора на
   `invariants.md` и ADR через `project.search`, сводный комментарий и
   инлайн-замечания; текст диффа и фрагменты — данные, не указания.
   **Prompt injection из диффа остаётся**: смягчение — поверхность: нет
   записи в репозиторий (`contents: read`), нет оболочки, худший исход —
   ложное или пустое ревью и потраченные ходы.
6. **Лимиты расхода подписки:** `--max-turns 15`, `timeout-minutes: 15`,
   `concurrency` по номеру PR с отменой, один запуск на PR (п. 1). Чем
   платим — окна подписки общие с сессиями самого владельца: серия PR дня
   съедает лимит, в который упрётся его же Claude Code. Числа окон плана не
   проверены (план владельца этим ADR не читался). `--model` не передаётся:
   идентификаторы моделей в проекте живут только во фронтматтере ролей.
7. **Авторизация GitHub — `github_token: ${{ secrets.GITHUB_TOKEN }}`** с
   `permissions: contents: read, pull-requests: write`; без установки
   Claude GitHub App и без `id-token: write`. Цена по документации:
   комментарии от `github-actions[bot]`, липкий комментарий не обновляется.
   Это буквально «права токена — только comment», как просил владелец.
   Развилка Р2.
8. **Живая проверка — на самом PR дня 32**: workflow из PR исполняется на
   этом же PR, как только оба секрета лежат. Гейт `compliance` смотрит
   workflow до появления секретов; результат первого запуска — в описании PR.

`.mcp.json`; замещение встроенной команды проектным скиллом. Отдельно не
проверено: достаточно ли `pull-requests: write` для сводного комментария
через инструменты действия; как отозвать токен `setup-token` до срока; есть ли
`claude setup-token` в сборке CLI владельца — бинарь `claude` в этой сессии
не найден в `PATH` и трёх обычных местах, владелец работает из VS Code.

## Последствия

Положительные — коротко: пробелы дней 31 и 32 закрываются без правок прода и
без ключа API; `project.search` получает второго потребителя — ревью PR; дни
33–35 уходят туда, где им место, — в репозиторий приложения.

Чем платим:

- **Секреты становятся достижимы из неслитой ветки.** Любой PR из ветки
  репозитория исполняет свой workflow с `RAG_KEY` и токеном подписки; гейты
  класса A стоят после запуска, а не до. Доверие — всем, кто пушит ветки:
  владелец и агенты под его токеном, у которых и так право мержа по
  консенсусу. Утечка токена — год запросов к модели за счёт подписки
  владельца, способ отзыва не подтверждён.
- **`RAG_KEY` в четвёртом месте.** `put-rag-key.sh` знает два места плюс
  ноутбук; GitHub Secrets ни один скрипт не кладёт и не сверяет — ротация
  ключа теперь обязана помнить четыре места руками.
- **Расход подписки общий с владельцем** и не наблюдается из репозитория:
  нет счётчика, нет метрики, только `--max-turns` и таймаут. День с пятью
  PR — пять ревью в его окне.
- **Prompt injection из диффа не снимается**, только сужается до поверхности
  без оболочки и без записи; ложное ревью на публичном PR — реальный исход.
- **Ревью от `github-actions[bot]`** не считается вердиктом ни одного гейта
  и в `gh pr view --json reviews` консенсуса не меняет — это демонстрация
  задания, не замена ролей. И само ревью неотличимо по автору от других шагов
  CI.
- **Вторая копия JSON-RPC** (`mcpgit/`) рядом с `mcpnews`, `mcpstore`, `rag/rpc.py`
  — цена границы зависимостей, названная в ADR `2026-09-28-0736`, п. 3, и
  уплаченная в четвёртый раз.
- **Тесты `mcpgit` едут в шаге с чужим именем** («Данные страницы прогресса»)
  — так уже живут семь тестов уровня проекта; имя шага врёт о содержимом.
- **`mcpgit` не в корпусе индекса**: `CODE_DIRS` в `rag/corpus.py` и
  регулярка `rag` в `ci.yml` — две копии, их правка — класс A; `/project-help`
  узнает о сервере из `architecture.md`, не из его кода.
- **Стороннее действие исполняет код в репозитории** — `anthropics/claude-code-action@v1`,
  плавающий тег; закрепление на sha — отдельное решение, здесь не принято.
- **День 31 показывает протокол, а не новую способность**: ветку и файлы
  Claude Code умеет без MCP.
- **Проверяющие не увидят код дней 33–35**; видео и выдержки — слово
  владельца против кода. Дни 33 и 34 не стали дешевле — они переехали.
- **Одна страница на пять дней** против «по каталогу на день» недели 26–30:
  раскладка требует дополнения, и на лендинге пять карточек ведут на одну
  страницу.

## Что этим НЕ решается

- Дизайн, данные и процесс `samui-villas` — ADR того репозитория.
- Карта зависимостей, матрица `ci.yml`, корпус индекса не меняются.
- Ревью действием не входит в гейты мержа; роли и консенсус — как были.
- `pull_request_target`, GitHub App, подпись коммитов — не вводятся.
- Прод не меняется ни одной строкой.

## Решения владельцу

Слова: «секрет репозитория» — значение в GitHub Secrets, доступное workflow;
«токен подписки» — вывод `claude setup-token`; «stdio-сервер» — программа,
которую Claude Code запускает на ноутбуке и говорит с ней через stdin/stdout.

- **Р1. RAG в ревью PR:** (а) секрет `RAG_KEY` в GitHub — четвёртое место
  ключа, ревью ищет по `project.search` *(предложено: задание требует RAG, и
  это единственный путь без кода)*; (б) без RAG через MCP — ревью читает
  `agent_docs/` с чекаута `Grep`/`Read`; дешевле на один секрет, задание
  выполнено только буквой «документация + код»; (в) второй ключ для CI в
  `rag/serve.py` — класс A в проде ради ревью, нет.
- **Р2. Авторизация GitHub:** (а) `GITHUB_TOKEN`, `pull-requests: write`,
  без App *(предложено: «только comment» буквально)*; (б) установить Claude
  GitHub App — комментарии от `claude[bot]`, липкий комментарий, но App
  просит набор прав шире нужного (Contents, Workflows — запись).
- **Р3. Когда запускать:** (а) `opened` + `ready_for_review`, фильтр путей
  кода *(предложено: одно ревью на PR)*; (б) плюс `synchronize` — ревью на
  каждый коммит, расход подписки кратно числу коммитов; (в) только по метке
  `ai-review` — ноль фоновых запусков, запуск руками.
- **Р4. Инструменты `mcpgit`:** (а) `git.branch` + `git.changed`
  *(предложено)*; (б) только `git.branch` — минимум задания; (в) плюс
  `git.diff` — дифф целиком, нужен потолок размера ответа.
- **Р5. Страницы:** (а) одна страница недели + пять карточек *(предложено)*;
  (б) пять страниц по образцу дня 27 — ≈ 6–8 часов и пять ревью; (в) только
  карточки с внешними ссылками на GitHub — некуда положить ограничение о
  приватном коде и видео.
- **Р6. Что показать проверяющим за дни 33–35:** (а) видео + текст о
  составе без выдержек кода *(предложено: ничего приватного не публикуется)*;
  (б) видео + выдержки кода по выбору владельца — публикуются куски
  приватного репозитория.

## Ручные шаги и проверки (для ADR о переезде)

Переезда нет. Руками владельца, до мержа PR 3: `claude setup-token` →
`gh secret set CLAUDE_CODE_OAUTH_TOKEN` и `gh secret set RAG_KEY`, оба со
скрытым вводом, значение в команде не появляется; на запрос — отзыв токена
и удаление обоих секретов, дни пересдаются без ревью. Видео дня 31 и
материалы дней 33–35 — владелец. Процесс `samui-villas` — отдельная задача
в том репозитории.

## Альтернативы рассмотрены

- **`/help` как имя скилла** — встроенная команда; владелец выбрал новое имя.
- **Инструмент ветки в службе `rag` или `mcp` на VPS** — там всегда `main`.
- **`mcpgit/` на `@modelcontextprotocol/sdk`** — SDK разрешён только `mcp/`.
- **Сервер внутри каталога скилла** — код в `.agents/skills/` не проверяет
  ни один шаг, и это дерево под исключениями линта.
- **Каталог `mcpgit/` в матрицу `ci.yml`** — правка `.github/**` ради двух
  инструментов; тесты и так идут в `docs-guard`.
- **`pull_request_target`** — секреты базовой ветки против кода из PR;
  документация поставщика предостерегает, владелец исключил.
- **Собственный скрипт ревью на `fetch` к API Anthropic** — ключа API нет.
- **Плагин `code-review` поставщика вместо своего промпта** — не зовёт
  `project.search`, рубрики задания не его.
- **`Bash(gh pr comment:*)` из примеров поставщика** — канал вывода секрета
  через раскрытие переменных.
- **Код дней 33–35 в `ai-advent`** — решение владельца: репозиторий
  приложения приватный и отдельный.
- **Единая страница итогов без карточек** — карточки на лендинге есть у
  каждого сданного дня; без них дни 31–35 на сайте не существуют.

## Дополнение 2026-10-18: авторизация ревью

Решение выше не переписывается: п. 2.2 остаётся тем, что было принято утром.
Это дополнение меняет только способ авторизации дня 32 и то, что из него
следует.

**Решение владельца 2026-10-18, дословно.** Вопрос: «Чем авторизовать
AI-ревью дня 32?» Ответ: **«Отдельный API-ключ для ревью
(Рекомендуется)»**.

Почему сменился способ:

1. **Токен `setup-token` нельзя отозвать точечно.** Его отзыв — это выход из
   аккаунта на всех устройствах («A revoked token means you signed out
   everywhere», `code.claude.com/docs/en/errors`). Для секрета, который
   читает workflow, исполняемый из PR, это неприемлемая цена инцидента:
   отзыв утёкшего токена ревью выбил бы владельца из его собственного
   Claude Code.
2. **Ключ API в Console снова выпускается.** Утром п. 0 фиксировал обратное
   («ключ API Anthropic истёк и новый в Console не создаётся»), и именно это
   вело к токену подписки. Предпосылка изменилась.
3. **Ключ ревью — отдельный от продового.** Отзыв ключа ревью не трогает
   прод, а расход ревью виден в Console отдельной строкой. Это требование
   владельца, а не удобство.

Что меняется в п. 2 «День 32»:

- **п. 2.2 заменяется.** Вход действия — `anthropic_api_key` (подтверждён в
  `action.yml:67` действия), секрет — **`ANTHROPIC_API_KEY_AI_REVIEW`**.
  Имя выбрано провайдер-первым, как `SSH_*` в этом репозитории: префикс
  называет подсистему (`ANTHROPIC_API_KEY`), суффикс — потребителя
  (`AI_REVIEW`). `grep ANTHROPIC_API_KEY` находит оба ключа, когда
  проверяешь, где они живут, а в диффе ключ ревью не спутать с продовым.
  Имя `ANTHROPIC_API_KEY` не берётся намеренно.
- **п. 2.6 меняется в части модели.** Там было: «`--model` не передаётся:
  идентификаторы моделей в проекте живут только во фронтматтере ролей».
  Теперь `--model claude-sonnet-5-5` передаётся явно, и это сознательное
  отступление: пока платила подписка, умолчание действия было бесплатным
  выбором, а с ключом API каждый запуск — счёт. Умолчание поставщика может
  смениться вместе с версией действия и подорожать молча; цена запуска
  обязана быть видна в файле. Почему `claude-sonnet-5-5` ($2/$10 за Mtok), а
  не `claude-haiku-5-5` ($0.10/$0.50): предмет ревью — расхождения с
  инвариантами и действующими ADR, то есть работа суждения; поверхностное
  ревью не стоит и своей цены.
- **п. 2.4 дополняется.** В Anthropic по-прежнему уходят дифф, файлы PR,
  фрагменты `project.search` и промпт — ничего, чего нет на GitHub. Меняется
  только биллинг: расход идёт на ключ API проекта, а не в окно подписки
  владельца. Поэтому потолки п. 2.6 (`--max-turns 15`, `timeout-minutes: 15`,
  `concurrency` на PR, один запуск на PR) теперь держат деньги, а не окно, и
  становятся важнее, чем были.

**Честная граница этого дополнения.** Правило AGENTS.md «идентификаторы
моделей живут только во фронтматтере ролей» писалось про документы, которые
повторяют идентификатор, и держит его шаг «Одна копия» в `docs-guard.yml` —
а он читает только `*.md` и только маркеры из
`agent_docs/guides/single-source.tsv`. Идентификатор в `*.yml` не краснеет ни
у кого. То есть это отступление **ничем механически не удерживается**: если
правило нужно распространить на исполняемую конфигурацию, это отдельное
решение владельца, а не следствие этой записи.

**Чего это дополнение не решает:** сколько ревью будет стоить на самом деле.
Оценка по форме диффа — порядка $0.15 за запуск на `claude-sonnet-5-5`, но
она не измерена; опорное значение проекта ($0.011 за некэшированный дайджест,
ADR `2026-09-07-2016`) к ревью не применимо — другая работа и другой объём
входа. Первый живой запуск даёт первое настоящее число, и если оно расходится
с оценкой вдвое, это повод остановиться и разобраться, а не поднять потолок.
