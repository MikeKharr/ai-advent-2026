# [2026-09-20 06:47] Админка почты: апстрим 443 и фильтрованный журнал

Файл: `agent_docs/development-history/2026-09-20-0647-mail-admin-upstream-443.md`

## Что сделано

- **Починена админка `mail.zpq.ai`** (PR #176, `6cbc3ef`, класс A): апстрим
  `reverse_proxy mail:8080` → `https://mail:443` с
  `transport http { tls_insecure_skip_verify }`. Сертификат на той стороне
  самоподписанный: провайдер ACME у Stalwart не заведён, соединение идёт по
  внутренней сети compose к своей же службе, наружу это не выходит.
- **Проверено живьём после выкатки:** админка отдаёт 302 на `/account`, по
  редиректу — 200. Соседи целы: адвент, `zpq.ai`, день 11 и атлас — 200,
  `www` — 301.
- **Включён access-лог блока `mail.zpq.ai` с фильтром query** — девять
  credential-параметров (`token`, `access_token`, `refresh_token`, `id_token`,
  `code`, `state`, `device_code`, `user_code`, `client_secret`) заменяются на
  `REDACTED`.
- **Служба `caddy` получила ротацию журнала** — `json-file`, `max-size 10m`,
  `max-file 3`.
- В `guides/logging.md` отмечено единственное место, где access-лог включён;
  само правило не менялось.

## Зачем

Админка отдавала 502 и держалась так несколько часов незамеченной:
последний успешный ответ был снят до применения настройки почты в прошлой
итерации, а после никто не опрашивал. Обнаружено случайно, при проверке после
выкатки PR #174; связь отказа с той выкаткой не подтвердилась.

## Чему научила итерация: три круга гейтов на правке одной строки

Ценность итерации не в самой правке, а в находках, невидимых в диффе.

1. **Ложное обоснование в комментарии.** Утверждалось со ссылкой на раздел
   «Bootstrap mode», что после мастера настройки порт 8080 перестаёт
   обслуживать администрирование. `reviewer` проверил исходники v0.16.22
   (`crates/common/src/manager/defaults.rs`): в наборе слушателей по умолчанию
   для нормального режима есть и 443, и 8080, а документация по безопасности
   советует закрывать 8080 **вручную**; названного утверждения в «Bootstrap
   mode» нет. Наблюдение автора засчитано, объяснение опровергнуто. Переписано
   на «8080 соединение не принимает — факт; причина не установлена».
2. **Утечка токенов в журнал.** Голый `log` пишет `request>uri` вместе с
   query, а Stalwart кладёт в query живые учётные данные: `?token=` для
   EventSource, `?code=`/`state` при входе. Гейт `compliance` нашёл, что это
   нарушает **письменную норму проекта** (`guides/logging.md`: «access-логи
   Caddy включаются только с фильтрацией query»), о которой забыли все трое
   участников.
3. **Отсутствие ротации.** У службы `caddy` единственной из пятнадцати не было
   блока `logging`. До этого PR она писала только старт и ошибки; PR впервые
   сажал туда поток запросов.

**Главный урок — живая проверка фильтра.** Зелёный гейт `caddyfile` работу
фильтра не доказывает: `caddy validate` конфигурацию не запускает, а
фильтр-энкодер при промахе пути поля **молча пропускает значение в журнал
целиком**. Проверка сделана значением, которое контролировал автор: запрос с
`?token=ZPQPROBE7e41a9c`, затем поиск **исходной строки** в журнале. Ноль
вхождений, запись легла как `"uri":"/?code=REDACTED&token=REDACTED"`. Искать
надо было не слово `REDACTED`, а отсутствие своего значения.

## Что осталось необъяснённым

**Девять подтверждённых 502 не оставили ни одной записи в журнале ошибок
Caddy.** При этом 5xx пишется туда безусловно — подтверждено независимо двумя
агентами по `modules/caddyhttp/server.go`; `handle_errors` в блоке почты нет,
глобального `log` и `debug` нет, catch-all нет. Две дешёвые версии проверены и
отпали:

- **короткий хвост** — снят журнал за сутки, 58 строк, ноль вхождений
  `error`, `502`, `dial`, `upstream`;
- **несовпадение блока** — страница 404 `zpq.ai` приходит так же, без
  заголовков своего блока и с `server: Caddy`, то есть на путях ошибок
  заголовки не применяются и в рабочем блоке.

Противоречие **не объяснено**; так и записано в комментарии к конфигу, а не
подогнано под удобную версию. Наблюдаемость здесь хуже ожидаемой — пункт
заведён владельцу в `backlog.md`.
