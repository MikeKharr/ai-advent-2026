- **Сквозное:** на экране дня — сырой JSON-RPC каждого вызова и имя сервера,
  как в консоли дня 16.

Мысли владельца (рассмотреть, не исполнять): свой MCP-клиент в `agents/`

## Вопрос 1. Расход без человека

Сегодня ни один вызов модели не происходит без посетителя: лимитеры дней
считают адреса, суточные счётчики живут в памяти дня, роутер держит $10 на
приложение `agents`. Планировщик ломает первую предпосылку — адреса нет.

Что рассматривалось и что выбрано (ADR, п. 6):

| Мера | Что держит | Держатель по I-14 | Цена |
|---|---|---|---|
| Потолок стартов в сутки в `jobs.db` | число запусков; переживает перезапуск, в отличие от счётчиков дней | тест «7-й старт не происходит, роутер не вызывается» | ноль |
| Отдельное приложение `scheduler` в роутере, `dailyCostUsd: 0.5` | деньги; журнал на томе; строка в `/v1/spend` | тест на `apps.json` (мутация «100» — красный) плюс существующий «исчерпанный лимит — `budget_exceeded`, провайдер не вызывается» | новый секрет — действие владельца |
| Отсутствие ключа = планировщик выключен | отказ по устройству: без секрета расхода нет | тест «без ключа ручка отвечает 503, роутер не вызывается» | ноль |
| `enabled` в `jobs.json` | выключатель через PR | тест «`enabled: false` — ручка отвечает 403» | ~5 минут до остановки |
| Один старт в UTC-час (`UNIQUE(job, slot)`) и один запуск в полёте | повторный или одновременный вызов ручки не порождает второго запуска | тесты «второй вызов в тот же час — 409», «два одновременных — один запуск» | ноль |
| Потолки цикла: 8 кругов, 120 с, 1024 токена ответа, 8 КБ на результат | верхняя граница одного запуска | тест потолка кругов | ноль |

Отвергнуто: кнопка на публичной странице (включает обратно любой), только
арифметика `max_tokens` (меняется при любой настройке и не имеет строки в
`/v1/spend`), общий ключ `agents` (расход по расписанию сливается с расходом
дней; память владельца: лимиты — на приложение).

Что гейт `compliance` может проверить сам: мутации трёх тестов выше;
`grep -c scheduler router/config/apps.json`; после выкатки — строка
`scheduler` в `admin.js spend`.

## Вопрос 2. Где планировщик и кто его останавливает

Первая редакция ADR выбирала таймер `setInterval` в процессе `agents`
(прецедент — две уборки в `agents/server.js`). Владелец решил иначе:
«делай cron — это более стандартный механизм»; оркестратор выбрал форму —
контейнер в compose, не хостовой `crontab` — и разделение ролей: cron
решает «когда», всё остальное в `agents`. Итог — ADR, п. 6.

- **Хостовой `crontab`:** вне репозитория, не едет выкаткой, правится по
  ssh вне закрытого списка, невидим с экрана. Отвергнут.
- **Cron-контейнер с исполнением внутри:** повторяет клиент роутера,
  SQLite, события и SSE `agents`. Отвергнут — у cron осталось «когда».
- **Таймер в процессе `agents`:** дефект планировщика или его остановка
  задевают дни 6–15 — общий процесс. Отклонён владельцем; cron этот
  недостаток снимает: `docker compose stop cron` дней не касается.
- **Cron-контейнер + ручка в `agents`** — выбран. Что подтверждено по
  исходнику busybox и конфигурации Alpine (ADR, «Проверено лично»):
  каталог crontab перечитывается по mtime — правка `deploy/cron/` доезжает
  `git reset` без пересоздания контейнера; окружение заданиям не
  передаётся — ключ через файл `/run/agent.key`, записанный на старте из
  `env_file`; вывод задания перехватывается для `sendmail` — `tick.sh`
  пишет в `/proc/1/fd/1`; расписание по `localtime()` — образ без
  `tzdata`, то есть UTC, и `tick.sh` печатает `date -u` и `date` рядом,
  чтобы расхождение было видно в `docker compose logs cron`.

Ручка `POST /v1/jobs/:job/trigger` — под `AGENT_KEY`, как весь `/v1/*`.
Одновременные вызовы: проверка «в полёте», счётчик суток и `INSERT` со
слотом `UNIQUE(job, YYYY-MM-DDTHH)` идут одним синхронным шагом до первого
`await` — второй вызов получает `409`, третьего запуска не бывает даже после
перезапуска `agents` (слот в базе). Пропущенный тик теряется: догона нет.
Выкатка `agents` посреди запуска — строка `running` без `finished_at`
помечается `interrupted` при старте.

Три уровня выключения: PR (`enabled: false` → `403`, или снятая строка
crontab → тиков нет; делает агент, класс A); по устройству (нет
`ROUTER_APP_KEY_SCHEDULER` → `503`, модель не вызывается); аварийно —
`docker compose stop cron` по закрытому списку, агент или владелец; дни
6–15 живы.

Конвейер: у `cron` нет `Dockerfile`, это не единица выкатки — как `caddy`.
Матрица, ожидание `healthy` и «Проверка живого сайта» её не видят, `up -d`
поднимает из `compose.yml`, образ тянется при первом `up`. Семь мест
конвейера не трогаются; проверка образа — шаг CI фазы 4 (`docker run` по
digest: `wget --help` содержит `post-data`, `crond --help` отвечает).

## Вопрос 3. Куда уходит сводка

| Вариант | Цена | Итог |
|---|---|---|
| Почта | почты нет и не будет в этой итерации | нет |
| Только на экран при открытии, из памяти | запуск в памяти живёт 10 минут; между сроками экран пуст | нет |
| SQLite `jobs.db` + страница дня 18 + SSE для идущего запуска | таблица, две ручки, уборка по числу строк | **выбрано** |

Что хранится: текст сводки, трейс JSON, токены, `budgetLeft` из ответа
роутера. Чего нет: адресов (посетителя у запуска нет), запросов посетителей
(вход фиксирован в `jobs.json`). Последние 50 запусков; при 6 в сутки — около
восьми дней истории.

## Вопрос 4. Три экрана или один

Дни сдаются порознь, у лендинга и страницы прогресса — строка на день,
конвейер выкатки и `Caddyfile` считают единицами. Один экран с режимами
сломал бы это за экономию одной раскладки. Три единицы `days/day18..20`;
общий элемент — запись трейса по правилам консоли дня 16 (сырое тело,
переключатель отступов, метка с байтами и миллисекундами) — копируется, как
копируются лимитеры дней. Цена: три раскладки, три `design-review`, семь мест
конвейера на каждую.

## Вопрос 5. Граница runtime-зависимостей

Клиенту SDK закрыт независимо от решения: ADR `2026-09-23-1227` вынес SDK в
отдельную единицу именно затем, чтобы дерево npm не оказалось в контейнере с
`ROUTER_APP_KEY`. Значит клиент в `agents` рукописный при любом раскладе.

Сервер без SDK стоит ~150 строк на единицу и теряет: валидацию схем (`zod`)
— вместо неё проверки руками, как в `days/*/env.js`; сессии и SSE-поток —
не нужны (день 16 тоже без сессий); ресурсы и промпты — не нужны;
совместимость с чужими клиентами — не нужна, серверы внутренние. Что
теряется по-настоящему: независимая реализация протокола на стороне
сервера. Возмещение — служба дня 16 третьим сервером (ADR, п. 4): наш
клиент обязан пройти `initialize` и `tools/call` против SDK.

Расширение исключения на новые единицы стоило бы нового ADR, правки стража
в `ci.yml`, двух деревьев npm в образах и `npm audit` в двух матрицах — и не
дало бы SDK клиенту.

## Вопрос 6. SQLite

- **Где:** `jobs.db` на томе `agents_data` рядом с `sessions.db`; свой файл,
  чтобы не трогать `migrate()` и 30-часовую уборку диалогов. Файлы дня 19 —
  `files.db` на новом томе `mcpstore_data`.
- **Выкатка:** `deploy.yml`, шаг «Выкатка», — `git reset --hard origin/main`
  и `docker compose up -d --remove-orphans`; именованные тома не
  затрагиваются, `rsync --delete` в этом репозитории нет (проверено по
  workflow). Условие про `rsync` из `zpq-ai` сюда не относится.
- **Кто чистит:** `jobs.db` — сам планировщик при записи (оставляет 50);
  `files.db` — сервер `mcpstore` тиком раз в 10 минут (30 часов) и вытеснением
  сверх 200.
- **I-10:** адресов ни в одной таблице нет; текст запроса посетителя дня 19
  попадает в имя и содержимое файла на 30 часов — та же норма, что у
  переписки дня 7. Это решение владельца № 5 в статусе ADR.

## Вопрос 7. Несколько контейнеров и имя сервера

Публиковать наружу не нужно: к серверам ходит только хост. Даже если бы
понадобилось — вход `zpq` отдаёт весь хост `challenge.zpq.ai` во внутренний
Caddy (`zpq-ai/deploy/Caddyfile:111-117`), и правка была бы здесь, не в
`zpq-ai`. Новые серверы — в сети `tools` вместе с `agents`; без ключа,
потому что достижимы только из неё (страж сетей держит).

Имя сервера на экране — из реестра хоста (`agents/config/mcp-servers.json`)
и из `serverInfo.name` ответа `initialize`; оба идут в событие `rpc`.
Расхождение реестрового и объявленного имени — само по себе предмет показа.

Служба дня 16 третьим сервером: `agents` не видит имя `mcp` (сеть `mcp`
отдельная), `fetch` в Node 22.12 не даёт подменить `Host` (спайк ниже),
поэтому — алиас `challenge.zpq.ai` у `caddy` в сети `default`. Хост зовёт
`http://challenge.zpq.ai/mcp`, Caddy применяет свой блок `/mcp` с
`header_up X-Forwarded-For {client_ip}` — лимитер службы видит адрес
контейнера `agents`, одно окно на 60/мин и 600/час, сводке хватает.

## Вопрос 8. Чего в плане не хватает

Прямо, по убыванию цены:

1. **Роутер не умеет `tool_use`.** `input` — строка, адаптер строит одно
   сообщение, блоки `tool_use` теряются в склейке `text`. Без PR в роутер
   цикл невозможен. Это самый дорогой пункт плана, и в мыслях владельца его
   нет.
2. **`agents` не видит `mcp`** — сеть заведена именно так; решение — алиас,
   не расширение сети.
3. **Ключ `MCP_KEY` для хоста** — копия в `agents.env` требует новой строки
   закрытого списка; принимается вместе с ADR.
4. **Живая проверка выкатки уронит внутренний сервер:** шаг «Проверка живого
   сайта» исключает только `router` и `agents`; `mcpnews`/`mcpstore` без
   публичного `/healthz` — красная выкатка. Седьмое место конвейера.
5. **Реестр агентов требует `taskClass`** — цепочка дня 19 без модели его не
   имеет.
6. **Правило «текстов в событиях нет»** (ADR `2026-09-09-0854`) противоречит
   требованию показывать сырой JSON-RPC — снимается для стадии `rpc` явно.
7. **`stop_reason: max_tokens` с `tool_use`** — обрезанный ввод инструмента
   разбирается как валидный; исполнять нельзя.
8. **Имена инструментов с точкой** (`clock.now`) не проходят ограничение
   имени инструмента API — нужна таблица соответствия.
9. **Инъекция через результаты инструментов** в дне 20 при наличии
   пишущего инструмента; ущерб ограничен построением `mcpstore`.
10. **Источник новостей:** архив лент проекта живёт внутри `agents` и с
    сервера недоступен; HN Algolia даёт шум по запросу `startup`.
11. **Память контейнера `agents`** без предела, а в нём теперь ещё и
    планировщик с трейсами по 64 КБ на тело.
12. **Прерванный выкаткой запуск сводки** — нужна пометка при старте
    `agents`, иначе строка `running` висит вечно и ручка вечно отвечает
    `409 busy`.
13. **Busybox `crond` не передаёт окружение заданиям и отдаёт их вывод
    `sendmail`** — ключ и журнал в cron-контейнере требуют обходов в
    `tick.sh`; без них первый тик молча не дошёл бы до ручки.

## Арифметика расхода

Haiku 4.5: $1 за миллион на входе, $5 на выходе (`providers.json`). Запуск
сводки: системный промпт и определения ~1,5 K токенов; до 8 кругов, вход
растёт на результат инструмента (до 8 КБ ≈ 2 K токенов) каждый круг;
верхняя граница входа ≈ 8 × (1,5 + 8 × 2) K ≈ 140 K токенов → $0,14, выход
8 × 1024 → $0,04; **худший запуск ≈ $0,18**, ожидание в 3–5 раз меньше
(сводка укладывается в 3–4 круга). Потолок: 6 × $0,18 ≈ $1,1 > $0,5 — то
есть при худших запусках роутер остановит планировщик на третьем, и это
задумано: денежный потолок первичен, счётчик стартов вторичен. День 20 у
посетителя — те же границы за счёт приложения `agents`; день 19 — модели
нет, $0.
