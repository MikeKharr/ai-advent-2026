# Атлас проекта: vault Obsidian и публичная витрина схемы проекта — проект решения

Роль `architect`. Основа: `AGENTS.md`, `agent_docs/invariants.md`,
`agent_docs/architecture.md`, `agent_docs/guides/agent-roles.md`,
`.agents/skills/day-cycle/SKILL.md`, ADR `2026-09-10-0426`, `2026-09-07-1525`,
`2026-09-08-0205`, `2026-09-07-1510`, `deploy/Caddyfile`, `deploy/compose.yml`,
`.github/workflows/*.yml`. Решение — ADR `2026-09-10-0550-project-atlas.md`
(статус «Предложено»).

## Задача

Владелец хочет видеть текущую схему проекта «в формате Obsidian»: архитектуру,
гейты, роли, граф ADR и ключевые правила, которые дают преимущество в
разработке. Допускается отдельный сервис на VPS и отдельный публичный адрес как
витрина для демонстрации. Проектируются два слоя, оба:

- **Vault** — настоящее хранилище Obsidian: заметки с фронтматтером,
  `[[wikilinks]]`, теги. Открывается в приложении Obsidian.
- **Витрина** — публичная страница `challenge.zpq.ai/atlas/`: интерактивный
  граф, панель заметки, обратные ссылки, проход по фазам цикла и гейтам.

Рабочее имя — **атлас** (`atlas/`): «витрина» в глоссарии уже занята копией
решений в Google Drive.

## Неоднозначности и допущения

1. **«Формат Obsidian» для витрины** прочитано как «модель Obsidian»: граф +
   заметка + обратные ссылки + теги, а не пиксельная копия приложения.
2. **«Показать всё»** прочитано как «все типы узлов, перечисленные владельцем»,
   с полным текстом документа не в витрине, а по ссылке на GitHub (см. развилку 2).
   Обоснование ниже, в составе витрины.
3. **Витрина не ходит в LLM.** Ничего в задаче не требует генерации на лету;
   расход — ноль. Проверено по каждому виду узла: всё извлекается из файлов.
4. **Пути в вендорных скиллах** (`.agents/skills/`) показываются именем и
   описанием из фронтматтера, не полным текстом: это чужой материал (MIT), и
   его полный текст в атласе не нужен.
5. **Единица деплоя** названа `atlas`, по образцу `router` и `agents`.

### Выбор

**Вариант 2.** Vault — производное от `agent_docs/`, по той же логике, что
витрина в Drive: источник истины один, копия несёт блок происхождения (тот же
формат, что в гайде `drive-sync`, удалённом по ADR `2026-09-11-0513`: путь, sha, время, «копия только для
чтения»). Выход — `atlas/dist/vault/`, каталог в `.gitignore`; Obsidian
открывает его после `node atlas/build.js`. Коммитить ли производный vault —
развилка 1 (рекомендация: нет).

Устройство vault:

```text
atlas/dist/vault/
├── adr/<id>.md            копия ADR; цитаты заменены на [[adr/<id>]], [[invariants/I-4]]
├── history/<id>.md        копия записи истории
├── design/<id>.md         спецификации раскладок и корпус
├── guides/<name>.md       гайды, architecture, invariants (целиком), AGENTS
├── invariants/I-N.md      по заметке на инвариант: текст пункта + ссылка на источник
├── roles/<name>.md        роль: модель, усилие, предзагруженные скиллы, «владеет / никогда»
├── days/dayN.md           день: название с лендинга, маршрут, зависимости, тома
├── services/<name>.md     router, agents, caddy, site
├── skills/<name>.md       имя и описание из SKILL.md, кто предзагружает
├── classes/A.md, B.md, C.md
├── phases/01-…10-….md     фазы /day-cycle
└── index.md               точка входа: гайды, первая фаза, три класса гейтов
```

Тома, ярусы моделей и внешние сервисы в vault — **не заметки**, а текст
внутри заметок дней, сервисов и ролей. Поэтому граф, который владелец видит в
Obsidian, и `graph.json` витрины — разные графы: в Obsidian нет узлов
`volume`, `tier`, `external` и рёбер `mounts`, `tier`, `calls`, `image`,
`publishes`. Это осознанно — заметка «том `router_data`» ничего не сказала бы
сверх строки в заметке роутера, — и на этапе 3 расхождение не должно
удивлять.

Фронтматтер каждой заметки: `type`, `id`, `title`, `date`, `status` (для ADR),
`day` (если определён), `tags` (`type/adr`, `status/accepted`, `day/8`).
Фронтматтер — **первый** блок файла, блок происхождения — сразу за ним, без
пустой строки: Obsidian читает фронтматтер только первым блоком, а гайд
`drive-sync.md` требовал блок первым потому, что писался для Drive, где
фронтматтера нет. За формой блока — гайд; позиция — после фронтматтера.
Ярлык времени — `СИНХРОНИЗИРОВАНО: на коммит от <дата>`: копия не
выкладывается однократно, а пересобирается по требованию и есть чистая
функция от коммита. Замена цитат — только в копии:
`` ADR `2026-09-10-0426` `` → `[[adr/2026-09-10-0426]]`,
`` `I-4` `` → `[[invariants/I-4]]`, `` `compliance` `` → `[[roles/compliance]]`,
`` `development-history/2026-09-09-2135` `` → `[[history/2026-09-09-2135]]`.
`.obsidian/` не генерируется — Obsidian создаёт его сам, там состояние окна.

`.canvas` (JSON Canvas) для топологии деплоя — развилка 3; в минимальный объём
не входит.

## Слой (б): витрина

### Как получить витрину

| | A. Quartz v4 (SSG для vault'ов) | B. Свой генератор без зависимостей | C. Только vault + Obsidian у владельца |
|---|---|---|---|
| Что даёт из коробки | Граф, backlinks, поиск, wikilinks, рендер markdown, всплывающие превью | То, что напишем: граф, панель, backlinks, фильтры, поиск по заголовкам | Ничего публичного |
| Зависимости | Клонируемый репозиторий (не npm-пакет), Node ≥22, npm ≥10.9.2, **51 прямая зависимость** (remark/rehype, Preact, D3, esbuild), транзитивно — сотни; конфигурация на TypeScript | Ноль. Node 22, `node:fs`, `node:test` | Ноль |
| ADR `2026-09-07-1525` (ноль зависимостей) | Буква ADR — про runtime; статика без runtime-зависимостей ей не противоречит. **Дух ADR — про проверяемость**: агент должен уметь собрать и запустить до передачи. Обоснование ADR — «код проверен до передачи» и «меньше supply-chain поверхности» — применимо к сборке целиком | Совпадает и с буквой, и с духом | Совпадает |
| Гейт ADR `2026-09-08-0205` (проверка стороннего кода до установки) | Принцип гейта — «код, исполняемый с правами разработчика, проверяется до установки» — распространяется на npm-дерево естественно: `postinstall` исполняется на машине владельца, где лежат ключ выкатки и tailnet к проду. Семантическое ревью сотен пакетов невозможно; остаётся `npm ci --ignore-scripts` в CI, lockfile, `npm audit` — и запрет `npm i` на машине владельца. Тогда агент **не может** собрать витрину локально, а `design-review` — увидеть её до мержа | Проверять нечего | Проверять нечего |
| Объём нашего кода | Извлечение графа всё равно наше (~300 строк): Quartz ест vault, а vault — производное. Экономится страница | ~600 строк Node (извлечение, раскладка, vault, статика) + ~400 строк страницы + ~200 строк тестов | ~400 строк (извлечение + vault) |
| Сопровождение | Обновления Quartz — слияние чужого репозитория; поломки при мажорных версиях (v5 уже вышла) | Наш код, наш стиль, наши тесты | Минимум |
| Итог | Отклонить: цена — потеря локальной проверяемости и неревьюируемое дерево кода на машине с ключами | **Выбрать** | Не закрывает задачу владельца |

Рассмотрено и отклонено без таблицы: Obsidian Publish (платный хостинг у
Obsidian, не под `challenge.zpq.ai`, вне CI), Perlite (PHP-сервис, читает vault
на лету — серверная работа, которая не нужна), Digital Garden (Eleventy +
Netlify — те же npm-издержки, что у Quartz, плюс внешний хостинг).

### Где хостить

Нужна ли серверная работа? **Нет.** Поиск — по заголовкам и описаниям на
клиенте (граф ~170 узлов, `graph.json` порядка 150–200 КБ до сжатия), граф
предрассчитан при сборке, живых данных нет. Отдельный контейнер как
«сервис» не оправдан — это прямой ответ на вопрос владельца.

Остаётся вопрос доставки статики, и здесь три способа:

| | 1. Контейнер статики `atlas` | 2. Сборка на сервере при выкатке | 3. Коммит `site/atlas/` в git |
|---|---|---|---|
| Как | `atlas/` — единица деплоя как `router`: CI собирает `atlas/dist/site`, образ `caddy:2-alpine` + файлы + `respond /healthz 200`, GHCR, пин тега, `handle_path /atlas/*` | В шаге выкатки после `git reset` — `docker run node:22-alpine node atlas/build.js`, выход в `site/atlas/` (ignored), отдаёт существующий `file_server` | Генерация локально, результат в git, `file_server` отдаёт |
| Новые понятия в конвейере | Ноль: ещё одна единица | Сборка на проде — нарушает «сервер только тянет образ» (`architecture.md`) | Производный артефакт в git: шум в каждом docs-PR, дрейф |
| Правки | `ci.yml`, `deploy.yml` (правило `detect`), `compose.yml` (+сервис без `env_file`), `Caddyfile` (+2 строки), лендинг (+1 ссылка) | `deploy.yml` (шаг сборки), `on.paths` | `.gitignore`, `on.paths` |
| Откат | Предыдущий тег, как у дней | Повтор выкатки с прошлого sha | `git revert` |
| Стоимость | ~10 МБ RAM, ноль CPU в простое | Ноль | Ноль |
| Ручной шаг первого деплоя | `docker compose restart caddy` (как у каждого нового маршрута) | Нет | Нет |

**Выбор — 1**, с оговоркой словами: контейнер не делает серверной работы,
это файлы за тем же образом Caddy, что уже стоит на сервере. Он выбран
потому, что конвейер уже умеет «единицу деплоя» и ничему новому учить его не
нужно; вариант 2 переносит сборку на прод, вариант 3 кладёт производное в
git. Если владелец возражает против контейнера как такового — развилка 4.

Страница отдаётся под `handle_path`, значит все пути в ней относительные,
без `<base>` — то же правило, что у дней (`guides/new-day.md`).

`compose.yml` читается узким парсером подмножества (двухпробельные отступы,
`services:` / `depends_on:` / `volumes:` / `env_file:`), а не полноценным
YAML: тест-страж проверяет, что найдено ровно то число сервисов и томов, что
в файле, — расширение файла за подмножество ломает тест, а не граф молча.

### «Правило → его следы»

Это и есть демонстрация преимущества: не список правил, а правило с его
следами. Реализуется рёбрами `fired` и `relies` без ручной работы.

Правило `fired` (уточнено после ревью этапа 1; детализация решения, само
решение ADR `2026-09-10-0550` п. 5 не меняется):

1. **Единица привязки — строка** записи истории. Строка таблицы (начинается
   с `|`) — одна единица целиком: роль в одной ячейке, признак в другой —
   это одно срабатывание (`2026-09-09-2135`, строки 43–44). Прозаическая
   строка делится на фрагменты по `;` и по концу предложения; роль и признак
   должны стоять **в одном фрагменте** — иначе «Compliance — вето нет;
   reviewer —» приписывал бы reviewer чужое вето.
2. **Признак** — слово с кириллическими границами, без учёта регистра:
   `вето`, `блокирующ…`, `находк…`, `правки`, `переделать`. Границы
   обязательны: `grep -i вето` ловит «отв**ето**в», «прив**ето**м»,
   «запр**ето**» — так возникло ложное «12 записей с вето» в первой редакции
   этого документа; записей с отдельным словом «вето» — 10, и две из них
   говорят «вето нет».
3. **Роль** — имя из `.claude/agents/` без учёта регистра («Compliance
   вынес вето», «Reviewer дал ПРАВКИ»), не внутри пути и не как часть
   `design-review`.
4. **Отрицание отбрасывается**: фрагмент с «вето нет», «блокирующих нет»,
   «без вето», «нет находок», «не ставил / не наложил / не дал» ребра не даёт.
   Проверка на репозитории: строки `2026-09-09-1535:88` и `2026-09-09-1624:50`
   рёбер не дают.
5. **Несколько срабатываний в одной записи — несколько рёбер**, по одному на
   строку, без дедупликации по паре «роль → документ»: два вето в таблице
   `2026-09-09-2135` — два следа, и счётчик витрины считает следы, а не
   записи. Записи считаются отдельно, как число различных концов рёбер.
6. Выдержка — **только показ**; единицу привязки задаёт п. 1, и она
   остаётся строкой. Показывается предложение с ролью и признаком целиком,
   собранное через переносы строк внутри абзаца, или строка таблицы целиком;
   не обрывок по переносу. Расширять до предложения саму единицу нельзя —
   проверено: единица «предложение с делением по `;`» даёт ложный след `qa`
   в `2026-09-10-0427:40` («Reviewer дал ПРАВКИ — диаграмма приведена к
   day-cycle (гейты параллельно после qa)…» — `qa` здесь внутри пояснения,
   что исправили, а не работа гейта), а без деления по `;` — три ложных
   следа `design` и `reviewer` на вето compliance из `2026-09-09-1907:47`.
7. Номер строки следа — строка, где начинается **совпавшая единица**, а не
   предложение вокруг неё: иначе след `design` из `2026-09-09-1624:51`
   встал бы на строку 50 «Compliance — вето нет», которую критерий этапа 1
   требует держать пустой. Следствие для витрины: номер строки и первые
   слова выдержки могут расходиться, переход по номеру приводит в середину
   цитаты — лечится подсветкой совпавшего фрагмента; это презентация,
   требование к этапу 3, а не правило.

Что правило даёт на `main` (пересчитано скриптом по 31 записи; числа
меняются с каждой новой записью и приведены как проверка правила, не как
константы): `compliance` — **11 следов в 8 записях**; `reviewer` — 2 в 2;
`design` — 1 в 1; всего 14 рёбер. Известный предел, который не чинится
регулярным выражением: записи зовут ревьюера «ревью кода» и «два блокера»
(`2026-09-08-1826:78`), а вердикты design-review — «правки по дизайну» без
имени роли; такие следы у `reviewer` и `design-review` не появятся, и
витрина обязана называть счётчик «следы по имени роли», а не «все находки».
Псевдонимы ролей в правило не вводятся: это уже разбор прозы, а не извлечение
по соглашению.

Остальные следы:

- У узла `I-4` — все документы, которые на него опираются (`relies`), среди
  них записи, где проверка «лимит до вызова» ловила дефект.
- У узла ADR `2026-09-10-0426` — поправка после вето compliance: запись
  `2026-09-10-0427` цитирует ADR (`cites`) и несёт след `compliance` (`fired`).
- Стартовая панель витрины — сводка по рёбрам `fired`: сколько следов у
  каждой роли-гейта и в скольких записях, по дням. Подпись — «следов», не
  «вето» и не «находок»: правило считает строки, а не события (см. «Панель
  заметки»).

Проход «по гейтам и ролям» — узлы `phase` 1→10 в панели «Цикл дня»: у каждой
фазы — роль, класс гейтов, критерий выхода, пометка человеческого гейта, и
ссылка на следующую фазу. Адрес узла — в `#`-фрагменте (`#adr-2026-09-10-0426`),
чтобы на любой узел можно было дать ссылку.

### Панель заметки

Заголовок, тип, статус, дата, день; факты (у роли — модель, усилие; у дня —
маршрут, зависимости); выдержка — первый абзац раздела «Контекст» (ADR) или
«Что сделано» (история); исходящие ссылки; обратные ссылки; раздел
«Следы в записях» (рёбра `fired`); ссылка на файл в GitHub.

Два презентационных требования к разделу следов — для `design` и для vault:

- **Заголовок и подпись называют отношение, а не вывод.** Правило находит
  имя роли рядом с признаком гейта, и только это; среди следов есть
  «Compliance дал „одобрено с условиями“» (гейт не сработал) и «его зона
  вето» (зона ответственности, не срабатывание). Поэтому заголовок —
  «Следы в записях», подзаголовок — «имя роли рядом с признаком гейта»;
  «Где сработало» и любые формы «сработал» / «вынес» в заголовках и подписях
  запрещены — врёт не число, а глагол.
- **Выдержка — целая фраза или строка таблицы**, не обрывок по переносу
  строки: «…+ compliance,» и «…код — „нужны правки“. Существенное:» —
  дефекты. Прозаический след — предложение с ролью и признаком, собранное
  через переносы внутри абзаца; табличный — строка целиком. Номер строки у
  следа — по совпавшей строке, не по началу предложения (п. 7 правила),
  поэтому в панели совпавший фрагмент выделяется внутри выдержки — иначе
  переход по номеру приводит в середину цитаты.

Требование к подписям счётчиков — для `design` при раскладке панели и
стартовой сводки. Рёбра `fired` — **следы, а не события**: одно вето может
дать два следа (`2026-09-08-1826`, строки 78 «вынес вето» и 114 «вето снято
решением владельца»), а след может стоять на фразе, где вето не выносилось
(`2026-09-08-1430:44` — «его зона вето»). Поэтому подпись «N вето» или
«N находок» будет ложью, а «N следов по имени роли в M записях» — правдой.
Число событий из текста не извлекается, и витрина его не показывает; рядом
со счётчиком — сами выдержки, чтобы читатель видел, что именно посчитано.

Полный текст документа в витрине не рендерится:
рендер markdown без зависимостей — самый большой кусок кода при наименьшей
ценности, GitHub делает это лучше, а в vault полный текст есть и так.
Развилка 2.

### Граф

Раскладка считается при сборке (детерминированная силовая, фиксированный
seed): картинка стабильна между сборками, клиенту остаётся нарисовать на
`canvas` и дать панораму, масштаб, наведение, клик. Координаты — поля `x`,
`y` узла в `graph.json`, единичный квадрат `0…1`, тип `number`, шесть знаков
после точки; они появляются в объёме этапа 3 (этап 1 их не делал — это
пропуск в его критериях, а не решение), и на клиенте силовая модель не
считается. Требование к раскладке
экрана (роль `design`): вид по умолчанию — не «клубок» из 170 узлов и ~600
рёбер, а окрестность выбранного узла (1–2 шага) плюс фильтры по типу; полный
граф — по явному включению. Цвета типов узлов — расширение палитры корпуса,
заданное в спецификации раскладки, не ad hoc.

## Актуальность

1. **Сборка при изменении источников.** `on.paths` у `ci.yml` и `deploy.yml`
   дополняются `agent_docs/**`, `.claude/agents/**`, `.agents/skills/*/SKILL.md`,
   `AGENTS.md`, `atlas/**`; правило `detect` выдаёт единицу `atlas` при diff в
   любом из них, а также в `deploy/compose.yml` и `deploy/Caddyfile`. Сборка
   образа `atlas` — двумя шагами: `node atlas/build.js` в workflow, затем
   `docker build atlas` (контекст — каталог единицы, как у остальных; в образ
   копируется только `atlas/dist/site`).
2. **Механический гейт на битые ссылки.** `node atlas/build.js --check` —
   шаг в `docs-guard.yml` (проверка `guard` уже обязательна для мержа):
   падает при цитате на несуществующий документ, `I-N` вне I-1…I-12, роли
   вне `.claude/agents/`, сервисе overlay, которого нет в compose, внешнем
   узле без единого ребра. Не проверяется то, что документ показывает как
   образец, а не ссылку: содержимое блоков кода, текст в двойных обратных
   кавычках, заглушки шаблонов (`YYYY-MM-DD-HHMM`) — образец от цитаты
   отличается формой записи, и та же цитата, написанная обычным образом,
   проверяется. Падает закрыто с первого дня: baseline чист (262/262,
   134/134).
3. **Следствие, которое надо принять:** после этого каждый мерж документов
   (класс C) вызывает выкатку единицы `atlas`. Дней это не касается, но
   деплой из docs-PR — новое поведение. Альтернатива — `workflow_dispatch`
   вручную — развилка 5.
4. **Vault** пересобирается той же командой; коммита не требует.

## Проверка по ограничениям

- **I-11.** Источник — git; и vault, и витрина — производные с блоком
  происхождения (sha в подвале страницы и в каждой заметке vault).
- **I-2, I-1, I-3.** Репозиторий публичен, витрина не расширяет публикуемое:
  входы — явный список путей, `deploy/*.env`, `.env*`, `temp/`, `logs/` не
  читаются никогда (на машине владельца такие файлы есть — `settings.json`
  запрещает их чтение агенту); `baseUrl` провайдеров не выводится; тест
  сборки подкладывает в копии репозитория `deploy/secrets.env` с маркером и
  проверяет, что маркера нет в выходе; второй тест грепает выход по
  образцам `sk-ant-`, `gsk_`, `BEGIN OPENSSH`, адресам `100.x`.
- **I-12.** Ничего в `agent_docs/adr/` не правится; переписываются копии.
- **noindex.** Заголовок `X-Robots-Tag` стоит на весь домен (`Caddyfile`,
  `development-history/2026-09-08-1245`) и накроет `/atlas/`. Ссылки
  работают, в поиск страница не попадёт — политика домена не меняется.
  Индексируемость — развилка 6.
- **Стоимость.** LLM не вызывается. Сервер: ~10 МБ RAM. Actions: сборка
  <1 с, образ ~30 с, выкатка как у любой единицы.
- **Класс изменения (framework v2).** Генератор, vault, страница — **B**
  (reviewer; UI — `design` до кода, `design-review` перед мержем). Доставка —
  **A**: `deploy.yml` ссылается на `secrets.*` (поправка ADR `2026-09-10-0426`),
  поэтому reviewer + compliance; `compose.yml` и `Caddyfile` едут в том же PR.
  Ссылка на лендинге — C, но внутри PR доставки.
- **Дизайн-корпус.** Действует для новых дней; атлас — не день, но новый
  экран на том же домене: применяются шкалы, палитра, состояния и
  `:focus-visible`, расширение палитры для типов узлов — в спецификации
  `design`. Развилка 7.

генератор с графом, не платформа. Каждый этап — один PR.

Четыре контракта данных, которые страница требует от генератора; это работа
`backend` в объёме этого этапа, формы взяты из раскладки, чтобы `backend` и
`frontend` не разошлись:

1. **Координаты.** Каждый узел `graph.json` несёт `x` и `y`: единичный
   квадрат `0…1`, тип `number`, шесть знаков после точки; детерминированная
   силовая раскладка с фиксированным seed. Проверка: две сборки одного
   коммита дают байт-в-байт одинаковый `graph.json`.
2. **Совпавший фрагмент.** Ребро `fired` несёт
   `marks: { unit, role, sign }` — полуинтервалы `[start, end)` в единицах
   кода UTF-16 по строке `excerpt` **до** любой обработки разметки; `unit` —
   совпавшая единица по п. 1 правила, `role` и `sign` лежат внутри `unit`;
   у строки таблицы `unit` — вся выдержка. Считается там же, где найден
   след (`atlas/lib/fired.js`); второго экземпляра правила в браузере нет.
   Проверка: для каждого из 14 рёбер `excerpt.slice(...role)` равен имени
   роли без учёта регистра, `excerpt.slice(...sign)` — слову-признаку.
3. **Выдержка без предела.** Для рёбер `fired` `clip` не применяется (см.
   поправку к этапу 2 выше).
4. **Происхождение.** `graph.json` несёт верхнеуровневое поле
   `provenance: { sha, dirty, date }`: `sha` — полный 40-значный hex
   коммита `HEAD`, `dirty` — `boolean`, есть ли несохранённые правки в
   рабочем дереве на момент сборки, `date` — дата коммита `ДД.ММ.ГГГГ`.
   Страница ставит их в подвал (раскладка, раздел «Подвал») и **пинит ссылки
   на GitHub к `sha`**, а не к `main` — иначе ссылка со старой сборки вела
   бы на другой текст. Поля нет — подвал говорит «из ветки `main`» без
   выдуманной даты, ссылки ведут на `main`. Раскрытия поле не несёт: sha и
   дата публичного репозитория; `dirty` в проде полезен — если образ соберут
   из непроверенного состояния, подвал это скажет. Тот же `sha` и тот же
   признак пишет блок происхождения vault — источник один.

Проверка: `/design-review` — `ГОТОВО`; локально `npx --no-install serve`
не нужен — `node atlas/build.js --serve` поднимает `node:http` на статике;
`#`-ссылка открывает узел; клик по `compliance` показывает 11 следов с
целыми выдержками (то же число, что в критериях этапов 1 и 2 — оно берётся
из `graph.json`, а не из текста спецификации); относительные пути, `<base>`
нет. Размер: факт на реализации — `dist/site` 271 КБ сырых (`graph.json`
183, `app.js` 66, `style.css` 18, `index.html` 4), ~59 КБ gzip; план
«≈250 КБ, страница ≈50 КБ» поднят до факта — `app.js` несёт граф, панель,
подсветку следов и разбор двух видов разметки, и 66 КБ без минификации для
этого честная цена. Граница на рост: `dist/site` **до 400 КБ сырых**,
`graph.json` до 250 КБ — узлы прибавляются с каждым днём и записью истории,
и предел должен ловить не сегодняшний размер, а неожиданный скачок
(например, полный текст скилла в узле); превышение — не блокер, а повод
пересмотреть, что попало в `graph.json`.

### Этап 4. Доставка (класс A)

`atlas/Dockerfile` (`caddy:2-alpine`, `respond /healthz 200`), сервис в
`compose.yml` без `env_file`, две строки в `Caddyfile`, правило `detect` и
`on.paths` в `ci.yml` и `deploy.yml`, шаг сборки перед `docker build`, ссылка
на лендинге.

Проверка: CI собирает образ и получает 200 на `/healthz`; после мержа и
`docker compose restart caddy` — `curl -s https://challenge.zpq.ai/atlas/`
200, в ответе заголовок `X-Robots-Tag: noindex`; sha в подвале страницы
равен `git rev-parse main`; docs-PR после этого вызывает пересборку только
единицы `atlas`.

## Развилки за владельцем

1. **Коммитить производный vault** (`atlas/dist/vault/`) или держать только
   генератор. Рекомендация: только генератор; коммит производного — шум в
   каждом docs-PR и дрейф, который придётся ловить ещё одним гейтом.
2. **Полный текст документа в витрине** или выдержка + ссылка на GitHub.
   Рекомендация: выдержка; рендер markdown без зависимостей — самый большой
   кусок кода ради того, что уже делает GitHub и Obsidian.
3. **`.canvas` топологии деплоя** для Obsidian. Рекомендация: не в первый
   объём; тот же вид даёт фильтр «сервисы и тома» в графе.
4. **Контейнер статики или сборка на сервере / копирование по ssh.**
   Рекомендация: контейнер — конвейер его уже умеет; сборка на проде
   нарушает принцип «сервер только тянет образ».
5. **Выкатка атласа при каждом мерже документов** или вручную по
   `workflow_dispatch`. Рекомендация: при каждом мерже — иначе витрина
   отстанет, как отстаёт Drive.
6. **Оставить noindex на `/atlas/`.** Рекомендация: оставить — политика
   домена; ссылка работает и без индексации.
7. **Атлас под дизайн-корпусом** (шкалы, палитра, состояния) или как
   лендинг — вне корпуса. Рекомендация: под корпусом с расширением палитры
   для типов узлов; иначе это второй визуальный язык на домене.
