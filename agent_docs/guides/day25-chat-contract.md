# Контракт хода дня 25

Что сервер обещает странице дня 25 на каждый ход диалога. Решение —
ADR `2026-10-05-0544`, п. 3; код — `agents/src/rag/chat.js`,
`agents/src/staged.js`, `agents/src/rag/retrieve.js`, `agents/src/rag/cited.js`.
Этот файл — контракт, а не пересказ ADR: расхождение кода с ним — дефект.

## Что взято из дня 15 и не переписано

Профили и шесть правимых промптов, диалог с рабочей памятью, машина этапов с
паузой на границе этапа, события запуска потоком, журнал этапов CSV и текст
промпта каждого круга — всё это код дней 13–15 (`agents/src/sessions.js`,
`memory.js`, `context.js`, `staged.js`, `runs.js`, `stage-log.js`). День 25 —
та же машина с четвёртым швом `rag`; копии `staged.js` нет.

## Этапы хода — восемь

`intake → assemble → retrieve → prepare → answer → verify → replenish → deliver`
(`RAG_STAGES`). Новый — третий; остальные — таблица дня 15 (`PREPARE_STAGES`).

`retrieve` стоит **до** `prepare` и `answer`, и внутри него первым идёт поиск,
а не переписывание. Отсюда обещание источников: хода без поиска не бывает, а
отказ поиска — отказ хода **до единого вызова модели** (I-4).

Возврат с `verify` идёт на `assemble`, значит `prepare` проходит на каждом
круге — у круга своя строка `run_prompts`. **А `retrieve` на кругах ≥ 2 не
повторяется:** у него ворота по `ctx.retrieved`, и круг берёт фрагменты
первого круга как есть. Вход отбора от круга не зависит (реплика, состояние
задачи, прошлые ходы — замечаний проверки в нём нет), а без ворот каждый
лишний круг стоил бы ещё переписывание, ещё реранкер и ещё **два
эмбеддинга** — то есть `4×кругов + 2` вызова вместо принятых 6–7 (находки
`reviewer` Б1 и `compliance` Б1 к PR #317).

## Вызовы модели — шесть на ход при одном круге

| № | Что | Класс | Потолок ответа | Схема |
|---|---|---|---|---|
| 1 | переписывание реплики в поисковый запрос (всегда, Р6(б)) | `summarize` | 500 | нет |
| 2 | реранкер: оценки десяти кандидатам | `layered_dialogue` | 200 | `ratings` |
| 3 | ответ посетителю | `layered_dialogue` | `maxTokens` хода | ответ дня 24 |
| 4 | проверка ответа (`kimi-k2.6`) | `layered_dialogue` | 400 | нет |
| 5 | пополнение памяти профиля | `summarize` | 400 | нет |
| 6 | состояние задачи (`stage.task`) | `layered_dialogue` | 2000 | `TASK_SCHEMA` |

Потолок шестого вызова **выведен из потолка хранилища**, а не выбран:
`TASK_ANSWER_TOKENS = TASK_STATE_CHARS / 2` (`agents/src/rag/chat.js`), потому
что состояние возвращается ЦЕЛИКОМ и счёт токенов проекта кладёт на знак вне
ASCII половину токена. Прежние 400 покрывали ≈800 знаков: состояние живого
размера (872 знака в прогоне дня 25) обрывалось по потолку, а обрезанный ответ
схемного класса роутер отдаёт отказом без повтора — состояние не обновлялось на
13 ходах из 18. Худший случай расхода вырос на 1600 токенов выхода на ход
(≈$0,008 по цене Haiku); обычный ход платит за фактическую длину состояния,
а не за потолок.

Формула хода, а не только его лучший случай: **`4 + 2×кругов`** вызовов, где
круг — проход «Сборка → Подготовка → Вызов → Проверка». Один круг (вердикт
«принято» с первого раза) — **6 вызовов**; отклонённый вердикт добавляет ещё
ответ и ещё проверку: 8 при `reviewRounds: 2`, 10 при 3. Это машина дней
13–15, и ADR, п. 4, называет её словами «проверка 1–2»; переписывание,
реранкер, пополнение и состояние — **по одному на ход при любом числе
кругов**.

Седьмой вызов сверх формулы бывает ровно в одном случае — сжатие истории при
стратегии «сводка» и наступившем пороге; это вызов дня 11, а не дня 25.

**Эмбеддингов на ход — два** (исходная реплика и переписанный запрос), при
любом числе кругов: они идут в суточные 500 службы `rag`, и счётчик общий с
днём 22, поэтому число здесь — предмет, а не справка.

## Запрос ответа

Блоки в порядке политики (`context.js`, `assemble`):
`<invariants>` → `<personalization>` → `<topic>` → блок стратегии памяти →
`<dialog>` → `<review>` → **`<fragments>`** → **`<task>`** → `<request>`.
Последние два — новые; складывает их `prepare`, и в `run_prompts` они
попадают дословно. Если отбор не оставил ни одного фрагмента, на месте
`<fragments>` стоит `<rejected>` — пути и заголовки отброшенных кандидатов без
текстов (исход «не знаю» дня 24).

Фрагменты, состояние задачи и записи памяти — **недоверенные данные**: блок
помечен сведениями, закрывающая метка обезвреживается, запрос стоит
последним. Держит это форма блока — и больше ничто (та же граница, что у дней
22–24; `agent_docs/invariants.md`, абзац о дне 22).

## Результат хода

Сверх полей дня 15 (`answer`, `summary`, `context`, `review`, `layers`,
`rounds`, `stagesPassed`, …):

| Поле | Что |
|---|---|
| `sources[]` | фрагменты, ушедшие модели: `n`, `source`, `section`, `score`, `relevance`, `text`, `truncated`. Номера те же, которыми ссылается ответ |
| `cited[]` | источники, на которые сослалась модель: `n`, `source`, `section` — **из отбора**, плюс `claimedSource`, `claimedSection` — что назвала модель |
| `quotes[]` | `n`, `text`, `verified`, `truncated` — дословность сверена кодом, не моделью; потолок цитаты (300 знаков) держит код, не схема: сверяются первые 300 знаков, и подтверждённая цитата уходит полем `text` обрезанной (`truncated: true`), а неподтверждённая — целиком, как её привела модель (ADR `2026-10-05-1013`) |
| `checks` | `sources_present`, `quotes_present`, `quotes_verbatim`, `cited_exact` |
| `status` | `answered` или `unknown` (поле схемы) |
| `outcome` | `answered`, `unknown_filter`, `unknown_model`, `unsupported` |
| `clarification` | уточняющий вопрос посетителю или `null` |
| `rewritten` | переписанный запрос или `null` |
| `candidates[]` | все кандидаты до отбора: `score`, `relevance`, `kept`, `from` |
| `index` | коммит, стратегия и число фрагментов индекса |
| `task` | состояние задачи после хода: `goal`, `constraints[]`, `terms[]`, `clarifications[]`, `open[]`, `round`, `stored` |

Пустой отбор — отдельный законный исход, а не ошибка: ход успешен,
`sources: []`, `outcome: "unknown_filter"`, в промпте вместо `<fragments>`
стоит `<rejected>`. Обещание дня читается ровно как в ADR, п. 3.5: **у каждого
ответа либо `sources.length ≥ 1`, либо исход «не знаю»** — третьего нет.

Путь и раздел источника берутся из отбора, а не из ответа модели (день 24,
находка `compliance`): выдуманный путь виден полем `claimedSource` и признаком
`cited_exact`, но на экран вместо настоящего не попадает.

Те же `sources`, `cited`, `quotes`, `checks`, `status`, `outcome`,
`clarification`, `rewritten` и `index` лежат в `meta.rag` **реплики агента**:
карточка показывает их и после перезагрузки, когда результата запуска уже нет.

`GET /v1/sessions/:id` отдаёт поле **`task`** — текущее состояние задачи с
`round` и `updatedAt` или `null`. Без него панель «Состояние задачи» исчезала
бы при перезагрузке страницы: результат хода живёт только до обновления.

## Состояние задачи

Таблица `task_state (session_id PRIMARY KEY, profile_id, state, round,
updated_at)`; `state` — JSON по `TASK_SCHEMA`, не длиннее 4000 знаков (потолок
держит `sessions.saveTaskState`: длиннее не пишется вовсе).

- обновляется шестым вызовом на этапе `replenish`, **целиком**, а не дельтой;
- вход этого вызова ограничен: реплика и ответ режутся `TASK_PAIR_CHARS`
  (2000 знаков каждая), иначе вход одного шестого вызова рос бы с потолком
  ответа хода до 32 000 токенов;
- разбор подрезает состояние под потолок хранилища (сначала открытые вопросы,
  затем уточнения, ограничения и термины; цель не трогается) — иначе
  переполнение означало бы «состояние не обновилось вовсе»;
- отказ вызова и неразобранный ответ состояние **не стирают**: прежнее остаётся
  в силе, ход заканчивается ответом, в ленте — предупреждение. Предупреждение
  несёт `providerReason` — причину словами роутера (`reasons[0].reason`), потому
  что `code` у обрыва по потолку токенов и у отказа провайдера один и тот же
  (`all_failed`);
- событие `llm_call` шестого вызова подписано `promptId: 'stage.task'` и
  отпечатком того текста, который ушёл модели, — хотя сам вызов идёт внутри
  этапа `replenish` (поле `data.state` у него поэтому `replenish`);
- уходит в промпт переписывания **следующего** хода вместе с двумя прошлыми
  парами реплик — поэтому «а почему так?» ищется по цели разговора;
- промпт `stage.task` — шестой правимый промпт профиля (`PROFILE_PROMPT_IDS`),
  виден в `describe().extraPrompts` и правится ручкой
  `PUT /v1/profiles/:id/prompts/:promptId`;
- срок — с диалогом, три оператора: `clear` уносит, `deleteProfile` уносит,
  `sweep` снимает по сроку профиля.

## Отказы хода

| Код | Когда | Оплачено |
|---|---|---|
| `search_unavailable` | адреса сервера MCP у сервиса нет | нет |
| `search_refused` | отказ инструмента или окна лимитера службы `rag` | нет |
| `search_failed` | служба не ответила | нет |
| `search_empty` | первый поиск вернул пустую выдачу | нет |
| `rerank_invalid` | реранкер ответил не по схеме | да, вызов реранкера |
| `answer_invalid` | ответ не по форме: чужой номер источника, `answered` без фрагментов | да, вызов ответа |
| `budget_too_small` | запрос с фрагментами не влезает в потолок этапа | да, отбор |
| прочее | как в дне 15 (`router_error`, `rate_limited`, `session_gone`, …) | по отказу |

Повтора ни у одного отказа нет: оплаченный отказ формы стоил бы столько же
второй раз (развилка Р4 дня 24).

| шестой вызов подписан своим промптом, а не промптом пополнения | тест «шестой вызов подписан промптом stage.task, а не промптом пополнения» |

| переписывание видит два прошлых хода | тест «переписывание видит прошлые ходы, а не только последнюю реплику» |
| потолок состояния 4000 знаков и подрезка под него | тест «потолок состояния 4000 знаков: длиннее не пишется, и подрезка его держит» |
| метка блока состояния обезврежена | тест «состояние задачи в промпте обезврежено: закрывающая метка внутри не рвёт блок» |
| пустой отбор — «не знаю», а не ответ по памяти | тест «пустой отбор: ход успешен, источников нет, исход — «не знаю»» |
| состояние видно странице после перезагрузки | тест «чтение диалога отдаёт состояние задачи: панель переживает перезагрузку страницы» |
| отказ поиска на оплаченном ходе не говорит «Модель не вызывалась» | тест «оплаченный ход не говорит „Модель не вызывалась“: отказ поиска называет, что уже оплачено» |
| форма ответа обязательна | тест «ответ со чужим номером источника — отказ формы, повтора вызова нет» |
| путь источника — из отбора, а не из ответа модели | тест «путь источника берётся из отбора: выдуманный путь модели виден, но не подменяет настоящий» |

Чего не держит ничто: достоверность путей в тексте ответа (их не сверяет ни
один шаг — I-7 и I-9 к дням 22–25 неприменимы) и граница блока данных при
фрагменте, в котором встретился дословный шаблон блока указаний.
