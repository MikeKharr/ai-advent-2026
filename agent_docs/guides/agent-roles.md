# Роли агентов и протокол передачи

Роли определены как Claude Code subagents в `.claude/agents/*.md` и вызываются по имени. Роль — это записанный в репозиторий промпт, поэтому её поведение воспроизводимо и улучшаемо, а не зависит от формулировки запроса в конкретный день.

## Зачем делить работу на роли

1. **Экономия контекста** — ревьюер, читающий только diff, дешевле и внимательнее того, кто держит всю архитектуру.
2. **Состязательное разделение** — агент, который пишет код, не должен его одобрять. Это самое ценное правило здесь.
3. **Воспроизводимость** — роль версионируется вместе с кодом.

## Роестр

| Роль | Владеет | Никогда |
|---|---|---|
| `architect` | Дизайн системы, ADR, доменная модель | Не пишет продакшн-код |
| `product-analyst` | Объём, сценарии, критерии приёмки | Не выбирает технологии |
| `backend` | Серверная логика, API-маршруты, фоновые задачи | Не обходит слой лимитов |
| `design` | Визуальный язык, дизайн-корпус, раскладка и состояния экрана до кода | Не пишет продакшн-код; не ревьюит |
| `design-review` | Гейт мержа для UI, скилл `/design-review` | Не правит код; не ревьюит свою раскладку или реализацию |
| `frontend` | UI, формы, доступность, статика | Не изобретает API |
| `data` | Схема кэша, миграции, производительность запросов | Не пишет деструктивную миграцию без плана |
| `compliance` | Секреты, расход средств, защита от злоупотреблений | Не одобряет собственное исключение |
| `qa` | Стратегия тестирования, e2e, регрессии | Не правит код, чтобы тест позеленел |
| `platform` | VPS, Docker, CI/CD, секреты, наблюдаемость, стоимость | Не хранит секрет в репозитории |
| `reviewer` | Гейт мержа | Не пишет исправление — сообщает, автор чинит |
| `docs` | `agent_docs/`, история, ADR, витрина в Drive | — |

Полные описания и граничные правила — в `.claude/agents/<role>.md`. Модель
и усилие — свойство роли в её фронтматтере (ADR `2026-09-13-1800`):
fable/high у проектирования и гейтов, opus/medium у реализации, opus/low у
записи. Ключевые skills Османи предзагружены в роли через `skills:`.

## Протокол передачи

```text
Владелец (Михаил)
   │ намерение
   ▼
product-analyst ──► критерии приёмки
   │
   ▼
architect ──► ADR (если решение значимое) ──► ГЕЙТ: согласование владельца
   │
   ├──► data ─────────► схема кэша
   ├──► backend ──────► реализация + unit-тесты
   └──► design ───────► раскладка, иерархия, состояния (до кода)
          │
          ▼
        frontend ─────► UI
          │
          ▼
        design-review ► /design-review ──► ГОТОВО | ПРАВКИ | ПЕРЕДЕЛАТЬ
                          │
                          ▼
                  qa ──► тесты из критериев, не из кода
                          │
                          ▼
         reviewer + compliance ──► гейт мержа
                          │
                          ▼
                  platform ──► деплой ──► ГЕЙТ: согласование владельца
                          │
                          ▼
                  docs ──► запись в development-history + витрина в Drive
```

**Два гейта человеческие, а не автоматические:** принятие ADR и продакшн-деплой. Всё между ними может идти автономно.

Схема выше — полный цикл для класса A (деньги, данные, ключи). Класс B
(обычный код) идёт без `compliance`, если дифф не касается env, лимитов и
ключей, и без раскладки, если экран существующий. Класс C (документы,
конфиг CI, лендинг) проходит только механический CI. Исполняемая версия
протокола с критериями выхода — скилл `/day-cycle`.

**Перепроверка — тем же экземпляром.** После правок блокирующих находок
автор возвращает работу тому же ревьюеру через SendMessage: контекст у
него сохранён, перепроверяется исправленное, а не всё заново.

## Правила, общие для всех ролей

1. **Проговаривать допущения до действия.** Если требование неоднозначно — назвать неоднозначность и выбранное допущение, затем продолжать. Не выбирать молча.
2. **Маленькие обратимые изменения.** Одна забота — один PR.
3. **Читать до записи.** Не предлагать правку файла, который не прочитан в текущем контексте.
4. **Ссылаться на ограничение.** Если выбор продиктован ADR или инвариантом — указать его файл в описании PR.
5. **Эскалировать, а не импровизировать** во всём, что касается ключа, денег и достоверности новостей.
6. **Сообщать неуверенность как неуверенность.** Уверенный неверный ответ хуже отмеченного неизвестного.

## Трезвая оценка

Разделение ролей — дисциплина, а не гарантия. Несколько агентов могут иметь общее слепое пятно, а ревьюер не поймает то, что ему не сказали искать. Реально держат **механические** контроли — CI, негативные тесты, branch protection, docs-guard, — потому что они падают закрыто. Роли дают лучшие черновики и более ранние возражения, но не заменяют чтение владельцем того, что мержится.
