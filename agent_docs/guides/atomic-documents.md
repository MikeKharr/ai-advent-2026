# Атомарные документы

Правило для событийных документов: одно событие — один файл.

## Где применять

Применять для append-only коллекций, где новые записи независимы друг от друга:

- `agent_docs/development-history/` — итерации разработки;
- `agent_docs/adr/` — значимые решения;
- `agent_docs/reports/` — отчёты задач, если появятся;
- `agent_docs/audits/` — аудиты и ревью, если появятся;
- `agent_docs/investigations/` — расследования багов и research notes, если появятся.

## Где не применять

Не дробить документы текущего состояния только ради атомарности:

- `AGENTS.md`
- `CLAUDE.md`
- `README.md`
- `agent_docs/architecture.md`
- `agent_docs/glossary.md`
- `agent_docs/invariants.md`
- `agent_docs/snapshot.md`
- `agent_docs/backlog.md`
- `agent_docs/guides/*.md`

Такие документы остаются canonical state: их читают как актуальное состояние, а не как журнал событий.

## Имена файлов

Формат:

```text
YYYY-MM-DD-HHMM-short-title.md
```

Пример:

```text
2026-09-07-1520-project-bootstrap.md
```

Правила:

- дата и время — реальный момент создания файла по UTC: взять командой `date -u +%Y-%m-%d-%H%M` в момент создания. Время не оценивать, не выводить из соседних имён и не переносить на «день адвента»;
- имя уже занято (тот же `YYYY-MM-DD-HHMM`) — следующая минута, не следующий час и не следующий день;
- заголовок H1 `[YYYY-MM-DD HH:MM]` повторяет имя; отдельная строка `Дата:` не нужна, дата решения владельца в статусе — реальная;
- правило действует для `adr/`, `development-history/` и `design/`;
- имена до PR #26 включительно (07–08.09) — в UTC+7 и не переименовывались, после — в UTC (решение о датах в именах, PR #109); старое имя переименованного документа → новое — таблица в `development-history/2026-09-11-1104-rename-future-dated-docs.md`;
- `short-title` писать латиницей в kebab-case;
- не использовать ручную сквозную нумерацию;
- не создавать общий индекс, который нужно обновлять при каждой записи;
- collection README описывает правила, но не обязан перечислять все записи.

Формат проверяется в CI (`.github/workflows/docs-guard.yml`).

## Чтение контекста

Фиксированного числа записей для чтения нет. Агент сам выбирает глубину по задаче.

Ориентиры:

- риск и обратимость изменения;
- затронутые файлы и подсистемы;
- связанные ADR;
- результаты поиска по ключевым словам, путям и названию задачи;
- необходимость восстановить причины прошлого решения.

## Архивация

Атомарные событийные записи не ротировать и не архивировать по возрасту. Порядок в каталоге — следствие реального времени в имени, а не цель: документ, уточняющий более ранний, ссылается на него текстом и стоять после него в листинге не обязан. Старые записи не создают конфликтов при добавлении новых.
