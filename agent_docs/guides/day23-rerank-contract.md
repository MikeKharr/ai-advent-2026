# Контракт запуска `rerank-agent` (день 23)

Источник истины — код: `agents/src/rag-agent.js` (`createRagAgent`,
опция `pipeline`) и `agents/src/rag/retrieve.js`. Этот файл — то же самое
словами, чтобы страница дня 23 писалась параллельно с агентом.
Решение — ADR `2026-10-05-0544`, п. 1.

## Вход

`POST /v1/runs` сервиса агентов, `agentId: "rerank-agent"`, `input`:

| Поле | Значение |
| --- | --- |
| `question` | непустая строка, до 600 знаков |
| `mode` | `rag`, `rerank` или `rewrite` — умолчания нет |

Режимы: `rag` — конвейер дня 22 (пять фрагментов, отбора нет; это «до»).
Системный промпт у записи `rerank-agent` свой — он на строку длиннее
промпта дня 22 (предупреждение о пропусках в номерах), поэтому «ровно день
22» верно про конвейер и неверно про промпт;
`rerank` — десять кандидатов → реранкер → не больше пяти; `rewrite` — то же
плюс переписывание вопроса и объединение двух выдач. Режима `norag` нет.

## Нумерация

Номер `[n]` присваивается кандидату один раз — при объединении, в порядке
убывания близости — и дальше не меняется: под ним кандидат уходит реранкеру,
под ним же в промпт ответа, под ним стоит в `candidates` и в `sources`.
Поэтому `[7]` в тексте ответа и седьмая строка списка кандидатов — одно и то
же место, а у оставшихся номера идут **с пропусками**: `sources` может быть
`[2], [7], [3]`. Страница не перенумеровывает.

## Результат успешного запуска (`result`)

| Поле | Тип | Что это |
| --- | --- | --- |
| `mode` | строка | режим запуска |
| `outcome` | `"answered"` \| `"unknown_filter"` | исход; поля нет у `rag-agent` дня 22 |
| `rewritten` | строка \| `null` | переписанный запрос; `null` в режимах `rag`/`rerank` и тогда, когда переписывание не дало нового запроса |
| `rewriteSearch` | `null` \| `"skipped"` \| `"ok"` \| `"empty"` \| `"failed"` | что стало со **вторым** поиском: его не было / переписывание не дало запроса / нашёл / вернул пусто / служба отказала |
| `candidates` | список \| отсутствует | все кандидаты **до** отбора, в порядке близости; в режиме `rag` поля нет |
| `sources` | список | фрагменты **после** отбора, в том порядке, в каком ушли модели |
| `answer` | строка \| `null` | текст ответа; `null` при `outcome: "unknown_filter"` |
| `refused` | булево | модель сказала «В найденных фрагментах ответа нет»; при `unknown_filter` — `true` |
| `index` | объект | `commit`, `strategy`, `chunks` индекса |
| `rpc` | объект \| `null` | тела JSON-RPC **первого** поиска: `server`, `method`, `request`, `response`, `status`, `ms`, `clipped` |
| `rpcRewrite` | объект \| `null` | то же для **второго** поиска; `null`, если его не было или он отказал |
| `tokens` | число | токены **только вызова ответа** (при `unknown_filter` — оценка входа реранкера). Вызовы переписывания и реранкера сюда не входят: полный расход запуска страница по этому полю не покажет |
| `budgetLeftUsd` | число \| `null` | остаток суточного бюджета по ответу роутера на вызов **ответа**; при `unknown_filter` — `null` |
| `truncated` | булево | ответ упёрся в потолок токенов |
| `model` | объект \| `null` | провайдер и модель ответа |
| `durationMs` | число | весь запуск |

Элемент `candidates[]`: `n`, `source`, `section`, `score` (косинус, может
быть `null`), `relevance` (`0`/`1`/`2` от реранкера), `kept` (булево),
`from` (`original` / `rewritten` / `both`), `snippet` (первые 400 знаков —
ровно то, что видел реранкер; полного текста здесь нет намеренно).

Элемент `sources[]`: `n`, `source`, `section`, `score`, `relevance`, `from`,
`text` (как отдала служба, до 2000 знаков), `truncated`. В режиме `rag`
отбора не было: `relevance` и `from` у источников отсутствуют, нумерация
сплошная 1–5, а `candidates`, `rewritten` и `outcome` не приходят вовсе —
это ровно ответ дня 22.

## Стадии и события

Новых стадий нет — используются существующие (`agents/src/runs.js`).
Порядок в режиме `rewrite` (в `rerank` нет шагов 2–3, в `rag` — 2–5):

1. `received` — `data`: `mode`, `model`, `maxTokens`, `questionChars`,
   `strategy`, `limit` (10 у `rerank`/`rewrite`, 5 у `rag`).
2. `rpc` + `planning` («Нашёл N фрагментов») — поиск по **исходному**
   вопросу; `data.query`, `data.limit`, `data.index`, `data.sources`.
3. `llm_call` / `llm_result` с `data.purpose === "rewrite"` — переписывание.
4. `rpc` + `planning` — поиск по переписанному запросу; затем `planning`
   «Переписал вопрос и поискал ещё раз» (`data.rewritten`, `data.found`,
   `data.rewriteSearch`), уровня `warn` при пустой выдаче. Если нового
   запроса не вышло — `planning` уровня `warn` «Переписывание не дало
   нового запроса»; если служба на втором поиске отказала — `planning`
   уровня `warn` «Поиск по переписанному вопросу не удался»
   (`data.code`), и запуск идёт дальше.
5. `llm_call` / `llm_result` с `data.purpose === "rerank"`, затем `planning`
   «Реранкер оставил K из N» — `data.kept`, `data.candidates` (без текстов).
6. `llm_call` / `llm_result` без `purpose` — вызов ответа.
7. `done`.

Отличить вызовы друг от друга страница обязана по `data.purpose`: у вызова
ответа этого поля нет.

## Отказы (`status: "failed"`, поле `error`)

| `code` | Когда | `paidNothing` |
| --- | --- | --- |
| `search_unavailable` | адреса сервера MCP у сервиса нет | `true` |
| `search_failed` | сервер не ответил | `true` |
| `search_refused` | отказ инструмента или окна лимитера — словами службы | `true` |
| `search_empty` | **первый** поиск вернул пустую выдачу | `true` |
| `rerank_invalid` | реранкер ответил не по схеме (повтора нет) | `false` |
| `router_error` / `rate_limited` / `budget_exceeded` | отказ роутера на любом из трёх вызовов | по ответу роутера |

**Что из этого может прийти после оплаченного вызова.** Все четыре кода
`search_*` возможны только на **первом** поиске, а он идёт раньше любого
вызова модели во всех режимах, — поэтому у них `paidNothing: true` и слова
«Модель не вызывалась» честны. Второй поиск режима `rewrite` запуск не валит
вовсе: его пустота и его отказ становятся полем `rewriteSearch` и записью
ленты уровня `warn`, а запуск идёт дальше по кандидатам исходного вопроса.
После оплаченного вызова приходят только `rerank_invalid`
(`paidNothing: false`) и отказы роутера на вызовах реранкера и ответа — у
них `paidNothing` ставится по ответу роутера.

## Исход «ни один фрагмент не относится»

Реранкер не оставил ни одного кандидата (`relevance ≥ 1`) — запуск
**успешен**, `outcome: "unknown_filter"`, `answer: null`, `sources: []`,
`candidates` на месте, модель ответа **не вызывалась**. Страница показывает
шаблон «Не знаю: ни один из N найденных фрагментов к вопросу не относится»
и список кандидатов с оценками. Запуск успешен, а не провален, потому что у
него есть что показать и что померить, а провал унёс бы `result` целиком.
